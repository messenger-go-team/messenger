# Автодеплой staging с отдельными правами (#37)

Actions проверяет успешность Go CI и Frontend CI для точного SHA ветки
`main`. Завершение любого из двух CI запускает эту проверку. Выкат и
публикация статуса занимают один общий слот GitHub для staging. Если
ожидающее задание заменено или `main` продвинулся, получившее слот
задание сверяет оба CI для актуального SHA `main` и продолжает только
при их успехе. На VPS под файловой блокировкой приёмник проверяет SHA
и оба CI до и после сборки.

Frontend CI публикует `web-dist-<SHA>-attempt-<номер>` после сборки профиля
staging. Deploy staging выбирает артефакт успешного push-запуска для текущего
`main` и передаёт ZIP по stdin команды `deploy-web <SHA>`. VPS сверяет
размер и SHA-256 с публичными метаданными того же запуска GitHub. Ещё один
секрет или токен на VPS не требуется. Подробности переключения и восстановления
есть в [порядке релиза](staging-release.md).

GitHub Deployments отражает подтверждённые выкаты через Actions.
При временном сбое GitHub API повторите запуск для того же SHA, пока
он актуален. Ответ `already_active` подтверждает рабочий релиз и даёт
тот же идентификатор переключения. Workflow находит запись для этого
переключения и дописывает недостающий статус. Состояние после ручного
отката смотрите на VPS в `.release-state/current` и в журнале оператора.

## Граница полномочий на общем VPS

- Отдельный пользователь Linux `messenger-stage`, без `sudo`, группы
  `docker` и доступа к системному `/var/run/docker.sock`. У него свой
  rootless Docker на `/run/user/<UID>/docker.sock`.
- Отдельные домашний каталог, Compose project, Docker-сеть, том
  PostgreSQL и секреты staging. В пользовательские контейнеры
  не монтируются системный сокет Docker, системные файлы, каталоги
  чужих сервисов, TLS-ключи и данные production.
- Администратор управляет внешним Nginx и TLS. Внешний Nginx
  отдаёт веб-сборку staging под `/app/` и проксирует REST и WSS
  этого домена на `127.0.0.1:18080`. На этом порту работает
  внутренний Nginx rootless-контейнера. Он использует
  публичные snippets и пересылает запросы в Auth, History и Chat.
- Производственный Nginx, системный Docker и production Compose
  остаются за пределами доступа `messenger-stage`. Rootless
  делит ядро и ресурсы VPS; отдельная VM создаёт более жёсткую границу.

## Подготовка новой копии staging

1. Администратор создаёт `messenger-stage`, настраивает rootless Docker
   для этого пользователя и включает его пользовательский сервис.
   Следуйте [инструкции Docker Rootless](https://docs.docker.com/engine/security/rootless/).
   На общем VPS системный Docker нужен остальным сервисам; при
   установке отдельного rootless daemon оставьте системный запущенным.
   Проверьте `docker info` на пользовательском сокете. Системный сокет
   должен быть недоступен тому же пользователю.
2. В `~/messenger36-stage` скопируйте
   [compose.yaml](staging-rootless/compose.yaml), внутренний
   [nginx.conf](staging-rootless/nginx.conf) и необходимые snippets из
   `deploy/nginx/snippets`. До старта ingress создайте
   `nginx/snippets/release-marker.conf` со строкой
   `return 200 "baseline";`. Запишите staging-only параметры Compose
   в файл `.env` с правами 0600. `STAGING_BASE_SHA` ссылается на
   подготовленные образы baseline из проверенного main, а остальные
   переменные описаны в Compose. Пароли DSN кодируются для URL.
3. Запустите PostgreSQL нового проекта. Восстановите staging-дамп в
   его отдельный том. Владельцев объектов и рабочие роли Auth/History
   подготовьте в новой БД до восстановления ACL. Прежний VPS-стенд
   продолжает обслуживать домен на время подготовки. Соберите или
   загрузите три образа baseline и запустите Auth/Chat/History/ingress.
   Проверьте готовность и доступ по локальному HTTP `127.0.0.1:18080`.
4. Переключите staging в согласованное окно по инструкции ниже.
5. От имени `messenger-stage` проверьте, что он управляет своим Docker,
   не член групп `sudo`/ `docker`, не может открыть системный сокет и
   менять файлы внешнего Nginx и TLS. Эти проверки проводятся на
   целевом VPS до выдачи ключа Actions.

## Переключение staging и возврат

1. Оставьте CD отключённым. Переведите публичный staging в режим
   обслуживания и остановите Auth, Chat, History и другие процессы,
   пишущие в старую БД. Остановка Chat закрывает и уже открытые WSS.
   Остановите приложения на новой стороне на время восстановления.
   Оставьте PostgreSQL доступным администратору для дампа и сверки.
   Для выделенных рабочих ролей старого staging запретите вход
   (`ALTER ROLE ... NOLOGIN`), завершите их оставшиеся сессии и проверьте
   `pg_stat_activity`. Держите прежнюю сторону без записи до окончания
   переключения.
2. Снимите финальный дамп старой БД. Восстановите его в чистой целевой
   БД с подготовленными ролями и ACL. Сверьте версии и чистоту схемы,
   количество и последние ID или контрольные записи в таблицах Auth,
   History и Later, а также доступ под рабочими ролями. Храните финальный
   дамп и прежний том до окончания приёмки.
3. Запустите новый Compose и проверьте readiness через loopback.
   Направьте внешний Nginx на
   [внутренний loopback-порт](staging-rootless/outer-location.conf.example).
   Если Nginx в контейнере, заранее проверьте доступ к loopback хоста.
   Проверьте `nginx -t` перед reload, затем HTTPS и публичный WSS.
   На время этих проверок ограничьте доступ оператором, затем снова
   откройте staging команде.
   Сохраните домен, ACME и сертификаты под управлением администратора.
   Используйте тестовый аккаунт, сохранённый финальным дампом, или
   создайте его после восстановления. Сохраните его
   `{"username":"…","password":"…"}` в
   `~/messenger36-stage/wss-probe.json` с правами 0600.
4. Если требуется вернуть старый стенд, снова закройте трафик и
   остановите запись. Пока в новой БД после восстановления не было
   записей, прежняя БД остаётся актуальной. После первой записи,
   включая записи от smoke, источником считается новая БД. Снимите
   с неё дамп после остановки всех писателей, восстановите в отдельной
   чистой БД старого стенда и проверьте совместимость его приложений,
   схему и данные. До успешной сверки держите трафик закрытым. После
   неё верните вход только рабочим ролям выбранной БД, запустите старый
   стек с этой БД и верните маршрут Nginx.
   Сохраните обе исходные копии на случай ошибки восстановления.

## Одноразовая настройка публикации веб-сборки

1. Подготовьте рабочую веб-версию, которую можно вернуть. На действующем
   стенде она уже лежит в `/var/lib/messenger/acme/staging-web` после #46.
   На новом стенде разместите под `releases/<SHA>/app/` файлы проверенного
   staging `dist`, запишите полный SHA в `releases/<SHA>/REVISION` и
   создайте относительный симлинк `current → releases/<SHA>`. Проверьте
   `/app/login`, `/app/contacts` и MIME-типы JS/CSS через HTTPS.
2. Выдайте пользователю `messenger-stage` право писать только в каталоги
   веб-публикации. Команды администратора для уже работающего staging:

   ```bash
   web=/var/lib/messenger/acme/staging-web
   install -d -m 0755 -o messenger-stage -g messenger-stage "$web" "$web/releases"
   sudo -u messenger-stage test -w "$web/releases"
   sudo -u messenger-stage test -r "$web/current/app/index.html"
   ```

   Оставьте родительский ACME-каталог и конфигурацию внешнего Nginx под
   управлением администратора. Передаваемый архив распаковывается от
   имени `messenger-stage`. Nginx требуется доступ для чтения.
3. Во внешнем TLS-сервере staging подключите
   [outer-web-app.conf.example](staging-rootless/outer-web-app.conf.example)
   рядом с [прокси для API и WebSocket](staging-rootless/outer-location.conf.example).
   Если ручной include #46 уже установлен, сравните его с шаблоном.
   Путь `/var/www/acme` внутри контейнера прокси соответствует
   `/var/lib/messenger/acme` на VPS. Выполните `nginx -t` и reload,
   если конфигурация изменилась.
4. До мержа PR установите обновлённый
   [SSH-приёмник](staging-ssh-receiver.sh) как root-owned файл 0755,
   сохранив предыдущую копию. Старый протокол `deploy <SHA>` обслуживает
   прежние версии приложения в переходный период. Версии с веб-автодеплоем
   требуют `deploy-web <SHA>` с ZIP. После установки проверьте `probe`.
5. После мержа откройте `Deploy staging` для текущего `main`. В журнале
   проверьте имя архива, строку `web SHA … passed HTTPS smoke` и
   `STAGING_RESULT`. Повторите workflow вручную. Результат
   `already_active` подтверждает тот же снимок и сохраняет точку отката.
   Проверьте прямое открытие и обновление `/app/login` и
   `/app/contacts` в браузере.

## GitHub и SSH после подтверждения границы

- Repository variable `STAGING_CD_ENABLED=false`. Эта переменная
  читается до входа в Environment. Старый флаг
  `STAGING_DEPLOY_ENABLED` больше не используется.
- Environment `staging` разрешает только `main`. Переменные:
  `STAGING_SSH_HOST` и `STAGING_KNOWN_HOSTS` с закреплённым ключом
  хоста. Secret: отдельный закрытый ключ `STAGING_SSH_KEY`.
- Установите SSH-приёмник как root-owned
  `/usr/local/sbin/messenger-staging-receive` с режимом 0755.
  Разрешённый открытый ключ добавляется к `messenger-stage`, не к root:

  ```text
  restrict,command="/usr/local/sbin/messenger-staging-receive" ssh-ed25519 <public-key> messenger-staging-actions
  ```

  Проверьте `probe` со строгой проверкой host key, отказ для
  произвольной команды и отказ сменить релиз на непроверенный SHA.
  Публичные API GitHub читаются по HTTPS. Если состояние SHA или CI
  нельзя подтвердить, приёмник прекращает попытку.
- После merge и проверок выставьте `STAGING_CD_ENABLED=true`. Первый
  запуск можно выбрать вручную в Actions для текущего main. Запишите
  SHA, ссылку на Actions, результаты WSS и smoke.
  Отключение переменной останавливает новые вызовы из Actions;
  удаление строки открытого ключа на VPS отзывает доступ.
