# Переключение и откат staging (#37)

[Скрипт staging-release.sh](staging-release.sh) запускается от пользователя
staging с доступом к отдельному rootless Docker. Базовый Compose,
сеть и внутренний Nginx должны быть готовы. Подготовка сервера описана
в [staging-actions.md](staging-actions.md).

## Что принимает скрипт

```bash
bash "$RELEASE_DIR/deploy/staging-release.sh" deploy "$SHA" "$RELEASE_DIR"
```

`SHA` - полный SHA разрешённого коммита. В каталоге релиза лежат
`REVISION`, статические `migrate` и `staging-wss-probe`, SQL из
`services/{auth,history}/migrations` и публичный snippet Nginx.
В веб-режиме там также находятся `web.zip` и `web.digest`
(64 знака SHA-256), полученные из Frontend CI для того же SHA. В rootless
Docker уже должны быть образы
`messenger36-stage-{auth,chat,history}:$SHA` с OCI-меткой
`org.opencontainers.image.revision=$SHA`. В режиме CD их готовит SSH-приёмник.

По умолчанию Compose находится в `~/messenger36-stage/compose.yaml`,
проект называется `messenger36-stage`, внутренний Nginx -
`messenger36-ingress`. Его snippets лежат в
`~/messenger36-stage/nginx/snippets`. Для локальной лаборатории параметры
задаются через `STAGING_ROOT`, `STAGING_PROJECT`, `STAGING_INGRESS`,
`STAGING_SNIPPETS` и `STAGING_URL`.

`~/messenger36-stage/wss-probe.json` - приватный файл (0600) с
`username` и `password` отдельного тестового аккаунта Auth.
Переопределения для диагностики - `STAGING_WSS_CREDENTIALS` и
`STAGING_WSS_PROBE`. Проба входит через HTTPS и ждёт `101` с
`messenger.v1` на публичном `/ws`. Секреты, JWT и тело ответа она
не пишет в отчёт.

## Порядок выката

1. Сверяем образы, сеть и mounts. Сохраняем прежние image ID и
   публичный snippet. Проверяем версии схемы. Поддерживаются
   Auth v1 и History v1/v2/v3/v4 с `dirty=false`. Перед обновлением History
   с v1, v2 или v3 сохраняем дамп. Для будущих миграций сначала проверяем
   совместимость предыдущей версии приложения с новой схемой.
2. Применяем миграции отдельным контейнером. Проверяем Auth v1 и History v4
   с `dirty=false`. Выдаём рабочей роли минимальные права для Later и
   UPDATE двух публичных курсоров и доступ к таблице временных разрешений
   presence. Compose переключает Auth, Chat и History.
   PostgreSQL продолжает работать в том же проекте.
3. Проверяем ID образов, `/healthz` и `/readyz`. Копируем публичный
   snippet, выполняем `nginx -t` и reload внутреннего Nginx. Сверяем
   маркер загруженной конфигурации через локальный порт внутри
   контейнера. Если передан веб-артефакт, сохраняем прежнюю ссылку в
   снимке и заменяем `staging-web/current` атомарным переименованием.
   Затем проверяем публичный HTTPS, редирект корня, HTML трёх SPA-маршрутов,
   содержимое и MIME JS/CSS и WSS handshake. Печатаем SHA веб-сборки после
   успешного веб-smoke.
4. После проверок сохраняем независимую копию в `verified` и записываем
   SHA-256 каждого файла. Сохранение рабочей копии входит в подтверждение
   релиза. При ошибке сохранения скрипт возвращает прежний релиз.
   Если повтор обнаруживает повреждённую копию, он атомарно ставит указатель
   на новую копию из проверенной текущей сборки. Если текущая
   веб-версия повреждена, альтернативный снимок из этой копии становится
   целью отката нового релиза. Повтор активного SHA с таким же SHA-256 ZIP
   проверяет состояние без пересоздания контейнеров и без потери
   предыдущей точки отката. При обоих исходах скрипт возвращает SHA и
   идентификатор переключения для восстановления записи GitHub Deployments.
   Другой ZIP того же коммита проходит новый выкат с явной записью обоих
   дайджестов. HTTP smoke печатает SHA-256 фактически проверенного архива.

После первого переключения Compose использует `compose.release.yaml`
как override. Для ручного управления указывайте его после базового Compose.
Снимки в `.release-state/` и соответствующие теги Docker нужны для отката.

## Настройки лимита отправки Chat

На уже подготовленном стенде добавьте `WS_SEND_INTERVAL` и `WS_SEND_BURST`
в `services.chat.environment` файла `~/messenger36-stage/compose.yaml` по
[шаблону rootless Compose](staging-rootless/compose.yaml). Значения по
умолчанию составляют `200ms` и `10`. При переопределении задайте значения
в `~/messenger36-stage/.env`. Проверьте итоговый Compose и примените настройки
при выкладке следующего нового SHA. Повтор активного SHA не пересоздаёт Chat.

## Откат

Перед ручным откатом отключите CD, отмените ожидающие запуски и дождитесь
завершения текущего job `Release to staging`, включая публикацию статуса.
После отката запишите фактический SHA и результат smoke в журнале
оператора. История GitHub Deployments показывает выкаты через Actions,
а фактическое состояние проверяется на VPS.

```bash
bash "$RELEASE_DIR/deploy/staging-release.sh" rollback
```

Запускайте из готового каталога релиза с WSS-пробой. Соблюдайте тот же
Docker-контекст пользователя staging. Если выкат C после A → B сорвался,
скрипт восстанавливает B, а ручной откат остаётся доступен на A. Штатный откат восстанавливает образы, публичный snippet внутреннего
Nginx и ссылку на веб-сборку из снимка. До переключения контейнеров
скрипт сверяет целевой каталог с подтверждённой копией и при повреждении
восстанавливает веб-файлы в отдельный каталог. При сбое переключения ссылка
восстанавливается даже при последующей ошибке возврата бэкенда.
Сохранённая версия проходит readiness, HTTPS, веб-smoke и WSS-проверки.
На действующем rootless стенде после первого веб-выката используйте
версию скрипта, поставленную с #166 или более поздним релизом.

Проверьте фактическую веб-версию после отката:

```bash
web=/var/lib/messenger/acme/staging-web
readlink "$web/current"
cat "$web/current/REVISION"
curl --fail --silent --show-error https://staging.tidingm.ru/app/contacts >/dev/null
```

Для тренировки ошибки JS MIME используйте изолированный тест ниже. Для
ручной проверки на стенде сначала запишите активный SHA, затем выполните
`rollback` в согласованное окно. После проверки прежнего SHA и
работоспособности приложения включите CD и повторите выкат текущего
`main`. Это не откатывает схему БД.
Схема History v4 и данные PostgreSQL, включая оба публичных курсора, сохраняются.

Миграция v4 упорядочивает отзыв членства и отправку presence. Чтобы вернуть
схему на v3, сначала остановите Chat/History с presence или верните прежние
образы. Затем выполните отдельный откат History на один шаг. Миграция v4
добавляет функции, триггеры и временную таблицу разрешений. Данные чатов
и публичные курсоры сохраняются. Откат v4 ждёт завершения ранее разрешённых
сетевых записей.

Откат миграции v3 - отдельная операция. При переходе на v2 оба публичных
столбца и накопленные в них значения удаляются. Записи Later и приватные
курсоры сохраняются.

Перед записью pending скрипт готовит веб-каталог для аварийного возврата
и сохраняет его путь в снимке. Аварийное восстановление использует этот
каталог и проверяет его по HTTPS. Оно может завершиться, даже если после
переключения каталог verified стал недоступен.

Если переключение прервалось до подтверждения нового релиза, `rollback`
сначала восстанавливает состояние перед попыткой. При ошибке восстановления
снимок и пометка незавершённой попытки остаются на диске для диагностики.

Локальная регрессия использует реальные приложения, PostgreSQL и два Nginx.
Она собирает предыдущий релиз со схемой v2 из зафиксированного коммита, применяет
v4 и проверяет возврат предыдущих образов, readiness History, ответ 404 на
`/receipts` и сохранение схемы и курсоров. Затем проверяет повторный выкат,
автоматический откат после ошибок Nginx, JS MIME и WSS и ручной
возврат к рабочей веб-версии.
Для запуска нужен Git-клон с историей `main`:

```bash
python3 deploy/test-staging-release.py
```

При `401` на авторизованном запросе `/receipts` тест указывает request ID,
время HTTP-ответа и значения JWT `iat` и `exp`. Сравните время ответа с
`iat` и проверьте журнал синхронизации часов, если токен выглядит
выпущенным в будущем. Сам токен в отчёт не попадает.
