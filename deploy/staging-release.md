# Ручной запуск скрипта CD для staging (#37)

[Скрипт staging-release.sh](staging-release.sh) переключает существующий
Compose-проект staging на подготовленный релиз. Скрипт запускается на VPS
от пользователя с доступом к Docker, каталогу проекта и конфигу Nginx.
Для запуска нужны Bash, Docker Compose, curl и flock. PostgreSQL и Nginx
должны работать в сети проекта.

Для VPS из #36 значения по умолчанию: проект `messenger36-stage`,
каталог `/root/messenger36-stage`, контейнер `messenger36-ingress`,
snippets `/root/messenger36-nginx/snippets`, URL `https://staging.tidingm.ru`.
В локальной лаборатории эти значения задаются соответственно
`STAGING_PROJECT`, `STAGING_ROOT`, `STAGING_INGRESS`, `STAGING_SNIPPETS` и
`STAGING_URL`. Имя проекта должно начинаться с `messenger36-stage`,
а ingress должен использовать сеть этого проекта и указанный каталог snippets.
Сертификат и домен задаются существующим конфигом Nginx.

## Подготовка релиза

На машине сборки берём исходники нужного коммита. Полный SHA записываем
в `REVISION`, из этого же дерева собираем статический `cmd/migrate` для
Linux и архитектуры VPS. Готовый бинарник кладём в корень каталога релиза
как `migrate`. Скрипт читает SQL из `services/{auth,history}/migrations` и
публичный конфиг из `deploy/nginx/snippets/public-locations.conf`.

Пример подготовки образов на Docker Engine, который будет запускать релиз:

```bash
for service in auth chat history; do
  docker build --label "org.opencontainers.image.revision=$SHA" \
    -f "$RELEASE_DIR/services/$service/Dockerfile" \
    -t "messenger36-stage-$service:$SHA" "$RELEASE_DIR"
done
```

Образы также можно собрать отдельно и загрузить на VPS с теми же тегами
и метками. Настройки и секреты сервисов берутся из существующего Compose.
Мигратор получает параметры PostgreSQL из запущенного контейнера через pipe.

## Выкат и проверка

```bash
bash "$RELEASE_DIR/deploy/staging-release.sh" deploy "$SHA" "$RELEASE_DIR"
```

Скрипт сохраняет ID и теги прежних образов и текущий публичный snippet в
`.release-state/` рядом с Compose. Он проверяет, что схемы совместимы с
откатом. Поддерживаются чистая Auth v1 и History v1/v2. При переходе History
с v1 на v2 перед изменением сохраняется дамп PostgreSQL. Для будущих
миграций с изменением контракта схемы сначала обновите эту проверку и
протестируйте предыдущую версию приложения на новой схеме.

Отдельный мигратор применяет схемы перед переключением, затем выдаются
права Later рабочей роли `messenger36_history`. Compose пересоздаёт Auth,
Chat и History с подготовленными образами. Скрипт проверяет ID контейнеров,
`/healthz` и `/readyz` каждого сервиса через внутреннюю сеть, выполняет
`nginx -t`, reload и проверяет по HTTPS коды `/me` (401), `/later` (401)
и `/internal/users/test` (404).

Новый Compose override называется `compose.release.yaml`. В дальнейшем
в командах для управления сервисами нужно указывать его после базового
`compose.yaml`. Старый `compose.history-release.yaml` относится к ручному
выкату History и при запуске скрипта не используется. Метки, снапшоты и
образы предыдущего релиза нужны для отката. Очищать их можно после проверки,
что они больше не нужны действующему проекту.

## Откат

```bash
bash "$RELEASE_DIR/deploy/staging-release.sh" rollback
```

При провале переключения скрипт сам пробует вернуть предыдущие образы и
snippet и завершает исходный `deploy` с ошибкой. При ручном вызове
`rollback` возвращается один предыдущий релиз. Неудачный откат сохраняет
снимок и пометку о незавершённом переключении. После прерывания во время
переключения используй `rollback` перед повтором. Миграция v2 и данные
Later сохраняются при откате контейнеров. Ошибка самого мигратора
останавливает выкат до пересоздания сервисов. Если схема стала dirty,
диагностируйте её отдельно перед следующим выкатом.

GitHub Actions и настройка GitHub Secrets подключаются на следующем
этапе #37. Скрипт проверяет HTTP-доступность сервисов и маршрутов. Сценарии
с реальными пользователями остаются в приёмочных тестах.
