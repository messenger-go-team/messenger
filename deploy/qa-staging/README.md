# QA-staging для T50

QA управляет отдельным Docker Compose-проектом `messenger-qa-staging` под
Linux-пользователем `messenger-qa`. Стек содержит веб-клиент, Nginx, Auth, History,
Chat и собственный PostgreSQL. По умолчанию Nginx отдаёт обычные API и WSS
напрямую. Тестовый прокси включается для выбранного профиля браузера или
протокольного соединения. Команды управления доступны из QA-учётки на VPS.
[Критерии T50](https://github.com/messenger-go-team/messenger/issues/50).

## Администратору VPS. Сделать один раз

1. Выделите DNS-имя и свободный loopback-порт, например `19080`.
   Создайте пользователя `messenger-qa` с собственным rootless Docker и
   включите запуск пользовательского сервиса после выхода из SSH.
   Можно использовать тот же VPS или отдельную VM. Для общего VPS проверьте,
   что учётка QA не входит в `sudo` или `docker` и не имеет доступа к системному
   Docker-сокету, пользователю общего staging и его данным.
   [Как организован rootless Docker в проекте](../staging-actions.md).
2. Установите **публичный** SSH-ключ QA в `authorized_keys` пользователя
   `messenger-qa`. QA нужен вход только в эту учётку. Установите Git, Bash,
   OpenSSL и Docker Compose v2 в доступный ей PATH. Под этой учёткой
   клонируйте репозиторий в `~/messenger` и переключитесь на утверждённый
   SHA, включающий каталог `deploy/qa-staging`.
3. Из корня checkout выполните команды под пользователем `messenger-qa`.
   Подставьте своё DNS-имя и порт.

   ```bash
   bash deploy/qa-staging/qa.sh configure https://qa-messenger.example.org 19080
   bash deploy/qa-staging/qa.sh up
   ```

   `configure` создаёт отдельные случайные секреты в
   `deploy/qa-staging/.env` с правами 0600. `up` собирает фронтенд и бэкенд
   из чистого checkout одного SHA. Используйте пустой PostgreSQL проекта.
4. Настройте TLS на внешнем Nginx и добавьте отдельный виртуальный хост по
   [шаблону](edge-nginx.conf.example). Если внешний Nginx в контейнере,
   проверьте, что он достигает loopback хоста через host network или другое
   уже используемое на VPS соединение с хостом. Проверьте конфигурацию
   `nginx -t`, затем выполните reload. Откройте `/app/login` и
   `/revision.txt` через HTTPS и проверьте WSS `/ws` под одноразовой учёткой.
5. Передайте QA адрес HTTPS, SSH-хост, имя пользователя и SHA. Попросите
   QA самостоятельно выполнить `status`, `seed` и `restart-chat`. Затем QA
   ведёт прогоны. Обращение к администратору нужно при проблеме с DNS/TLS,
   потерянном техническом доступе, неисправности rootless Docker либо
   недоступности VPS.

Для смены версии остановите прогон. Проверьте checkout и назначьте его SHA
в `QA_REVISION` файла `.env`, затем выполните `qa.sh up`. Зафиксируйте новый SHA
для следующих прогонов. `up` сохраняет текущий QA-том, `reset --confirm`
создаёт пустой том на текущей сборке. Общий staging обслуживается своими
инструментами.

## Тестеру. Данные, прогон и восстановление

Подключитесь к выделенной учётке `messenger-qa` и выполняйте из
`~/messenger`. Ниже `qa` означает эту функцию в вашей SSH-сессии:

```bash
cd ~/messenger
qa() { bash deploy/qa-staging/qa.sh "$@"; }
qa status
qa seed later01 2
```

`seed` создаёт A, B, постороннего C, чат A–B и заданное число сообщений
от B. Код набора из 4–14 строчных букв или цифр должен быть новым. Для
пагинации можно создать 205 или 250 сообщений. Сохраните UUID пользователей,
чата и нужного сообщения. В выводе `seed` есть одноразовые пароли. Храните
его в приватном терминале или файле с правами 0600. Для тестов создания нового
личного чата регистрируйте отдельную пару. В браузере используйте независимые
профили A/B. Запускайте сбои по одному, особенно `storage-down` и профиль
медленного клиента, поскольку они меняют состояние всего QA-стенда.

- `qa restart-chat` штатно перезапускает только Chat и ждёт готовности. Для
  `REC-06` запишите `message.ack` и `message_id` до перезапуска. Проверьте
  WSS close 1001, переподключение, старые сообщения, отсутствие дублей и
  успешную новую отправку. Для `MSG-02` отправьте один `client_msg_id` из
  двух соединений, затем повторите после перезапуска. Оба успешных ack
  должны ссылаться на тот же ID, `qa inspect-chat CHAT` покажет одну строку.
- `qa reset --confirm` пересоздаёт тестовую БД с нуля. Все наборы и сессии
  этого QA-проекта удаляются. После сброса выполните `qa status`, затем
  `qa seed` с нужным кодом. Для свежих сценариев в текущей БД достаточно
  нового кода набора.
- После тестов с управляемыми правилами выполните `qa clear`. Она снимает
  HTTP/WS-правила и SQL-барьеры. Если применяли `storage-down` или
  `slow-profile on`, верните режим командами `storage-up` или
  `slow-profile off`. В завершение проверьте `qa status`.

### Данные и Auth

| Кейсы | Действия |
| --- | --- |
| LATER-16/17 | На свежих наборах сохраните Later-запись под A, который ещё не отправлял сообщений, и выполните `qa delete-message MESSAGE`, `qa delete-chat CHAT` или `qa revoke CHAT USER`. Проверьте исчезновение после обновления, отсутствие напоминания и 404 при действии из ещё открытого списка, как описано в кейсе. |
| LATER-18 | Сохраните активную запись, выполните `qa revoke CHAT USER`, проверьте, что она скрыта. Выполните `qa restore CHAT USER` и проверьте, что вернулась та же запись и состояние вычислено по свежему `server_time`. |
| AUTH-08 | Войдите под одноразовой учёткой, сохраните тестовую cookie приватно, выполните `qa expire-refresh USER`. Повтор с тестовой cookie должен дать 401. Команда истекает активные refresh-сессии указанной учётки. Гонку двух запросов с одним действующим refresh проверяйте отдельно на новой сессии. |
| AUTH-13 | `qa auth-check USER` проверяет закрытый маршрут снаружи, статусы запросов из внутренней сети и форму UserSummary. `qa inspect-auth USER` выводит признаки хеширования и сроки без значений хешей. Логи Auth сверяйте приватно на одноразовом потоке. |

Границу exp и поля JWT в `AUTH-06` проверяйте протокольным клиентом и
[тестом Auth с управляемыми часами](../../services/auth/internal/auth/service_boundaries_test.go).
Для испытаний в браузере используйте выданные самим QA-staging токены и
фактический HTTPS.

### Ошибки History и порядок commit

- `qa storage-down` делает таблицы History временно недоступными
  **во всём QA-проекте**. Для `HIST-04` проверьте 503 / `service_unavailable`
  на списке, истории и отметке прочтения. Для `LATER-22` отдельно проверьте
  создание/обновление, перенос и Done. Снимите отказ командой
  `qa storage-up`, повторите запросы и сверьте записи и курсоры.
- Для `MSG-05` выполните `qa gate save CHAT hold 45`, отправьте одно
  сообщение. Активный барьер задерживает вставку на 1,2 с внутри транзакции
  при стандартном RPC-таймауте 3 с. До записи не должно быть успешного ack.
  Снимите барьер `qa release-gate save CHAT`. Отдельно выполните
  `qa gate save CHAT reject 45`, отправьте сообщение и получите ошибку.
  `qa inspect-chat CHAT` и `qa gate-log` показывают состояние и срабатывание.
  Снимите отказ, повторите отправку с тем же `client_msg_id` и сверьте одну запись.
- Для `UNREAD-06` нужны два свежих набора по два сообщения B.
  В первом поставьте `qa gate read CHAT hold 45`, отправьте единственный
  `POST /chats/CHAT/read` с `{"seq":2}` от A. Когда в `qa gate-log`
  появится `held read`, начните отправку сообщения B. `qa wait-locks` во второй
  SSH-сессии показывает ожидающую транзакцию. Сразу вызовите
  `qa release-gate read CHAT`, учитывая 3-секундный RPC-таймаут отправки.
  Проверьте оба успешных ответа и `last_seq=3`, `last_read_seq(A)=2`,
  `unread_count(A)=1`. Во втором наборе включите прокси в профиле A и
  поставьте `qa arm hold-read CHAT USER_A 45`. Запустите
  `POST /read`. Когда `qa status` покажет совпадение правила, отправьте B и
  дождитесь ack. Затем `qa release hold-read`. Повторите проверку курсоров.
  Для прогона через UI правило `skip-extra-read` пропускает первый выбранный
  `POST /read` и подавляет последующие. В протокольном прогоне отправляйте
  этот POST своим клиентом и держите автоотметки браузера выключенными.
- Для `UNREAD-07` первый вариант - `qa gate read CHAT reject 45` и
  сверка, что курсор не продвинулся. Для второго используйте прокси
  от пользователя A и `qa arm drop-read CHAT USER_A 45`. Один успешный
  ответ 204 History после commit обрывается до gateway. Внешний Nginx может
  показать 502. Через `qa inspect-chat CHAT` подтвердите уже сохранённый
  курсор, затем повторите тот же `seq` и получите 204.

### Потеря событий и heartbeat

В профиле браузера, который должен видеть сбой, откройте DevTools на
QA-домене и установите cookie в консоли, затем перезагрузите вкладку:

```javascript
document.cookie = "messenger_qa_faults=1; Path=/; Secure; SameSite=Strict";
```

Для протокольного клиента используйте `wss://QA_HOST/ws?qa_fault=1` для
WS и `Cookie: messenger_qa_faults=1` для History. Обычные вкладки продолжают
ходить напрямую. По завершении удалите cookie и перезагрузите профиль.

- `qa arm drop-ack|drop-new|drop-both CHAT VIEWER 45 [CLIENT_MSG_ID]`
  подавляет выбранные события только для этого чата и получателя. Для
  `REC-03` до таймаута дополнительно включите
  `qa arm block-history CHAT VIEWER 20`, если клиент успевает догрузить
  сообщение раньше. Выполняйте варианты по отдельности на свежих данных.
  Для `REC-05` подавите только `message.new` для B, оставьте сокет B открытым,
  затем проверьте возврат вкладки и периодическую сверку истории. Счётчики
  совпадений показывает `qa status`. Используйте `qa release RULE` для
  нужного шага или `qa clear` между сценариями.
- Для штатного heartbeat в `REC-07` держите прямое WSS-соединение через
  Nginx больше 75 с. Для отсутствия Pong включите прокси у отдельной учётки
  и выполните `qa arm no-pong USER 70`. Проверьте, что Chat закрывает
  соединение после таймаута и освобождает ресурсы. Другие соединения
  продолжают нормально отвечать.
- Для медленного клиента подготовьте отдельный набор. Выполните
  `qa slow-profile on`, `qa arm slow-reader USER_B 30`, затем откройте новое
  проксируемое соединение B. Из второго терминала запускайте
  `qa burst CHAT USERNAME_A` с паролем тестового A на стандартном вводе.
  Утилита отправляет до 800 тестовых сообщений внутри QA-проекта.
  Снимите паузу примерно через 4,5 секунды после начала отправки, чтобы
  разблокировать TCP до таймаута записи. В терминале отправителя:

  ```bash
  IFS= read -rs -p 'Пароль тестовой учётки A: ' password
  printf '%s\n' "$password" | qa burst CHAT USERNAME_A &
  burst_pid=$!
  unset password
  sleep 4.5
  qa release slow-reader
  wait "$burst_pid"
  ```

  Проверьте ожидаемое закрытие 1013 и сохраните фактический код.
  После проверки выполните
  `qa slow-profile off`, `qa clear`; по необходимости сбросьте набор.
  Для проверки логики медленного клиента сохраняйте и результат генератора,
  и код закрытия. Отсутствие 1013 нельзя считать прохождением кейса.

Для отчёта T50 сохраните URL, SHA фронта и бэкенда, ID кейса, действие,
результат, тестовые идентификаторы и наблюдаемое состояние. Секреты,
cookies и токены в отчёт не включайте. Если для варианта отсутствуют
требуемые условия или спецификация, зафиксируйте `Blocked` с причиной.
У шага 5 `REC-03` есть отдельное условие согласования критерия
окончательного failed в [описании кейса](../../docs/qa/test-cases/proposed-tests.md).
