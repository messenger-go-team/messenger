# Работа над проектом

Требования и Definition of Done основаны на [SPEC](docs/SPEC.md), разделы 8–10.
Задачи ведём в [GitHub Issues](https://github.com/messenger-go-team/messenger/issues).

## Задачи и ветки

- Одна задача — одна рабочая ветка и один PR в `main`.
- Перед началом назначьте исполнителя и проверьте зависимости задачи.
- Если задача занимает больше дня, разбейте её на несколько задач.
- Название ветки включает тип работы, номер задачи и краткое описание:
  `feat/27-auth`, `fix/35-message-ack`, `docs/3-contributing`.
  Для изменений, подготовленных Codex, используется префикс `codex/`.
- Прямой push в `main`, force push и удаление `main` запрещены.

Начинайте работу от актуальной `main`:

```bash
git switch main
git pull --ff-only
git switch -c feat/27-auth
```

Общий шаблон задачи находится в `.github/ISSUE_TEMPLATE/task.yml`.
Шаблоны баг-репорта и тест-кейса относятся к задаче QA
[T22](https://github.com/messenger-go-team/messenger/issues/22).

## Коммиты и pull request

Используйте Conventional Commits: `тип: краткое описание`.
Основные типы: `feat`, `fix`, `docs`, `refactor`, `test`, `ci`, `chore`, `build`.
При необходимости добавьте область: `feat(auth): добавить ротацию refresh-токенов`.

Заголовок PR также следует этому формату: он становится заголовком
итогового squash-коммита. Описание должно объяснять результат и способ проверки.
Свяжите PR с задачей через `Closes #N`, например `Closes #27`.
Так задача закроется при merge PR в `main`.

До готовности используйте Draft PR. Когда изменение готово, переведите PR
в обычный и запросите ревью у участника с правом записи в репозиторий.
Для merge нужны:

- минимум один approval другого участника; если для изменённых файлов определён
  CODEOWNERS, это одобрение должен дать соответствующий владелец кода;
- успешные **Go lint** и **Go test**;
- актуальность ветки относительно `main` и отсутствие конфликтов;
- закрытые обсуждения в ревью.

Одобрение владельца кода, который не является автором PR, одновременно
выполняет требование независимого ревью. Отдельный второй approval ради этого
не требуется. Если PR затрагивает несколько областей, одобрения должны
покрывать владельцев всех изменённых файлов. Один общий владелец может
проверить весь PR.

Новые изменения, требующие ревью, сбрасывают прежние approvals.
После исправлений дождитесь CI и повторного одобрения.
Правила действуют и для администраторов; список обхода правил пуст.

Merge выполняется только через **Squash and merge**.
В `main` попадает один итоговый коммит на PR, рабочая ветка удаляется автоматически.

## Владение кодом и контракты

Состав команды и распределение ревью описаны в [docs/team.md](docs/team.md).
В `.github/CODEOWNERS` заданы профильные владельцы фронтенда, QA, дизайна
и контрактов. Общие владельцы `@afilistovich` и `@kakocuk1` сохранены
для всего репозитория и повторены в правилах отдельных каталогов.

Более конкретное последнее правило CODEOWNERS заменяет предыдущее.
Поэтому общие владельцы явно указаны в каждой области: автор PR сможет
получить независимое ревью, даже если он единственный профильный специалист.

Для изменений контрактов в `/api` дополнительно нужны согласования
фронтенда и владельца сервиса по SPEC §8. Проверьте, что оба направления
представлены в Reviewers, и при необходимости добавьте ревьюеров вручную.
CODEOWNERS с несколькими владельцами требует approval любого одного из них
и не обеспечивает оба согласования автоматически.

## Проверки

Команды локального запуска и устройство CI описаны в [docs/ci.md](docs/ci.md).
Тесты пишем вместе с поведением, которое они проверяют.
Для документационных изменений укажите, какие ссылки и примеры проверены;
автоматические тесты приложения для них могут не требоваться.

## Definition of Done

- Критерии приёмки задачи выполнены.
- Код и необходимые тесты добавлены; проверки CI проходят.
- Контракты и документация соответствуют изменению.
- Получено необходимое ревью, замечания устранены.
- Если меняется поведение приложения, QA проверил его на staging.
- PR с привязкой к задаче смержен в `main` через squash.

Для изменений без исполняемого кода объясните в PR, почему тесты приложения
или staging не применимы. Дополнительные командные договорённости фиксируйте
в этом документе через PR.

## Настройки репозитория

Защита описана в `.github/main-ruleset.json`, параметры merge —
в `.github/repository-settings.json`. Применение и проверка настроек
описаны в [docs/repository-rules.md](docs/repository-rules.md).
Изменение этих файлов само по себе не обновляет настройки GitHub.
