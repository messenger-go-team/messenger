# Контракт WebSocket v1

Статус: проект T09 для согласования фронтендом и владельцем chat-сервиса.
Документ задаёт поведение будущей реализации, а не описывает работающий API.
Источник: [T09](https://github.com/messenger-go-team/messenger/issues/9),
[SPEC](../../docs/SPEC.md) FR-CHAT-2..7, FR-CHAT-9..10, FR-WEB-3..5, §6-8.

## 1. Этапы и направления

C -> S означает клиент -> chat, S -> C означает chat -> клиент.

| Событие | Направление | Этап | Назначение |
| --- | --- | --- | --- |
| `message.send` | C -> S | MVP | Сохранить текст |
| `message.ack` | S -> C | MVP | Подтвердить сохранение |
| `message.new` | S -> C | MVP | Передать сохранённое сообщение участникам |
| `error` | S -> C | MVP | Ошибка команды |
| `message.delivered` | C -> S, S -> C | 2 | Продвинуть курсор доставки участника |
| `message.read` | C -> S, S -> C | 2 | Продвинуть курсор прочтения участника |
| `presence` | S -> C | 2 | Онлайн-состояние пользователя |
| `typing` | C -> S, S -> C | 2 | Временный индикатор набора |

В MVP команды этапа 2 получают `unsupported_type`. Клиент не отправляет их
до включения этого этапа согласованной версией приложения. Группы, вложения,
изменение и удаление сообщений вне v1. Права и рассылка уже в MVP определяются
через `chat_members`, без отдельной схемы «отправитель-получатель».

## 2. Подключение и JWT

Внешний адрес: `wss://<домен>/ws`. Локально допустим
`ws://localhost:<порт>/ws`. Домен и порт задаются окружением.
Nginx передаёт запрос chat-сервису с поддержкой Upgrade.

Браузер передаёт access JWT через `Sec-WebSocket-Protocol`:

```javascript
const socket = new WebSocket(`${wsOrigin}/ws`, [
  "messenger.v1",
  `bearer.${accessToken}`,
]);
```

- В запросе обязательны `messenger.v1` и ровно один элемент `bearer.<access JWT>`.
  Префикс `bearer.` - соглашение проекта для credentials в handshake,
  а не стандартная схема HTTP Bearer и не второй выбранный протокол.
- Сервер проверяет JWT **до HTTP 101**: только HS256, подпись, `exp`, `iat`
  и `sub` (UUID). Общий пакет проверки и секрет не короче 32 байт соответствуют
  SPEC и auth-контракту T07.
- В HTTP 101 сервер выбирает **только** `Sec-WebSocket-Protocol: messenger.v1`.
  JWT не отражается в ответе; `socket.protocol` равен `messenger.v1`.
- JWT и весь заголовок с credentials исключаются из логов Nginx/chat,
  трассировок и отчётов об ошибках. Токены не передаются в URL или событиях.
  Refresh-токен используется только в REST auth.
- `Origin` проверяется по точному allowlist окружения (схема, хост, порт).
  Неизвестный, отсутствующий и `null` Origin дают 403. Тестовые небраузерные
  клиенты также передают разрешённый Origin.
- Авторизация соединения ограничена `exp`: по истечении сервер закрывает
  его с 4401, новые команды не принимает. Начатая транзакция может завершиться,
  поэтому потеря ack обрабатывается обычным повтором.
- Клиент обновляет токены через REST auth и создаёт новый сокет. Обновления JWT
  внутри соединения нет. Refresh между вкладками координируется клиентом,
  чтобы один ротируемый токен не использовался конкурентно.
- При logout клиент закрывает свои соединения и отзывает refresh через auth.
  Немедленный серверный отзыв выданного access JWT в MVP не обещается.

### Ошибки до Upgrade

| HTTP | code | Причина |
| --- | --- | --- |
| 400 | `invalid_handshake` | Нет messenger.v1 или некорректен Upgrade |
| 401 | `unauthorized` | Нет одного корректного JWT, истёк или невалиден |
| 403 | `origin_not_allowed` | Origin не разрешён |
| 429 | `rate_limited` | Лимит новых подключений на границе, когда включён |
| 503 | `service_unavailable` | Сервис не готов или останавливается |

Chat возвращает JSON `{ code, message }`, для 401 также
`WWW-Authenticate: Bearer`. Nginx может вернуть собственное тело.
Браузерный WebSocket API не предоставляет HTTP-статус и тело неуспешного
handshake: интерфейс не строит логику на чтении этого JSON. При ошибке
подключения клиент сверяет срок access, при необходимости делает один refresh
и повторяет подключение с backoff, без бесконечного цикла refresh.

## 3. Конверт, формат и ограничения

Один WebSocket **message** - один JSON-объект UTF-8 в text. Фрагментация frames
допустима; лимит применяется после сборки. Binary, массивы и несколько JSON
подряд не поддерживаются.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `type` | string | Имя события из раздела 1 |
| `id` | UUID string | ID команды/события, правила ниже |
| `ts` | RFC 3339 UTC string | Время конверта, например 2026-11-08T12:00:00Z |
| `payload` | object | Поля события |

Все четыре поля обязательны.

- Клиент создаёт новый `id` каждой попытке команды, в том числе повторной.
  Ack и ошибка разобранной команды копируют её `id` для корреляции.
- Для new, presence, typing и рассылки статусов сервер создаёт свой `id`.
  Он не является ID сообщения в БД; повтор рассылки допустим.
- Если входной `id` невалиден/отсутствует, `error.id` - новый серверный UUID;
  корреляция по id тогда невозможна.
- Клиентский `ts` не определяет порядок, права, TTL и время сохранения.
  Сервер ставит своё время конверта; сохранённое время - `payload.created_at`.
- ID доменных объектов и `client_msg_id` - UUID string. Клиент генерирует UUID v4.
- `seq` - целое JSON number: 1..9007199254740991 для сообщения, 0 допустим
  для пустого курсора. Это безопасный диапазон JavaScript. Выход за него требует
  новой версии контракта; округлённые значения не выдаются.
- Поля payload ниже обязательны, если явно не помечены иначе. Неизвестные поля
  C -> S конверта/payload дают `invalid_payload`. Клиент игнорирует
  дополнительные поля и неизвестные типы S -> C без разрыва соединения.
  Несовместимые изменения требуют новой версии протокола.
- Текст: 1..4096 Unicode code points, не байт и не UTF-16 code units.
  Строка только из Unicode White_Space запрещена. Chat отклоняет U+0000 после
  декодирования JSON с `invalid_payload` и `retryable: false` до вызова History.
  PostgreSQL `text` не хранит этот символ. Буквальная последовательность из
  обратной косой черты и `u0000` допустима. Пробелы, переводы строк и исходная
  Unicode-последовательность сохраняются, trim и Unicode-нормализации нет.
  Plain text отображается без HTML-интерпретации.
- Максимум входного JSON-message - **64 KiB (65536 байт)**, включая конверт
  и JSON escaping. Это отдельный лимит от длины body. События S -> C также
  укладываются в 64 KiB. Compression в v1 не используется.

## 4. message.send - отправить текст

C -> S, MVP. Payload:

| Поле | Тип | Значение |
| --- | --- | --- |
| `chat_id` | UUID | Чат, уже созданный через history REST |
| `client_msg_id` | UUID | Постоянный ID логического сообщения при всех повторах |
| `body` | string | Текст по ограничениям раздела 3 |

```json
{
  "type": "message.send",
  "id": "10000000-0000-4000-8000-000000000001",
  "ts": "2026-11-08T12:00:00Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "client_msg_id": "30000000-0000-4000-8000-000000000001",
    "body": "Привет!"
  }
}
```

`sender_id` берётся только из JWT, участники - из history. Клиент не задаёт
автора, участников, серверный ID, seq и created_at. Участие проверяется
на каждую команду, в том числе повторную.

## 5. message.ack - подтверждение сохранения

S -> C, MVP, только в соединение, отправившее команду. Payload:

| Поле | Тип | Значение |
| --- | --- | --- |
| `chat_id` | UUID | Чат |
| `client_msg_id` | UUID | ID из команды |
| `message_id` | UUID | Сохранённый messages.id |
| `seq` | integer | Номер внутри чата |
| `created_at` | timestamp | Время первого сохранения, присвоенное history |

```json
{
  "type": "message.ack",
  "id": "10000000-0000-4000-8000-000000000001",
  "ts": "2026-11-08T12:00:00.100Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "client_msg_id": "30000000-0000-4000-8000-000000000001",
    "message_id": "40000000-0000-4000-8000-000000000001",
    "seq": 42,
    "created_at": "2026-11-08T12:00:00.090Z"
  }
}
```

Ack отправляется **после commit в PostgreSQL через history**, не после записи
в память/Redis или начала gRPC. Он означает `sent` в UI, не delivered/read.
Повтор возвращает те же пять полей payload; id и ts конверта относятся
к текущей попытке.

## 6. message.new - сообщение участникам

S -> C, MVP. После сохранения рассылается во все активные соединения всех
участников, включая отправителя и его другие вкладки. Отправляющая вкладка
может получить и ack, и new. Их относительный порядок не гарантируется.

Payload: все пять полей ack плюс `sender_id: UUID` (автор из JWT)
и `body: string` (сохранённый текст).

```json
{
  "type": "message.new",
  "id": "50000000-0000-4000-8000-000000000001",
  "ts": "2026-11-08T12:00:00.110Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "client_msg_id": "30000000-0000-4000-8000-000000000001",
    "message_id": "40000000-0000-4000-8000-000000000001",
    "sender_id": "60000000-0000-4000-8000-000000000001",
    "seq": 42,
    "body": "Привет!",
    "created_at": "2026-11-08T12:00:00.090Z"
  }
}
```

Рассылка не является постоянной очередью. Офлайн-клиент читает history.
В MVP Broker работает в памяти (T34), Redis pub/sub подключается позднее;
внешний контракт при этой замене не меняется.

## 7. Идемпотентность, порядок и повторы

Ключ: `(chat_id, sender_id, client_msg_id)` в history. Одинаковый ключ и body,
в том числе при конкурентных запросах, создают одну запись, один seq и
возвращают исходный payload ack. Дедупликация действует весь срок хранения
сообщения, не TTL сокета/Redis. Другой чат или пользователь не делит этот ключ.
Тот же ключ с другим body даёт `idempotency_conflict`, не изменяя запись.

Клиент сохраняет pending с chat_id, client_msg_id и точным body до отправки.
При таймауте ack (начальное значение 10 с), разрыве или `retryable: true`
повторяет прежние данные с **новым id конверта и прежним client_msg_id**,
с backoff и без параллельных повторов одного сообщения. Метка failed не
доказывает отсутствие записи на сервере. Кнопка повтора сохраняет client_msg_id.
Изменение текста - новое сообщение с новым client_msg_id.

При повторе сервер не обязан повторять new, но дубли рассылки допустимы.
Потеря рассылки после commit восстанавливается через history: ack не обещает
атомарность PostgreSQL и Broker.

Seq назначает history монотонно внутри чата; между чатами номера не сравнивают.
Клиент сортирует по seq, объединяет ack/new/history по message_id или
`(chat_id, seq)`; собственный pending - по
`(chat_id, sender_id, client_msg_id)`. Ts и порядок прихода не заменяют seq.

## 8. Переподключение и history

1. Переподключиться с действующим JWT. Начальная задержка 1 с, затем 2, 4, 8,
   16, максимум 30 с, jitter +/-20%. После стабильной работы 30 с сбросить
   задержку. После logout reconnect выключен.
2. После открытия сокета буферизовать new и запросить актуальный список чатов
   из history, включая чаты, неизвестные до разрыва.
3. Для каждого чата запросить `after_seq=<последний синхронизированный seq>`,
   `limit=100`; для нового чата курсор 0. Страницы читать по возрастанию seq
   до исчерпания, двигая курсор по history, затем объединить с буфером.
4. После успешной догрузки сохранить синхронизированный курсор. Повторить
   pending без ack с прежними client_msg_id: они могли сохраниться до разрыва.

Синхронизированный курсор - граница уже прочитанного из history диапазона,
не `max(seq)` любого new или своего ack. New с seq=44 не позволяет перескочить
ещё не загруженное seq=43. SPEC не обещает отсутствие числовых пропусков:
завершённость догрузки определяется ответом history, не ожиданием каждого числа.
При сомнении клиент читает history от безопасного курсора.

Синхронизация также выполняется после возврата вкладки на передний план и
периодически (начальное значение 30 с для активной вкладки). Это восстанавливает
потерю pub/sub без разрыва сокета. Недоступность history не позволяет продвинуть
курсор. Офлайн-очереди и replay по id конверта нет.

URL, форма страниц и список чатов принадлежат T08, SaveMessage и признак
первого сохранения - T10. При их подготовке согласовать доменные поля и
семантику after_seq; этот документ не вводит второй REST API.

## 9. error - ошибка команды

S -> C. Id копируется из разобранной команды. Payload:

| Поле | Тип | Значение |
| --- | --- | --- |
| `code` | string | Машинный код из таблицы |
| `message` | string | Краткое описание, не стабильный API |
| `retryable` | boolean | Допустим повтор с backoff |
| `request_type` | string или null | Тип исходной команды, null если неизвестен |
| `client_msg_id` | UUID или null | Валидный ID message.send, иначе null |

```json
{
  "type": "error",
  "id": "10000000-0000-4000-8000-000000000001",
  "ts": "2026-11-08T12:00:00.050Z",
  "payload": {
    "code": "forbidden",
    "message": "Нет доступа к чату.",
    "retryable": false,
    "request_type": "message.send",
    "client_msg_id": "30000000-0000-4000-8000-000000000001"
  }
}
```

| code | retryable | Причина |
| --- | --- | --- |
| `invalid_json` | false | Текст не разбирается как один JSON-объект |
| `invalid_payload` | false | Поля, UUID, timestamp или текст нарушают ограничения payload |
| `unsupported_type` | false | Неизвестный тип, неверное направление или этап не включён |
| `forbidden` | false | Не участник либо чат недоступен; существование не раскрывается |
| `idempotency_conflict` | false | Повтор ключа с другим body |
| `invalid_seq` | false | Курсор вне 0..last_seq чата |
| `rate_limited` | true | При включённом лимите команд; повтор с задержкой |
| `temporarily_unavailable` | true | Зависимость недоступна или исход сохранения неизвестен |
| `internal_error` | true | Неожиданная ошибка; повтор безопасен с прежним ключом |

False запрещает автоматический повтор без исправления причины, не требует
закрывать сокет. При неизвестном исходе сервер не утверждает, что сообщение
не сохранено. Ошибка рассылки после успешного commit не отменяет ack.
Ошибки не содержат SQL, stack trace, JWT, секреты и чужие данные. Для неверного
JSON request_type и client_msg_id равны null. Размер и повреждённый UTF-8
обрабатываются закрытием, не гарантией error.

## 10. Доставка и прочтение - этап 2

В личном чате хранятся курсоры **участника**, общие для его устройств:
last_delivered_seq и last_read_seq. Статус покрывает сообщения с seq <= курсора;
собственные сообщения не считаются подтверждением от собеседника.

C -> S: оба события содержат `chat_id: UUID` и `seq: integer` (0..last_seq).
Пользователь определяется из JWT, user_id от клиента запрещён. Клиент
подтверждает только действительно полученный диапазон. Read отправляет
после показа сообщений в активном окне, не по одному факту получения new.

```json
{
  "type": "message.delivered",
  "id": "10000000-0000-4000-8000-000000000002",
  "ts": "2026-11-08T12:00:01Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "seq": 42
  }
}
```

```json
{
  "type": "message.read",
  "id": "10000000-0000-4000-8000-000000000003",
  "ts": "2026-11-08T12:00:03Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "seq": 42
  }
}
```

History сохраняет `max(старый, новый)` после проверки участия и диапазона.
Read продвигает и delivered минимум до этого seq. Delivered означает приём
клиентским приложением, не успешную запись сервера в сокет.
После сохранения chat рассылает всем соединениям всех участников, включая
инициатора, текущее значение соответствующего курсора:

```json
{
  "type": "message.delivered",
  "id": "50000000-0000-4000-8000-000000000002",
  "ts": "2026-11-08T12:00:01.100Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "user_id": "60000000-0000-4000-8000-000000000002",
    "seq": 42
  }
}
```

```json
{
  "type": "message.read",
  "id": "50000000-0000-4000-8000-000000000003",
  "ts": "2026-11-08T12:00:03.100Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "user_id": "60000000-0000-4000-8000-000000000002",
    "seq": 42
  }
}
```

Если read поднял delivered, рассылаются оба события. Повтор/меньший seq
не понижает состояние и возвращает рассылкой актуальный курсор. Отдельного ack
нет. Получатель применяет max даже при перестановке событий. После reconnect
курсоры восстанавливаются из history; включение этапа 2 требует расширения
T08/T10 для чтения/сохранения этих данных. Группы вне v1.

## 11. presence - этап 2

Только S -> C. Payload: `user_id: UUID`, `status: "online" | "offline"`,
`last_seen_at: timestamp | null`. Для online last_seen_at=null; для offline -
время последнего серверного подтверждения активности, оценка с учётом heartbeat/TTL.

```json
{
  "type": "presence",
  "id": "50000000-0000-4000-8000-000000000004",
  "ts": "2026-11-08T12:01:00Z",
  "payload": {
    "user_id": "60000000-0000-4000-8000-000000000002",
    "status": "offline",
    "last_seen_at": "2026-11-08T12:00:15Z"
  }
}
```

Online - есть хотя бы одно живое авторизованное соединение, offline - ни одного.
Закрытие одной из двух вкладок не переводит пользователя в offline.
Состояние доступно только участникам общих личных чатов, с проверкой прав
при рассылке; подписок на произвольный user_id нет.

При подключении сервер отправляет снимки состояния собеседников, затем
изменения. Новый личный чат добавляет наблюдение и снимок, потеря прав прекращает
наблюдение. Неизвестное состояние клиент показывает как unknown, не offline.
Presence временный, не определяет сохранение/доставку. На этапе 2 достаточно
одного chat; Redis TTL и объединение между инстансами добавляются позднее.

## 12. typing - этап 2

C -> S: `chat_id: UUID`, `is_typing: boolean`. Автор берётся из JWT.

```json
{
  "type": "typing",
  "id": "10000000-0000-4000-8000-000000000004",
  "ts": "2026-11-08T12:02:00Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "is_typing": true
  }
}
```

S -> C остальным участникам: `chat_id: UUID`, `user_id: UUID`,
`is_typing: boolean`, `expires_at: timestamp`.

```json
{
  "type": "typing",
  "id": "50000000-0000-4000-8000-000000000005",
  "ts": "2026-11-08T12:02:00.100Z",
  "payload": {
    "chat_id": "20000000-0000-4000-8000-000000000001",
    "user_id": "60000000-0000-4000-8000-000000000001",
    "is_typing": true,
    "expires_at": "2026-11-08T12:02:05.100Z"
  }
}
```

Сервер проверяет участие. Клиент посылает true не чаще раза в 2 с, false -
при остановке, отправке и уходе из чата. TTL true - 5 с от приёма сервером;
для false expires_at равно серверному ts и индикатор убирается сразу.

Несколько вкладок объединяются по (chat_id, user_id): false/закрытие одной
убирает только её сигнал. Общий false - когда живых сигналов не осталось,
общий expires_at для true - максимальный срок живых сигналов.
Клиент ограничивает показ 5 с после приёма, не полагаясь только на часы.
По серверному ts игнорирует более старый сигнал этой пары.
Typing не сохраняется в history, не повторяется после reconnect, не имеет ack;
потеря false устраняется TTL.

## 13. Heartbeat, таймауты и закрытие

Ping/Pong - управляющие frames RFC 6455, не JSON. Сервер посылает Ping каждые
25 с, ждёт соответствующий Pong максимум 10 с. Браузер отвечает на уровне
протокола, JavaScript не посылает JSON pong. Начальный write timeout - 10 с.
Очередь записи ограничена; медленный клиент с переполненной очередью
отключается с 1013 и восстанавливается через history.
Nginx proxy_read_timeout больше цикла heartbeat с запасом, начально 75 с (T36).

| Close code | Значение и действие клиента |
| --- | --- |
| 1000 | Нормальное закрытие; после собственного logout reconnect выключен |
| 1001 | Остановка сервера; reconnect с backoff, затем history |
| 1002 | Ошибка WebSocket-протокола; исправить клиент |
| 1003 | Binary не поддерживается; исправить клиент |
| 1007 | Невалидный UTF-8; исправить клиент |
| 1009 | Более 64 KiB; уменьшить message, автоматически его не повторять |
| 1011 | Серверная ошибка; reconnect с backoff |
| 1013 | Временная перегрузка/медленный клиент; reconnect с backoff |
| 4401 | Код проекта: JWT истёк; refresh через REST и reconnect |

При пропаже Pong транспорт разрывается, доставка Close не гарантирована.
1006 может наблюдаться при потере сети, но **не отправляется** в Close.
Причина Close - диагностика без токенов/внутренних ошибок, логика основана
на коде. Graceful shutdown прекращает новые Upgrade и закрывает соединения,
не отменяя сохранённые сообщения.

## 14. Приёмочные сценарии и согласование

Для мок-сервера T20, реализации T33-T35 и QA:

- Handshake выбирает messenger.v1; неверный JWT даёт 401 до 101, чужой Origin -
  403; истечение JWT закрывает соединение с 4401.
- A пишет B: ack после сохранения, все вкладки участников получают new
  с одинаковыми message_id/seq/created_at.
- Потеря ack и конкурентный повтор дают одну запись и исходный payload ack.
  Другой body с тем же ключом - idempotency_conflict; чужой чат - forbidden.
- Пустой/пробельный body и 4097 code points запрещены; 4096 допустимы в пределах
  64 KiB. Проверить кириллицу, emoji, комбинируемые символы и JSON escaping.
- `"body":"a\u0000b"` даёт `invalid_payload` с `retryable: false`. Запись
  не создаётся, `last_seq` не меняется, ack и new не отправляются. Сокет
  принимает следующую валидную команду. `"body":"a\\u0000b"` с буквальной
  обратной косой чертой сохраняется как введено.
- Ошибка JSON, направления или типа не мешает следующей валидной команде;
  binary/превышение размера закрывают сокет.
- Reconnect догружает несколько страниц и новый чат, объединяет буфер/history
  без дублей и перескока курсора. Потеря рассылки при живом сокете также устраняется.
- Этап 2: курсоры не уменьшаются, read продвигает delivered, будущий/чужой seq
  запрещён. Вторая вкладка не сбрасывает presence/typing.
- Нет Pong, медленный читатель и остановка освобождают соединение;
  подключение через Nginx держится дольше минуты.

На ревью подтвердить JWT, поля событий, несколько вкладок и совместимость
с T08/T10. Эти примеры не заменяют approval и проверку реализации.
