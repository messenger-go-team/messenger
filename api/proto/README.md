# Внутренний gRPC-контракт history v1

Проект [T10 / #10](https://github.com/messenger-go-team/messenger/issues/10)
для согласования обоими бэкендерами и фронтендом по SPEC §8.
Это контракт будущей реализации, а не работающий history-сервис.
Нормативные источники: [SPEC](../../docs/SPEC.md),
[WebSocket v1](../ws/events.md), [history.proto](history.proto),
[схема PostgreSQL](../../docs/db/schema.md#historymessages).

## Граница доверия и форматы

`messenger.history.v1.HistoryService` вызывается только chat-сервисом внутри
сервисной сети. Порт не публикуется в Nginx или наружу. Chat проверяет access JWT
и берёт sender_id/requester_id/user_id только из его sub. Идентификатор пользователя
из WS payload не принимается. History доверяет этой идентичности только от chat;
сетевой доступ к RPC должен быть ограничен при развёртывании. Выбор service credentials
или mTLS - отдельная задача развёртывания, этим контрактом не реализован.

Все UUID обязательны, ненулевые; строковое представление - канонические
36 символов с дефисами в нижнем регистре. client_msg_id - UUID v4.
UUID в других полях не ограничены версией. Chat приводит UUID из JWT/WS
к каноническому виду перед RPC; это не преобразование body. History валидирует запросы сам:
proto3 не обеспечивает required, ограничения длины или авторизацию.
Пустые значения по умолчанию не считаются корректными UUID.

body - валидный UTF-8, 1..4096 Unicode code points, не только Unicode White_Space.
PostgreSQL `text` не хранит U+0000. Chat проверяет декодированный `body` до RPC
и отвечает `invalid_payload` с `retryable: false`. History проверяет `body`
самостоятельно и отклоняет U+0000 с `INVALID_ARGUMENT` до записи.
Пробелы, переводы строк и исходная Unicode-последовательность сохраняются точно.
Буквальный текст `\u0000` допустим, если после декодирования это шесть
печатных символов, включая обратную косую черту.
Лимит WS 64 KiB относится к JSON-конверту и проверяется chat отдельно.
seq - int64 в protobuf, но допустим только диапазон 1..9007199254740991,
чтобы WS/REST могли представить его точно как JSON number. Переполнение
не приводит к округлению/обнулению или записи нового сообщения.
created_at - обязательный валидный google.protobuf.Timestamp первого сохранения
по серверным часам history; наружу chat переводит его в RFC 3339 UTC.
Не использовать ProtoJSON напрямую как WS payload: int64 в ProtoJSON - строка.

## SaveMessage

Вход: chat_id, sender_id, client_msg_id, body.
Выход: message_id, seq, created_at, duplicate.

1. History валидирует запрос и проверяет существование чата и актуальное участие
   sender_id. Проверка обязательна при каждом вызове, включая повторный.
2. Проверка прав, выделение seq и вставка согласованы в одной транзакции PostgreSQL.
   Предварительный CheckMembership не заменяет эту проверку.
3. Уникальны (chat_id, seq) и (chat_id, sender_id, client_msg_id).
   Один ключ с тем же точным body, включая конкурентные вызовы, создаёт одну запись.
   Первый сохранённый вызов получает duplicate=false, повтор - true и те же
   message_id, seq и created_at. Повтор не увеличивает last_seq.
4. Тот же ключ с другим body возвращает ALREADY_EXISTS без изменения записи.
   Ключ действует весь срок хранения сообщения, без Redis TTL.
5. OK возвращается только после успешного commit. Chat строит ack из ответа
   и исходных chat_id/client_msg_id, рассылает new участникам. Body и sender_id
   берутся из запроса, поскольку сохранение не преобразует текст.

`seq` монотонно возрастает и уникален внутри чата. При реализации [T29](https://github.com/messenger-go-team/messenger/issues/29)
каждое новое сообщение увеличивает `last_seq` на единицу в транзакции вставки.
Повтор, конфликт текста и откат транзакции не продвигают `last_seq`.
При конкурентном сохранении N новых сообщений в одном чате с исходным
`last_seq=L` N успешных транзакций дают последовательные номера от L+1 до L+N.
Потребители контракта используют монотонность и уникальность `seq` без
предположения о непрерывности номеров. Завершение догрузки REST-истории
определяется по `has_more_after`; для следующей страницы используется
`next_after_seq`.

Повторная проверка прав может запретить доступ к ранее записанному сообщению.
Членство и счётчик должны быть защищены от конкурентного изменения при реализации
транзакции; отдельный SELECT до неё недостаточен.

При duplicate=true chat отправляет ack, но не обязан повторять new.
Дубли new разрешены WS-контрактом. Commit и рассылка не атомарны; потерянная
рассылка восстанавливается чтением REST history. Ошибка последующего
GetChatMembers не отменяет commit и не должна превращать успешный ack в отказ.

## Участники и членство

`GetChatMembers(chat_id, requester_id)` проверяет участие requester_id, возвращает
уникальные актуальные user_ids из chat_members, включая requester_id.
Порядок - по канонической UUID-строке по возрастанию. В MVP у личного чата
два участника. Usernames, контакты, presence и статусы доставки сюда не входят.
Без участия - PERMISSION_DENIED, отсутствующий чат - NOT_FOUND.
Chat использует список для рассылки во все соединения участников.

`CheckMembership(chat_id, user_id)` возвращает OK + is_member=true/false
для существующего чата. false - нормальный отрицательный результат, а не ошибка.
Отсутствующий чат - NOT_FOUND. Сбой БД нельзя подменять false.
Это проверка текущего пользователя chat для typing и других команд;
не внешний endpoint для проверки произвольных пользователей.
Оба метода возвращают снимок на момент чтения; кэш не даёт бессрочных прав.
Изменение состава групп и атомарная рассылка при таком изменении вне MVP.

## Ошибки и повторы

Возвращается стандартный gRPC status; код - машинный контракт.
Текст status.message - диагностика, не парсится клиентом, не содержит SQL,
stack trace, body, JWT, секреты или чужие данные. При ошибке response отсутствует.
Дополнительные status details в v1 не требуются.

| gRPC code | Когда | Действие chat / WS |
| --- | --- | --- |
| INVALID_ARGUMENT | Невалидный UUID, body или обязательное поле | invalid_payload, retryable=false |
| NOT_FOUND | Чата нет, все методы | forbidden, false; не раскрывать существование чата |
| PERMISSION_DENIED | Sender/requester не участник, SaveMessage/GetChatMembers | forbidden, false |
| ALREADY_EXISTS | SaveMessage: ключ уже записан с другим body | idempotency_conflict, false |
| RESOURCE_EXHAUSTED | Временный лимит нагрузки | rate_limited, true с backoff |
| OUT_OF_RANGE | SaveMessage: следующий seq превысит безопасный диапазон | internal_error, true; сигнал оператору, ограниченный backoff |
| UNAVAILABLE | БД/сервис временно недоступны | temporarily_unavailable, true |
| DEADLINE_EXCEEDED | Истёк deadline, исход сохранения может быть неизвестен | temporarily_unavailable, true |
| CANCELLED | Отменён context вызывающей стороны | Не отправлять в закрытый сокет; исход может быть неизвестен |
| INTERNAL / UNKNOWN / DATA_LOSS | Неожиданная ошибка | internal_error, true; диагностика на сервере |
| UNIMPLEMENTED | Версии сервисов несовместимы | internal_error, true; исправить deployment, без горячего цикла |
| UNAUTHENTICATED | Отказ service-аутентификации, если она включена | internal_error, true; не запускать refresh пользовательского JWT |

Если CheckMembership вернул false, chat отвечает forbidden без повторов.
Коды выше задают поведение будущего сервиса; транспорт также может вернуть ошибку.
Неизвестные коды обрабатываются как internal_error с ограничением частоты повторов.

Каждый RPC вызывается с deadline; стартовое значение 3 с, настраивается окружением.
Таймаут, отмена и разрыв не доказывают отсутствие commit. SaveMessage повторяют
только с прежними chat_id, sender_id, client_msg_id и точным body; новый ключ
приведёт к новому сообщению. Повторы последовательные, с backoff и jitter,
без немедленного бесконечного цикла и без установленного лимита «три попытки».
Читающие RPC можно безопасно повторять, но повтор может вернуть новый снимок.

## Генерация и проверки

Из корня репозитория на Linux/WSL с Go из go.mod и GNU Make:

```bash
make proto
make test
make lint
```

make proto устанавливает Buf v1.72.0, protoc-gen-go v1.36.12 и
protoc-gen-go-grpc v1.6.2 в игнорируемый bin/proto, проверяет формат и lint,
затем генерирует api/gen/history/v1/history.pb.go и history_grpc.pb.go.
Системный protoc и аккаунт Buf не нужны: плагины локальные.
Первому запуску нужен доступ к Go module proxy; следующие используют Go cache.
Версии фиксированы в Makefile; runtime-зависимости - в go.mod/go.sum.
Инструменты не добавляются как runtime-зависимости приложения.

Сгенерированные файлы коммитятся и вручную не редактируются.
После изменения .proto форматировать `bin/proto/buf format -w`, затем make proto.
CI повторяет генерацию и проверяет отсутствие diff. Для проверки совместимости
будущих изменений: `bin/proto/buf breaking --against '.git#branch=origin/main'`
после появления первого контракта в main. Номера удалённых полей резервировать,
не переиспользовать; несовместимый API выпускать новым package v2.

## Приёмка будущей реализации

- Первая запись, одинаковый последовательный/конкурентный повтор и конфликт body.
- Один результат после commit с потерянным ответом и повтора по прежнему ключу.
- Один client_msg_id у разных sender/chat не объединяет сообщения.
- Не участник и отсутствующий чат; повтор после отзыва членства запрещён.
- CheckMembership=false отличается от ошибки БД; чужой список участников недоступен.
- 4096/4097 code points, emoji, White_Space, сохранение перевода строк без trim.
- Запрос WS с JSON-полем `"body":"a\u0000b"` даёт `invalid_payload` с
  `retryable: false`. Прямой `SaveMessage` с U+0000 даёт `INVALID_ARGUMENT`.
  В обоих случаях запись и `last_seq` не меняются. Chat не отправляет
  `message.ack` и `message.new`, соединение остаётся пригодным для следующей
  валидной команды. Строка с буквальной последовательностью `\u0000` сохраняется
  без изменений.
- Граница seq, валидный Timestamp, восстановление после потери рассылки.

## Согласование с REST history

В [OpenAPI history](../openapi/history.yaml), принятом в #8, поле `Message.id`
содержит тот же серверный UUID, что и `message_id` в ответе SaveMessage и
событиях WebSocket. `seq` и `created_at` относятся к той же сохранённой записи.
При догрузке клиент передаёт `after_seq` и объединяет REST-историю с событиями
по серверному ID или паре `(chat_id, seq)`.

REST не возвращает `client_msg_id`. После догрузки и обработки буфера WS клиент
повторяет `message.send` для pending, для которых допустим автоповтор и
ещё нет подтверждения через `message.ack` или соответствующий собственный
`message.new`. В повторе
сохраняются `chat_id`, `client_msg_id` и точный `body`, используется новый
`id` WS-конверта. Если сообщение уже сохранено, SaveMessage возвращает
исходные `message_id`, `seq` и `created_at`. По `message_id` из ack
клиент объединяет pending с записью из REST, у которой совпадает `id`.

`POST /chats/{chat_id}/read` обрабатывает history по REST. Принадлежность к
контактам из auth не участвует в проверках: права определяет `chat_members`.
Транзакции, авторизацию и рассылку проверяют при реализации сервисов.

Основания инструментов: [Buf generation](https://buf.build/docs/configuration/v2/buf-gen-yaml/),
[gRPC Go](https://grpc.io/docs/languages/go/quickstart/),
[gRPC status codes](https://grpc.io/docs/guides/status-codes/).
