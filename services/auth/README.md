# Auth

Реализация [#27](https://github.com/messenger-go-team/messenger/issues/27):
регистрация, вход, ротация refresh и выход по
[OpenAPI](../../api/openapi/auth.yaml) и [SPEC](../../docs/SPEC.md).
Схема PostgreSQL используется из миграций #12 без изменений.
Auth подключается через `pgx/stdlib`: отмена context прерывает сетевые операции
и при полной недоступности PostgreSQL; миграции сохраняют свой существующий драйвер.

## Запуск

Из корня репозитория подготовьте `.env` по `.env.example`, задайте собственный
пароль PostgreSQL, затем:

```bash
docker compose up -d --wait postgres
make migrate-up MIGRATE_SERVICE=auth
make build SERVICE=auth
export JWT_SECRET="$(openssl rand -hex 32)"
export AUTH_INTERNAL_TOKEN="$(openssl rand -hex 32)"
export AUTH_DATABASE_URL='postgres://messenger:YOUR_LOCAL_PASSWORD@127.0.0.1:15432/messenger?sslmode=disable'
HTTP_ADDR=127.0.0.1:8081 ./bin/auth
```

Значение `JWT_SECRET` должно быть одним и тем же у auth/chat/history.
URL-кодируйте специальные символы username/пароля в URL подключения.
Auth читает только окружение процесса, `.env` автоматически не загружает.
Миграции применяются отдельно, при запуске Auth схему не изменяет.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `AUTH_DATABASE_URL` | нет | PostgreSQL URL/DSN; обязательна, содержит секрет |
| `JWT_SECRET` | нет | Общий HS256-секрет минимум 32 байта |
| `AUTH_INTERNAL_TOKEN` | нет | Отдельный служебный секрет, минимум 32 печатных ASCII-байта без пробелов, отличный от JWT_SECRET |
| `HTTP_ADDR` | `:8080` | Адрес HTTP listener |
| `SERVICE_NAME` | `auth` | Поле service JSON-логов |
| `LOG_LEVEL` | `INFO` | Уровень slog |
| `SHUTDOWN_TIMEOUT` | `10s` | Время завершения активных запросов |

TLS завершается на внешнем Nginx. Refresh cookie всегда `Secure`: браузерный
сценарий login/refresh/logout проверяйте через HTTPS, в том числе локально.
HTTP listener предназначен для внутренней сети или локальной диагностики.
Docker-образ подключается в #26, Nginx - в #36, автодеплой - в #37, staging - в #38.
В #36 внешний путь должен оставаться `/auth/...` по OpenAPI: cookie имеет
`Path=/auth` и не будет отправляться браузером на `/api/auth/...`. Если команда
выберет другой внешний префикс, сначала нужно отдельно согласовать изменение
OpenAPI и cookie Path; в этой реализации контракт сохранён.

## Поведение API

- `POST /auth/register`: 201 с `id`, исходным `username`, `created_at`,
  без автоматического входа и cookie; занятый username без учёта регистра - 409.
- `POST /auth/login`: 200 с `token_type: Bearer`, `access_token`, `expires_in: 900`;
  неизвестный username и неверный пароль дают одинаковый 401.
- `POST /auth/refresh`: refresh только из cookie; 200 с новым access и новым
  refresh cookie. Старый refresh отзывается в той же транзакции.
- `POST /auth/logout`: отзыв только предъявленной сессии, удаление cookie,
  пустой 204. Отсутствующий, истёкший и уже отозванный refresh дают 401,
  как определено текущим контрактом.

Эти четыре маршрута не требуют access JWT. Профиль, поиск и контакты требуют
пользовательский Bearer JWT (см. ниже). Внутренний lookup использует отдельный
служебный секрет по OpenAPI. Изменения контракта проходят согласование
фронтенда и владельца сервиса по SPEC §8.
Существующие access JWT продолжают действовать до своего `exp` после logout;
logout отзывает refresh.

Register/login принимают `application/json`, ровно поля `username` и `password`.
Неизвестные, повторные и пропущенные поля, неверные типы, некорректный UTF-8,
одиночные UTF-16-суррогаты в JSON escape-последовательностях,
дополнительное JSON-значение и тело больше 1 MiB дают 422.
Корректные суррогатные пары и явно переданный U+FFFD сохраняются. Username - 3-32 ASCII
буквы/цифры/подчёркивания, пароль - минимум 8 Unicode code points; пробелы и
исходный пароль сохраняются без trim/нормализации и без предела bcrypt 72 байта.
Ошибки возвращаются как `ApiError` с `request_id`, ответы Auth имеют `no-store`.

Access JWT подписывается HS256 и содержит `sub`, `iat`, `exp` со сроком 900 секунд.
Совместимость проверяется настоящим общим `pkg/jwtauth`.
Refresh - 32 криптографически случайных байта, base64url без padding; в БД
хранится только SHA-256 digest. Каждый новый refresh живёт 30 дней.
Cookie: `refresh_token`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/auth`,
без Domain. Refresh никогда не возвращается в JSON. Дубли cookie отклоняются.

Пароли хранятся как Argon2id PHC: v19, 64 MiB, 3 итерации, parallelism 2,
случайная salt 16 байт, ключ 32 байта. Прочитанные параметры ограничены этим
набором. На сервис допускается до 4 одновременных KDF; ожидание отменяется
по context. Login неизвестного пользователя выполняет сравнение с dummy hash.
Прикладной context имеет timeout 10 секунд; запущенный Argon2 завершается сам.

Ротация и logout блокируют строку refresh. Срок проверяется по
`clock_timestamp()` после блокировки. Из двух конкурентных применений одного
токена успешно ровно одно. Ошибка до commit откатывает отзыв и вставку successor.
При потере подтверждения commit результат неизвестен; автоматического повтора
ротации нет, клиенту может потребоваться новый вход.

## Профиль, поиск и контакты (#28)

Все пять операций требуют один `Authorization: Bearer <access JWT>` из общего
`pkg/jwtauth`. Cookie и query-параметр не заменяют этот заголовок. Пользователь
берётся из проверенной identity; `user_id` в теле или query не выбирает владельца.
Если пользователь из действительного JWT уже отсутствует в БД, возвращается 401.

| Операция | Поведение |
| --- | --- |
| `GET /me` | Публичный User: id, исходный username, created_at |
| `GET /users/search?prefix=...` | До 20 UserSummary по префиксу без учёта регистра |
| `GET /contacts` | Весь собственный список, без пагинации |
| `PUT /contacts/{contact_id}` | Добавление и повтор возвращают пустой 204 |
| `DELETE /contacts/{contact_id}` | Удаление и отсутствие записи возвращают пустой 204 |

Поиск принимает один `prefix` длиной 1-32 ASCII символа `[A-Za-z0-9_]`.
Пропуск, повтор, пустое значение, недопустимые символы или повреждённая query дают
422. Подчёркивание в SQL экранируется как буквальный символ. Пустой результат -
`{"users": []}`. Поиск может включать текущего пользователя: фильтрация себя
на экране остаётся правилом фронтенда из #68.

Контакты односторонние, сравниваются по UUID и сортируются по ASCII lower-case
username; исходное написание сохраняется. Пустой список - `{"contacts": []}`.
Добавление себя даёт 422, несуществующего пользователя 404. Некорректный UUID
даёт 422 для PUT и DELETE. DELETE собственного или несуществующего UUID даёт 204.
Прописные hex-символы UUID нормализуются до сравнения. Nil UUID имеет корректный
формат: при отсутствии пользователя PUT даёт 404, DELETE даёт 204.
Удаление контакта не изменяет чаты, сообщения и chat_members.

Для #36 внешний Nginx должен проксировать также `/me`, `/users/search`, `/contacts`
и `/contacts/{contact_id}` по OpenAPI. Реальной конфигурации Nginx в main пока нет;
доступность через внешний HTTPS проверяется после деплоя в #38.

## Внутренний lookup (#28)

`GET /internal/users/{user_id}` принимает ровно один
`Authorization: Bearer <AUTH_INTERNAL_TOKEN>` и возвращает только `id` и
исходный `username`. Credential сравнивается через SHA-256 digest и
constant-time compare. Парольный hash, created_at и refresh не возвращаются.
Пользовательский access JWT, cookie и query-параметр не дают служебного доступа.
Ошибки credentials дают 401; отсутствующий пользователь и некорректный UUID
дают 404. Успешный lookup не зависит от существования пользовательской сессии.

Секрет обязателен для запуска всего Auth: при его отсутствии или неверном
формате процесс завершается до запуска HTTP, включая login и refresh.
Рабочего значения по умолчанию нет, значение не совпадает с JWT_SECRET.
Передайте одинаковый отдельный секрет только Auth и
History через окружение/Secrets. Не отдавайте его фронтенду и не пишите в логи.
Замена текущего секрета требует согласованного обновления потребителя и Auth;
автоматической ротации нескольких служебных ключей здесь нет.

Сервисный HTTP использует тот же внутренний порт Auth по OpenAPI.
Он не добавляет шифрование канала: внутренний HTTP предполагает доверие
окружению одного VPS. TLS внешнего Nginx не шифрует отдельный History -> Auth.
Внутренний TLS/mTLS является отдельным инфраструктурным решением.

Для #36 подготовлен [snippet](../../deploy/nginx/snippets/auth-locations.conf):
он проксирует публичные Auth/profile/search/contacts и отвечает 404 на
`/internal` и `/internal/...` даже при верном служебном credential.
Его нужно включить в публичный `server`, объявив upstream `auth_backend`
с адресом Auth внутри Compose. Порт самого Auth наружу не публиковать.
Полная конфигурация домена, TLS и деплоя остаётся в #36-38.
Порядок передачи секрета до выката описан в [deploy README](../../deploy/README.md#служебный-секрет-authhistory-для-37),
а проверка исходного URI и закрытого lookup - в [проверках Nginx](../../deploy/nginx/README.md).
Проверка локального Nginx не заменяет QA реального стенда.

## Состояние и остановка

- `/healthz` - 200, пока HTTP-процесс отвечает.
- `/readyz` - 200 после запуска, когда доступны необходимые таблицы и поля
  `auth.users`, `auth.refresh_tokens` и `auth.contacts` под ролью сервиса.
  Проверяются чтение, INSERT для всех трёх таблиц, UPDATE для refresh и
  DELETE для contacts; отсутствующая миграция или права
  дают 503. Проверка не читает credentials, не меняет данные и ограничена одной
  секундой. После применения миграции/выдачи прав готовность восстанавливается
  без перезапуска. При остановке readiness сбрасывается.
- `/metrics` - внутренние Go/process-метрики, результаты HTTP-операций и статистика пула БД.
- При SIGTERM listener закрывается и активным запросам даётся
  `SHUTDOWN_TIMEOUT`; при превышении соединения принудительно закрываются.

Логи - JSON с service/request_id, без body, query, паролей и токенов.
Ошибки SQL/DSN не выдаются клиенту и не пишутся в прикладные логи.
Служебные endpoints не следует публиковать через внешний Nginx.

## Метрики Auth

`auth_http_requests_total` и `auth_http_request_duration_seconds` измеряют
вызовы зарегистрированных HTTP-операций от входа в обработку маршрута до
ответа. Например, `operation="POST /auth/login"` для входа и
`operation="PUT /contacts/{contact_id}"` для записи контакта. Метка `result`
содержит класс ответа `2xx`, `3xx`, `4xx`, `5xx`, `aborted` или `other`.
Отказ авторизации учитывается в маршруте, для которого он произошёл.
`aborted` фиксируется при `http.ErrAbortHandler` или при панике после начала
ответа либо перехвата соединения. Остальные классы отражают статус ответа
на стороне обработчика. Обрывы со стороны клиента и ошибки записи тела
отдельно не измеряются.

В метрики операций не входят служебные health, readiness и scrape, а также
ответы роутера без шаблона операции, например 404, 405 и редиректы нормализации
пути. Если прикладной обработчик возвращает 404, метрика учитывает его
по шаблону маршрута.
Серии появляются после первого вызова операции.

`auth_db_pool_connections` показывает число открытых (`state="open"`),
занятых (`state="in_use"`) и свободных (`state="idle"`) соединений.
`auth_db_pool_max_open_connections` показывает предел пула.
`auth_db_pool_waits_total` и `auth_db_pool_wait_duration_seconds_total`
накапливают число ожиданий соединения и их длительность в секундах.
По ним можно отличить задержку в очереди пула от задержки операции при
свободных соединениях. Scrape берёт локальную статистику `database/sql`.
Значения меток ограничены шаблонами операций, классами ответа и состояниями пула.

Проверка с внутренней сети сервиса:

```bash
curl -fsS http://127.0.0.1:8080/metrics | grep -E '^auth_(http|db_pool)_'
```

## Проверки

```bash
make test
make lint
make build SERVICE=auth
```

Для интеграционных тестов используйте тестовый PostgreSQL и роль с CREATEDB:

```bash
AUTH_TEST_DATABASE_URL='postgres://test_user:test_password@127.0.0.1:15432/postgres?sslmode=disable' \
  go test -race -count=1 ./services/auth -run TestAuthIntegration -v
```

Тест создаёт отдельную БД `messenger_auth_test_*`, применяет настоящую миграцию
Auth и удаляет эту БД после проверки. Таблицы БД из URL не изменяются.
Без переменной integration-тесты пропускаются; в **Go test** CI она обязательна
и задана вместе с отдельным PostgreSQL 18. Проверки прав дополнительно
создают временную роль при наличии CREATEROLE (в CI это право есть);
при отсутствии этого права пропускается только соответствующий подтест.

Проверяются HTTPS login/register/refresh/logout, структура JSON и cookie,
Argon2id, совместимость JWT, независимость сессий, expiry, повтор старого refresh,
готовность до/после миграции, потеря таблиц и недостаточные права роли,
отклонение одиночных суррогатов и сохранение корректных Unicode-паролей,
конкурентные регистрации/refresh/logout, rollback при ошибке successor и expiry
после ожидания row lock. Unit-тесты покрывают валидацию, KDF, сервисные правила,
безопасные ошибки, readiness, метрики, логи, recovery и graceful shutdown.

Перед завершением задачи нужны независимое ревью и QA на staging по
[CONTRIBUTING](../../CONTRIBUTING.md). На внешнем HTTPS проверить cookie,
ротацию/выход, ошибки 401/409/422, недоступность БД и остановку/перезапуск Auth.
