# Шаблон Go-сервиса

Основа для auth, chat и history по [T06](https://github.com/messenger-go-team/messenger/issues/6).
HTTP, логи и сигналы используют net/http, log/slog и os/signal.
Метрики подключены через общий internal/metrics и официальный prometheus/client_golang.
Все Go-файлы этого каталога составляют один исполняемый пакет main без
импортов собственного пути. Копирование не требует замены Go import paths.

## Сборка и запуск

Из корня репозитория нужны Go из go.mod, GNU Make и C-компилятор для race detector.
В Windows используйте WSL.

~~~bash
make build
export JWT_SECRET="$(openssl rand -hex 32)"
SERVICE_NAME=template HTTP_ADDR=127.0.0.1:8080 ./bin/_template
~~~

В другом терминале:

~~~bash
curl -i http://127.0.0.1:8080/healthz
curl -i -H 'X-Request-ID: local-check-1' http://127.0.0.1:8080/readyz
~~~

Оба endpoint возвращают 200 и JSON при работающем шаблоне.
Каждый ответ содержит X-Request-ID. Для остановки нажмите Ctrl+C или отправьте
SIGTERM процессу бинарника. Запускайте бинарник напрямую, чтобы сигнал получал
сам сервис, а не родительский процесс go run или make.

## Конфигурация

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| SERVICE_NAME | template | Значение service в JSON-логах; непустое |
| HTTP_ADDR | :8080 | Адрес host:port; :8080 слушает все интерфейсы, 127.0.0.1:8080 - только loopback |
| LOG_LEVEL | INFO | Уровень log/slog: DEBUG, INFO, WARN, ERROR; регистр не важен, допустимы смещения slog |
| SHUTDOWN_TIMEOUT | 10s | Положительная длительность ожидания активных HTTP-запросов |
| JWT_SECRET | Нет | Общий секрет HS256 минимум 32 байта; обязателен при запуске |

Значения читаются из окружения процесса. Отсутствующая переменная получает
default; явно пустая проходит валидацию как заданное значение и приводит
к ошибке для этих настроек. Порт 0 допустим для автоматического выбора
свободного порта, фактический адрес есть в записи server listening.
Ошибки конфигурации и запуска завершают процесс с кодом 1 и JSON-диагностикой.

Файл .env автоматически не загружается. Существующий корневой .env относится
к локальному Compose; шаблон не читает его и не логирует всё окружение.
У сервисов и Compose будут отдельные настройки зависимостей в следующих задачах.

JWT_SECRET проверяется при чтении конфигурации. Секрет хранится внутри
общего verifier и не выводится в ошибках конфигурации. Всем сервисам нужно
передать одно значение, не генерировать разные ключи для auth/chat/history.
Пример ключа в корневом .env.example нужно заменить перед использованием.

## Защищённые HTTP-маршруты

Прикладной mux в server.go подключён через общий pkg/jwtauth middleware.
При копировании шаблона добавляйте защищённые маршруты в application.
Health/readiness/metrics обслуживаются отдельным mux, остаются доступны
без JWT и сохраняют ответы 405 для неподдерживаемых методов.
До добавления прикладных маршрутов запрос с действующим JWT к неизвестному
пути получает 404, без действующего JWT - 401.

Публичные register/login/refresh/logout добавляются отдельно от защищённого
прикладного mux; эта задача не реализует auth API. Пользователь из JWT
доступен через jwtauth.FromContext(r.Context()); доступ к конкретному чату
или ресурсу проверяет сам сервис. Подробнее и пример использования:
[pkg/jwtauth](../../pkg/jwtauth/README.md).

## Проверки состояния и остановка

- GET /healthz возвращает 200 и {"status":"ok"}: HTTP-процесс отвечает.
- GET /readyz возвращает 200 и {"status":"ready"} после запуска listener.
  До готовности/при остановке состояние readiness сброшено; handler отдаёт
  503 и {"status":"not_ready"}, пока соединение ещё позволяет выполнить запрос.
- При SIGTERM или Ctrl+C readiness сбрасывается, listener закрывается,
  активные HTTP-запросы получают время на завершение. Новый shutdown context
  не наследует уже отменённый signal context.
- При превышении SHUTDOWN_TIMEOUT соединения принудительно закрываются,
  процесс завершается с кодом 1. Успешная остановка возвращает 0.
- Начальные таймауты HTTP: заголовки 5s, чтение/запись 15s, idle 60s,
  максимум заголовков 1 MiB. Лимиты body задаются отдельно будущими обработчиками.

У шаблона пока нет PostgreSQL, Redis и gRPC, поэтому readiness проверяет
только собственный жизненный цикл. После копирования сервис добавляет проверки
тех зависимостей, без которых не может обслуживать запросы.

Server.Shutdown не закрывает hijacked WebSocket-соединения. Их регистрацию,
оповещение и ожидание завершения добавляет chat в T33, как и WS-лимиты/таймауты.

## Логи и request_id

JSON-логи пишутся в stdout, ошибка чтения конфига - в stderr.
Каждая запись содержит service. HTTP-middleware принимает X-Request-ID
из 1..64 символов A-Z, a-z, 0-9, точки, дефиса и подчёркивания; при отсутствии
или невалидном значении генерирует криптографически случайный ID.
Он возвращается в заголовке ответа и доступен обработчикам через:

~~~go
loggerFromContext(r.Context()).InfoContext(r.Context(), "operation completed")
~~~

Access log содержит request_id, method, path и duration_ms. Заголовки, query
и body туда не записываются. Не добавляйте в прикладные логи пароли и токены.
Стартовые/служебные записи вне HTTP-запроса не имеют request_id.

RequestLogging передаёт writer в recovery с сохранением возможностей Upgrade
для будущего chat. Корреляция исходящих REST/gRPC-вызовов добавляется в задачах
соответствующих клиентов.


## Panic recovery

Стек обработчиков: requestLogging -> recoverPanic -> router.
Router направляет служебные запросы в отдельный mux, прикладные - через
JWT middleware. В конфигурации служебных unit-тестов newHandler использует
обычный NotFoundHandler; подключение JWT проверяется отдельно в auth_test.go.
Логгер с service/request_id создаётся до recovery. Последний запоминает
X-Request-ID до вызова handler, поэтому JSON 500 и диагностическая запись
используют один ID даже если handler успел изменить заголовок.

При panic до начала ответа возвращается HTTP 500, application/json и
совместимый с auth ApiError:

~~~json
{"code":"internal_error","message":"Внутренняя ошибка сервера.","request_id":"local-check-1"}
~~~

Подготовленные handler заголовки представления/фрейминга (например,
Content-Length и Content-Encoding) удаляются перед этим JSON.
Текст panic и stack trace остаются в серверной записи panic recovered,
клиент их не получает.

После финального WriteHeader, Write или Flush ответ уже нельзя заменить.
Recovery логирует ошибку и передаёт http.ErrAbortHandler серверу для прерывания
ответа, не дописывая JSON. Информационный 103 допускает последующий финальный
500; 101 Switching Protocols считается началом ответа.

При неожиданной panic после успешного Hijack recovery самостоятельно закрывает
захваченное соединение: net/http им больше не владеет. Успешный Upgrade без
panic оставляет соединение у handler. Сам http.ErrAbortHandler передаётся
без дополнительного error-log/JSON, сохраняя стандартную семантику; владельцу
hijacked-соединения в этом случае по-прежнему нужно управлять его закрытием.

Обёртка отслеживает прямые Flusher/Hijacker и вызовы через ResponseController,
включая прозрачные обёртки с Unwrap. Она не объявляет эти интерфейсы, если
они недоступны. Остальные операции ResponseController делегируются через Unwrap.
Не обходите tracking-обёртку прямой записью в нижележащий writer.

Recovery работает в той же горутине, где вызывается ServeHTTP. Panic в отдельно
запущенных горутинах и управление всем жизненным циклом WS в него не входят.
В production-маршрутах нет специального endpoint для вызова panic; сценарии
проверяются тестовыми handlers.

## Метрики Prometheus

GET /metrics возвращает настоящую экспозицию Prometheus на том же HTTP-порту,
что health/readiness. Настройка находится в общем пакете internal/metrics,
который используется и копиями шаблона в том же монорепозитории.

~~~bash
curl -sS -H 'Accept: text/plain; version=0.0.4' http://127.0.0.1:8080/metrics
~~~

Примеры семейств: go_goroutines, go_memstats_alloc_bytes,
process_cpu_seconds_total, process_resident_memory_bytes.
Их собирают стандартные Go/process collectors официального client_golang v1.25.0.
Процессные метрики проверены на целевой Linux/WSL-платформе.

Registry создаётся один раз при создании handler конкретного сервиса.
Глобальные DefaultRegisterer/DefaultGatherer не используются: повторное создание
handler не вызывает duplicate registration, набор метрик не смешивается между
экземплярами. При этом два handler в одном процессе измеряют один Go runtime
и процесс, поэтому сами значения базовых метрик могут совпадать.

Endpoint предназначен для scrape по внутренней сети/локальному адресу.
Не добавляйте /metrics во внешние маршруты Nginx без отдельного решения.
Пакет не поднимает отдельный listener и не добавляет аутентификацию к /metrics;
границу доступа задаёт окружение и маршрутизация.

Здесь только базовые runtime/process collectors. HTTP/WS бизнес-метрики,
Prometheus server и Grafana добавляются отдельными задачами.
Request_id и user_id не используются как labels метрик.

Пакет расположен вне _template также для корректной работы go mod tidy:
команда пропускает каталоги с начальным подчёркиванием, а internal/metrics
виден при обходе модуля и удерживает зависимости Prometheus в go.mod/go.sum.
Тесты самого шаблона по-прежнему явно добавлены в make test и CI.
## Создание сервиса копированием

Пример для auth, выполнять из корня только если services/auth ещё отсутствует:

~~~bash
test ! -e services/auth && cp -R services/_template services/auth
make build SERVICE=auth
SERVICE_NAME=auth HTTP_ADDR=127.0.0.1:8081 ./bin/auth
~~~

Имя сервиса задайте в окружении/Compose: переименование каталога само по себе
не меняет SERVICE_NAME. Затем замените README копии документацией этого сервиса
и добавьте его маршруты/зависимости, сохранив lifecycle и тесты.
Новый go.mod не нужен: сервис входит в корневой модуль и использует общий
internal/metrics. Копирования в services/auth достаточно внутри этого репозитория;
при переносе в отдельный проект потребуется перенести и общий пакет.
При росте кода выделяйте internal-пакеты уже под путём конкретного сервиса.

## Проверки

~~~bash
make test
make lint
~~~

Makefile и CI **явно** добавляют ./services/_template к ./...: Go обычно
пропускает каталоги, начинающиеся с подчёркивания. После копирования обычные
services/auth, services/chat и services/history включаются в ./... автоматически.

make lint по умолчанию запускает закреплённый golangci-lint v2.15.0 через go run.
При первом запуске нужен доступ к Go proxy и кешу инструментов, go.mod/go.sum
проекта при этом не меняются. Можно использовать установленный бинарник:

~~~bash
make lint GOLANGCI_LINT=golangci-lint
~~~

Бинарник должен поддерживать Go из go.mod; старый линтер, собранный Go 1.26,
не подходит для проекта на Go 1.27.3. CI использует бинарник той же версии.
Тесты покрывают конфиг, health/readiness, JSON-логи и request_id, занятой порт,
завершение активного запроса и принудительное закрытие по deadline.
Дополнительно проверяются JSON 500 и продолжение работы после panic, обрыв начатого ответа, ErrAbortHandler, прямые/ResponseController Flush и Hijack, закрытие соединения при panic после Hijack и сохранение успешного Upgrade.

Проверки метрик включают разбор экспозиции Prometheus, базовые Go/process-семейства, независимость registry и маршрут /metrics в стеке requestLogging/recovery.
