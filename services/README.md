# Go-сервисы

Монорепозиторий содержит три сервиса с границами ответственности из
[SPEC, раздел 6](../docs/SPEC.md).

| Планируемый каталог | Ответственность | Таблицы во владении |
| --- | --- | --- |
| `auth/` | Пользователи, токены и контакты | `users`, `refresh_tokens`, `contacts` |
| `chat/` | WebSocket-соединения и доставка событий | Собственных таблиц нет |
| `history/` | Чаты, участники, сохранение и выдача сообщений | `chats`, `chat_members`, `messages` |

chat сохраняет сообщения через gRPC-вызов history. history назначает `seq`
и обеспечивает идемпотентность по `client_msg_id`. Доступ к чатам определяется
членством в `chat_members`, включая личные чаты с двумя участниками.

Готовый [шаблон сервиса](_template/README.md) находится в `_template/` (T06).
Из корня: `make build`, `make lint`, `make test`. Сервисы создаются копированием
шаблона; инструкция, переменные окружения и ограничения описаны в его README.
Все сервисы входят в один корневой Go-модуль. Версия Go указана в
`go.mod` и используется в CI. Проверки и локальные команды описаны в
[docs/ci.md](../docs/ci.md).

## Миграции PostgreSQL

Миграциями владеют только auth и history. Они лежат рядом с владельцем:
`auth/migrations` и `history/migrations`. Таблицы миграций тоже раздельные:
`auth_schema_migrations` и `history_schema_migrations`. Поэтому добавление
миграции одного сервиса не меняет версию другого.

Сначала поднимите PostgreSQL и дождитесь его готовности:

```bash
docker compose up -d --wait postgres
```

Затем примените все миграции одной командой:

```bash
make migrate-up
```

Команда читает `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и
`POSTGRES_PORT` из корневого `.env`. Значения из уже заданного окружения
имеют приоритет над `.env`.
Запускайте из корня репозитория. По умолчанию подключение идёт к
`127.0.0.1:15432`; при необходимости задайте `POSTGRES_HOST` и
`POSTGRES_SSLMODE` (по умолчанию `disable` для локальной разработки).
Отдельный CLI golang-migrate не нужен: команда использует Go-библиотеку.

Для проверки отката начальной миграции и повторного применения выполните:

```bash
make migrate-down
make migrate-up
make migrate-version
```

По умолчанию `migrate-down` откатывает по одной миграции каждого сервиса.
Можно ограничить команду владельцем, например
`make migrate-up MIGRATE_SERVICE=history`, или изменить число шагов:
`make migrate-down MIGRATE_SERVICE=auth MIGRATE_STEPS=2`.

Начальные миграции рассчитаны на PostgreSQL 18 и
[схему T11](../docs/db/schema.md). Они создают таблицы, ограничения и индексы,
включая ASCII-нормализацию username с collation `"C"`, уникальность сообщений
и предел `9007199254740991` для seq и курсоров. `gen_random_uuid()` встроен
в PostgreSQL; дополнительное расширение pgcrypto не требуется.
Граница курсоров относительно `chats.last_seq`, сравнение body при повторе
и точное число участников личного чата проверяются сервисом в транзакциях,
как описано в схеме. U+0000 отвергает сам тип `text`; Chat/History должны
проверять его до записи для предсказуемой ошибки валидации.

Откат начальной миграции удаляет все данные соответствующего сервиса.
Проверяйте его на отдельной БД. `down` удаляет только перечисленные таблицы,
затем пустую схему, без CASCADE. Если появились посторонние объекты или
зависимости, транзакция отката завершается ошибкой и сохраняет объекты.
При ошибке golang-migrate отмечает версию как dirty: сначала разберите причину
и состояние БД; автоматического force/reset версии команда не выполняет.
При выборе `all` сервисы обрабатываются последовательно, в отдельных
транзакциях. Ошибка второго сервиса не откатывает уже завершённую операцию первого.

### Интеграционные проверки миграций

Тесты создают и удаляют собственные БД с префиксом `messenger_migrate_test_`.
Указанный пользователь должен иметь право CREATEDB. Используйте тестовый
PostgreSQL; таблицы БД из URL тесты не изменяют.

```bash
MIGRATE_TEST_DATABASE_URL='postgres://test_user:test_password@127.0.0.1:15432/postgres?sslmode=disable' \
  go test ./cmd/migrate -run TestMigrationsIntegration -count=1 -v
```

Без `MIGRATE_TEST_DATABASE_URL` интеграционные тесты пропускаются.
В CI отдельное задание `Migration integration` запускает их с PostgreSQL 18.
Проверяются `up -> down -> up`, независимость версий сервисов, уникальность,
self-contact, нормализация и сортировка username, границы seq и курсоров,
FK отправителя, U+0000, длина Unicode-текста и сохранность посторонних
объектов при отказе отката.
