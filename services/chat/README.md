# Chat

WebSocket-эндпоинт /ws из [#33](https://github.com/messenger-go-team/messenger/issues/33)
по [контракту WebSocket v1](../../api/ws/events.md).
Транспорт реализован в #33, хаб и рассылка серверных событий - в #34.
Chat обрабатывает `message.send`, передаёт автора из access JWT и сохраняет
сообщение через `History.SaveMessage`. После commit Chat отправляет `message.ack`
исходному сокету и `message.new` всем подключённым вкладкам участников.
Повтор с тем же `client_msg_id` и тем же текстом возвращает метаданные исходной
записи. Если уведомление пропущено, сообщение доступно через REST History.

## Запуск

Из корня репозитория соберите и запустите сервис:

    make build SERVICE=chat
    JWT_SECRET="<общий секрет HS256, минимум 32 байта>" \
      WS_ALLOWED_ORIGINS="http://localhost:5173,http://127.0.0.1:5173" \
      HTTP_ADDR=127.0.0.1:8080 ./bin/chat

Настройки общие с [шаблоном Go-сервиса](../_template/README.md).
SERVICE_NAME по умолчанию равен chat. Обязательный WS_ALLOWED_ORIGINS -
список HTTP(S) origins через запятую. Указывайте схему, хост и порт
в том виде, в каком их присылает браузер, без пути и конечного слеша.
`HISTORY_GRPC_ADDR` задаёт приватный `host:port` History (по умолчанию
`history:9090`). При запуске обоих сервисов в WSL укажите адрес слушателя
History, например `127.0.0.1:9090`. `HISTORY_RPC_TIMEOUT` ограничивает вызов
History и по умолчанию равен `3s`.

`/readyz` проверяет готовность History через приватный gRPC health
на том же адресе с таймаутом в одну секунду. Если History недоступен
или его хранилище не готово, Chat возвращает `503`. `/healthz` проверяет
жизнеспособность процесса Chat.

В DevTools на разрешённом origin откройте соединение с действующим
access JWT, выпущенным с тем же JWT_SECRET:

    const ws = new WebSocket("ws://127.0.0.1:8080/ws", ["messenger.v1", "bearer." + accessToken])
    ws.onopen = () => console.log(ws.protocol)
    ws.onclose = ({ code }) => console.log(code)

Ожидаемый протокол - messenger.v1. Ctrl+C на сервере отправляет Close 1001.
При истечении токена сервер отправляет Close 4401.
Один WebSocket-message ограничен 64 KiB. Сервер отправляет Ping каждые
25 секунд, ждёт соответствующий Pong до 10 секунд и ограничивает запись
каждого кадра 10 секундами. При переполнении очереди из 32 событий сервер
отключает медленное соединение с Close 1013, если транспорт ещё позволяет
записать управляющий кадр. Клиент восстанавливает данные через REST history.

## Лимит отправки сообщений

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `WS_SEND_INTERVAL` | `200ms` | Положительный интервал пополнения на одну команду. При `200ms` это 5 команд в секунду |
| `WS_SEND_BURST` | `10` | Положительное целое, максимальный запас команд на пользователя |

Лимит применяется к валидным `message.send` после разбора команды и до
`History.SaveMessage`. Все вкладки, устройства и чаты одного пользователя
делят бюджет внутри одной реплики Chat. Переподключение к той же реплике
сохраняет бюджет. Каждая реплика ведёт свой счётчик, поэтому подключения к
разным репликам могут использовать несколько бюджетов. При перезапуске
бюджет реплики начинается заново.

Сверх лимита Chat возвращает `rate_limited` с `retryable: true` и
`retry_after_ms` до пополнения одного токена. Клиент приостанавливает всю
очередь на максимум из подсказки сервера и клиентского backoff, затем
отправляет первое готовое сообщение в порядке очереди. При повторе сохраняются
`client_msg_id` и текст, id конверта создаётся заново. Без подсказки сервера
используется клиентский backoff. Отклонённая попытка не вызывает History и
не рассылается.

На внутреннем `/metrics` счётчик
`chat_ws_message_send_rejected_total{reason="rate_limited"}` считает только
локальные отказы по бюджету. Метка `reason` имеет одно фиксированное
значение. Идентификаторы и текст команд в метрику не входят.

## Рассылка

Chat регистрирует соединение по `sub` проверенного access JWT и удаляет его
при закрытии. `/metrics` содержит gauge `chat_active_websocket_connections`,
который считает соединения, включая несколько вкладок одного пользователя.

Для серверного события `broadcastChat` вызывает `GetChatMembers` от имени
проверенного пользователя. Брокер в памяти ставит событие в очередь каждого
открытого сокета из полученного списка. Ошибка History прерывает рассылку.
События для офлайн-пользователей не буферизуются.

    curl -i http://127.0.0.1:8080/healthz
    curl -i http://127.0.0.1:8080/readyz
    curl -sS http://127.0.0.1:8080/metrics | grep '^chat_active_websocket_connections '
    go test -race -count=1 ./services/chat

WebSocket можно открыть с тестовым JWT без PostgreSQL и Redis. Для определения
участников при рассылке нужен доступ к gRPC History по приватной сети.

## Статусы доставки и прочтения

В личном чате клиент подтверждает полученный или показанный диапазон
командами `message.delivered` и `message.read`. Chat передаёт `chat_id` и
`seq` в `History.AdvanceReceipt` с идентификатором из `sub` access JWT.
History обновляет курсоры и подтверждает транзакцию.

После успешного RPC Chat запрашивает актуальный состав чата и рассылает
сохранённый курсор всем открытым соединениям обоих участников. Если
`message.read` поднял и курсор доставки, Chat публикует оба события.
Повтор и допустимый старый `seq` возвращают актуальный курсор через ту же
рассылку. `message.ack` подтверждает сохранение `message.send`.

На каждом сокете команды статусов обрабатываются последовательно в
отдельной от `message.send` очереди до четырёх ожидающих команд. На одной
реплике Chat все вкладки аккаунта делят бюджет статусов. Бюджет
пополняется на одну команду каждые 50 мс, начальный запас - 24 команды.
Повторы тоже расходуют этот бюджет.
Одновременно реплика обрабатывает до восьми статусов, включая RPC записи
и получения участников. При переполнении очереди или исчерпании одного
из лимитов Chat возвращает инициатору `temporarily_unavailable` с
`retryable: true` до обращения к History. Клиент повторяет команду по
правилам раздела 10, а бюджет отправки текста работает отдельно.

Офлайн-вкладки восстанавливают курсоры через `GET /chats/{chat_id}/receipts`.
Форматы событий, условия продвижения и обработка ошибок описаны в
[контракте WS](../../api/ws/events.md#10-доставка-и-прочтение---этап-2).

    go test -race -count=1 ./services/chat -run Receipt

## Presence на одной реплике

Первый авторизованный WebSocket переводит пользователя в online. Уход последней
вкладки, истечение JWT или отсутствие ответного Pong завершают присутствие.
Chat учитывает самое позднее подтверждение активности на любой вкладке и
хранит его в памяти до 24 часов. После перезапуска время начинается с чистого
состояния. Heartbeat использует существующие Ping каждые 25 секунд и таймаут
Pong 10 секунд.

Chat обнаруживает кандидатов при подключении и с базовым интервалом
5 секунд с разбросом ±20%. Изменение статуса известного собеседника будит
сверку сразу. При сбое History ожидание повтора растёт до минуты.
Четыре обработчика объединяют до 32 операций разных пользователей
в один `BatchPresence` и запускают суммарно до 100 RPC в секунду.

Для записи изменившихся статусов Chat резервирует в History право
на запись для пакета до 128 собеседников. Просроченный кадр пропускается
до Gorilla. Уже начатая запись использует обычный дедлайн WebSocket.
Срок до начала записи - 1 секунда, предельное окно до завершения -
11 секунд от начала RPC. Chat освобождает разрешение после последнего
кадра, а History очищает потерянные разрешения. Сами статусы
presence по-прежнему хранятся в памяти Chat.

    go test -race ./services/chat -run Presence -count=1
    go test -race ./services/history -run TestListPresencePeersIntegration -count=1

Второй тест использует `HISTORY_TEST_DATABASE_URL` с изолированным PostgreSQL.
Поля событий и поведение при reconnect описаны в [контракте WS](../../api/ws/events.md#11-presence---этап-2).
