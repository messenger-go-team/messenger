# Staging для QA

Публичный адрес стенда [staging.tidingm.ru](https://staging.tidingm.ru).
Используйте HTTPS для REST и `wss://staging.tidingm.ru/ws` для WebSocket.
Разрешённый Origin для тестового клиента - `https://staging.tidingm.ru`.
Предлагайте подпротоколы `messenger.v1` и `bearer.<access JWT>`.
Отчёт о приёмке ведётся в [#38](https://github.com/messenger-go-team/messenger/issues/38).

### Веб-клиент (#46)

Production-сборка SPA: `web/.env.production` (`VITE_API_MOCK=false`, same-origin).
Образ: `docker build -f web/Dockerfile -t messenger-web:<tag> web` (порт 8080,
`/healthz`). Пока rootless compose и ingress не отдают SPA на `/`, UI на
публичном URL недоступен — нужен сервис `web` и proxy `location /` на него.
Подробности и чек-лист приёмки: [web/README.md](../web/README.md#staging-46).

## Доступ и тестовые данные

Ответственный за staging выдаёт выделенные тестовые учётки по согласованному
каналу. QA получает имена и тестовые пароли. Административный SSH, строки
подключения к БД и служебный аккаунт пробника остаются у оператора.
Тестовые пароли хранятся в закрытом хранилище, а в manifest набора используются
только код, имена и UUID.

После получения доступов QA входит на staging через `POST /auth/login` под
выданными учётками и сверяет свой профиль через `GET /me`. В задаче #38 QA
подтверждает получение доступов и успешный вход. Для подтверждения достаточно
даты и результата. Пароли, токены и cookies остаются в приватном канале.

Для нового набора выберите уникальный код из 6–12 строчных букв и цифр.
Через `POST /auth/register` создайте `qa38_<код>_a`, `qa38_<код>_b` и
`qa38_<код>_c` с отдельными паролями. Выполните `POST /auth/login`
и узнайте UUID каждого аккаунта через `GET /me`. С токеном A вызовите
`POST /chats/personal` с телом `{"user_id":"UUID_B"}`. Сохраните ID чата и UUID
участников в manifest. Аккаунт C остаётся вне чата A–B.

## Как подтвердить сборку

Перед прогоном откройте [Deploy staging](https://github.com/messenger-go-team/messenger/actions/workflows/deploy.yml).
В журнале успешного SSH-шага найдите `STAGING_RESULT deployed` или
`STAGING_RESULT already_active` и выпишите SHA. Оператор сверяет его с
`REVISION` активного снимка из `.release-state/current` и OCI-меткой
образов запущенных сервисов. При ручном откате фактическая версия на VPS
может отличаться от последней записи GitHub. [Порядок релиза](../deploy/staging-release.md)

У staging отдельный rootless Compose-проект `messenger36-stage`, БД
`messenger_stage` и собственный том. Внутренний ingress слушает
`127.0.0.1:18080`. Оператор работает через пользовательский Docker-сокет
пользователя `messenger-stage`. [Устройство стенда](../deploy/staging-actions.md)

## Чек-лист публичной проверки

1. Через HTTPS проверьте login и `Set-Cookie` с `Secure`, `HttpOnly`,
   `SameSite=Lax` и `Path=/auth`. Успешный refresh меняет cookie, прежний
   токен даёт `401`. Logout возвращает пустой `204`, удаляет cookie и отзывает
   текущий refresh.
2. Откройте A1/A2, B и C через публичный WSS. Отправьте из A1 сообщение в
   A–B. A1 получает `message.ack`, A1/A2/B - `message.new` с тем же
   `message_id`. У C этого события нет. Проверьте сохранение через REST.
3. Сверьте `before_seq` и `after_seq`, последний текст и `unread_count`.
   Чтение истории сохраняет счётчик, отметка прочтения даёт пустой `204` и
   продвигает только собственный курсор. Постороннему C чтение и отметка
   прочтения возвращают `403`.
4. Оператор замеряет внутреннюю метрику `chat_active_websocket_connections`
   отдельным прогоном. Закройте сокеты предыдущего прогона, включая C, и
   снимите исходное значение N. Подключите только A1/A2/B и проверьте N+3.
   После закрытия A2 дождитесь N+2 и проверьте обмен сообщениями между A1 и B.
   После закрытия A1 и B метрика возвращается к N.
5. Отдельно удерживайте WSS дольше минуты с Ping/Pong. В согласованное окно
   оператор штатно останавливает и запускает только Chat. Зафиксируйте
   Close `1001`, возврат готовности и повторный публичный Upgrade.

В отчёте #38 укажите URL, фактический SHA, дату, результаты и номера тестовых
сообщений. Логи с JWT, cookies и паролями оставляйте в закрытой среде.
[Контракт Auth](../api/openapi/auth.yaml) · [Контракт History](../api/openapi/history.yaml) · [Контракт WebSocket](../api/ws/events.md)

## Сброс тестового чата

Закройте тестовые соединения и согласуйте сброс этого набора. Оператор
запускает проверенную копию скрипта на VPS от пользователя `messenger-stage`.
Подставьте код набора и UUID из manifest. Сначала сверьте ожидаемый чат и
счётчики в режиме предварительного просмотра.

```bash
bash /путь/к/staging-qa-reset.sh --preview КОД_НАБОРА UUID_A UUID_B UUID_ЧАТА
bash /путь/к/staging-qa-reset.sh --apply КОД_НАБОРА UUID_A UUID_B UUID_ЧАТА
```

Скрипт проверяет rootless-проект, БД, тестовые имена, состав чата и личную
пару. Он берёт общий lock staging и отклоняет чат с Later-записью другого
владельца. `--apply` удаляет выбранный чат, его сообщения, членство,
личную пару и связанные Later-записи. Тестовые учётки и остальные чаты
сохраняются. Для следующего прогона создайте новый чат через
`POST /chats/personal` и запишите его UUID.
[Скрипт сброса](../deploy/staging-qa-reset.sh)
