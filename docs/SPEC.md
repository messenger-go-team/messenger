# SPEC: универсальный мессенджер

Версия v0.2. Решения по открытым вопросам приняты (раздел 13), сроки сокращены вдвое, групповые чаты перенесены на этап после показа руководителю практики. После согласования документ переносится в репозиторий как `docs/SPEC.md` (экспорт в Markdown), и задачи ссылаются на него в поле «Источник».

## 1. Цель и контекст

Командный проект для портфолио: мессенджер на Go, на котором мы показываем практики промышленного бэкенда: реалтайм по WebSocket, надёжную доставку сообщений, горизонтальное масштабирование, наблюдаемость, автоматизированное тестирование и деплой.

Результат: работающее веб-приложение на публичном домене, репозиторий с понятной архитектурой и документацией, нагрузочный отчёт и демо.

## 2. Объём работ

### Делаем

- MVP (этап 1): регистрация и вход, личные чаты, история сообщений, доставка в реальном времени, адаптивный веб-клиент со всеми экранами сразу для мобильной, планшетной и десктопной ширины.
- Этап 2: статусы «доставлено» и «прочитано» в личных чатах, presence (онлайн/офлайн), индикатор набора текста, smoke-сценарии e2e.
- Этап 3: несколько инстансов chat-сервиса, надёжная доставка (ack, повторы, идемпотентность), переподключение без потерь, метрики, нагрузочные тесты, PWA, ограничение частоты запросов на Nginx.
- Этап 4 (по остаточному принципу): файлы и картинки, поиск по сообщениям, мобильное приложение (опционально, последним, только если этапы 1-3 закрыты).
- Этап 5: финал: README, демо-видео, финальная регрессия, готовность к показу руководителю практики.
- Этап 6 (после показа руководителю практики): групповые чаты, статусы доставки и прочтения в группах.

### Не делаем

- Push-уведомления на устройства.
- Сквозное шифрование, голосовые и видеозвонки.
- Боты, каналы, федерация с другими мессенджерами.
- Kubernetes и сервис-меш.
- Подтверждение почты и восстановление пароля.
- Собственный Go-gateway: вместо него Nginx на границе.

## 3. Пользователи и роли

- Пользователь: регистрируется, ищет людей, ведёт личные чаты.
- Участник группы: пишет в группу. Owner создаёт группу и управляет участниками (этап 6, после показа).

## 4. Функциональные требования

Идентификаторы FR-… используются в поле «Источник» задач.

### Аутентификация (auth)

- FR-AUTH-1: регистрация по username и паролю. Username уникален, 3-32 символа (латиница, цифры, подчёркивание), пароль не короче 8 символов.
- FR-AUTH-2: вход возвращает пару токенов: access (JWT, живёт около 15 минут) и refresh (непрозрачный токен, живёт около 30 дней).
- FR-AUTH-3: обновление токенов по refresh с ротацией: использованный refresh больше недействителен.
- FR-AUTH-4: выход отзывает refresh-токен.
- FR-AUTH-5: GET /me возвращает профиль текущего пользователя.
- FR-AUTH-6: поиск пользователей по префиксу username (в выдаче не больше 20 записей).
- FR-AUTH-7: собственный односторонний список контактов: получение, идемпотентное добавление и удаление. Контакты сортируются по username без учёта регистра. Добавить себя нельзя. Удаление контакта не меняет чат, историю и права участников.

### Чат (chat)

- FR-CHAT-1: между двумя пользователями существует не более одного личного чата.
- FR-CHAT-2: отправка текстового сообщения (до 4096 символов) по WebSocket.
- FR-CHAT-3: доставка сообщения онлайн-получателю в реальном времени (событие message.new).
- FR-CHAT-4: отправитель получает message.ack с серверным id, номером seq и временем после сохранения сообщения.
- FR-CHAT-5: повторная отправка с тем же client\_msg\_id не создаёт дубль и возвращает исходный ack.
- FR-CHAT-6: порядок сообщений внутри чата определяется монотонным номером seq, который назначает сервер.
- FR-CHAT-7: офлайн-получатель увидит сообщение в истории при следующем входе.
- FR-CHAT-8 (этап 6, после показа): групповые чаты: создание, добавление и удаление участников, выход из группы.
- FR-CHAT-9 (этап 2): статусы delivered и read в личных чатах (по последнему доставленному и последнему прочитанному seq).
- FR-CHAT-10 (этап 2): presence и индикатор набора текста.
- FR-CHAT-11 (этап 6, после показа): статусы delivered и read в групповых чатах.
- FR-CHAT-12 (этап 1): модель универсальная с первого дня: личный чат это чат с двумя участниками, права и рассылка событий определяются по chat\_members, а не по схеме «отправитель и получатель».

### История (history)

- FR-HIST-1: список чатов пользователя: последнее сообщение, время, счётчик непрочитанных.
- FR-HIST-2: история чата с курсорной пагинацией (before\_seq, after\_seq, limit до 100).
- FR-HIST-3: читать историю и писать в чат могут только его участники, иначе 403.
- FR-HIST-4 (этап 4): поиск по сообщениям своих чатов.

### Веб-клиент (web)

- FR-WEB-1: экраны: вход, регистрация, список чатов, окно чата, профиль, отдельный экран «Контакты» в общей навигации. Поиск пользователей и начало личного чата сохраняются также в списке чатов (T43). Позже создание группы.
- FR-WEB-2: адаптивная вёрстка для мобильной, планшетной и десктопной ширины, все экраны этапа 1 сразу.
- FR-WEB-3: автоматическое переподключение WebSocket с экспоненциальной задержкой и индикатором состояния соединения.
- FR-WEB-4: у каждого сообщения виден статус: sending, sent, delivered, read, failed. Для failed есть повторная отправка.
- FR-WEB-5: после переподключения клиент догружает пропущенные сообщения через history по after\_seq.
- FR-WEB-6 (этап 3): PWA: веб-манифест, иконки, установка на домашний экран и офлайн-оболочка приложения (service worker).
- FR-WEB-7 (этап 4, опционально): мобильное приложение: Android-сборка на базе существующего веб-клиента (например, через Capacitor) без публикации в сторах и без push-уведомлений. Берём только если этапы 1-3 закрыты.

### Контакты в MVP (T85 / #68)

- `GET /contacts` возвращает весь список текущего пользователя из JWT, без пагинации, по возрастанию ASCII lower-case username. Исходное написание сохраняется. Контакты односторонние: добавление A -> B не добавляет A в список B.
- `PUT /contacts/{contact_id}` возвращает пустой `204` при добавлении и повторе, `404` для несуществующего пользователя, `422` при попытке добавить себя или некорректном UUID. `DELETE /contacts/{contact_id}` возвращает пустой `204` и при отсутствии записи, включая собственный ID, `422` при некорректном UUID. Для всех операций нужен JWT, иначе `401`.
- Пустой ввод показывает все контакты и не вызывает глобальный поиск. Непустой ввод фильтрует контакты локально по вхождению подстроки в username без учёта регистра; отдельный блок «Найдено» использует `GET /users/search?prefix=...` по правилам OpenAPI: 1-32 символа `[A-Za-z0-9_]`, без учёта регистра, максимум 20 результатов. Невалидный ввод не отправляется на сервер.
- Глобальный поиск выполняется с debounce и отменой или игнорированием устаревших ответов. После очистки ввода поздний ответ не восстанавливает результаты. Себя не показываем; из блока «Найдено» исключаем ID строк, уже показанных в отфильтрованных контактах. Принадлежность к контактам определяем по множеству ID всего ответа `GET /contacts`; обязательный `is_contact` не добавляем.
- Действия строки: добавить, удалить, написать. «Написать» использует общий create-or-get личного чата history из T08 и переходит в окно по `chat_id`; добавление контакта не обязательно. Повторное действие открывает тот же чат. Маршрут окна согласуется в T43/T44, здесь новый маршрут не вводится.
- Есть состояния загрузки, пустых контактов, пустой поисковой выдачи, ошибки с повтором и выполняемого действия. При ошибке сохраняется последний корректный список. Действие блокируется на время запроса; после успеха список обновляется, optimistic update необязателен. Пустой `204` не разбирается как JSON.
- Экран работает в трёх раскладках: на узкой ширине отдельно с возвратом, на широкой размещение определяет макет. Текущие экраны MVP сохраняются. Общие поиск и create-or-get переиспользуются с T43. Макеты выполняются в #69, экран на моках в #70, настоящий API и staging в T46.
- Подготовленная схема T11 использует направленную пару `(user_id, contact_id)` как уникальный ключ и запрещает self-contact; новая таблица не требуется. Блокировки в текущий объём не входят. Правила сценариев проходят frontend/backend review в PR по задаче #68 до реализации.

## 5. Нефункциональные требования

Числа ниже целевые. Мы проверяем их нагрузочными тестами в этапе 3 и фиксируем фактические значения в отчёте.

- NFR-1 (производительность): один инстанс chat держит не менее 2 000 одновременных соединений. p95 задержки доставки онлайн-получателю не больше 300 мс при суммарной нагрузке около 200 сообщений в секунду.
- NFR-2 (доставка): от клиента до сервера «минимум один раз» (повторы), на стороне сервера эффект «ровно один раз» за счёт идемпотентности по client\_msg\_id. Порядок внутри чата сохраняется.
- NFR-3 (устойчивость): перезапуск или падение инстанса chat не теряет подтверждённые сообщения. Клиенты переподключаются и догружают пропущенное.
- NFR-4 (безопасность): пароли хранятся только в виде bcrypt или argon2 хеша. TLS на внешней границе. Права проверяются на каждый запрос. Задано ограничение размера сообщений. Частота запросов ограничивается на Nginx (limit\_req). Секреты лежат только в переменных окружения и GitHub Secrets.
- NFR-5 (наблюдаемость): структурные JSON-логи с request\_id, метрики Prometheus (соединения, сообщения в секунду, задержки, ошибки), эндпоинты /healthz и /readyz, дашборд в Grafana.
- NFR-6 (качество): линтер и тесты обязательны в CI. Нужны unit-тесты сервисного слоя, integration-тесты с реальной БД, API-тесты по OpenAPI в CI, 3-5 smoke-сценариев e2e на Playwright (с этапа 2) и нагрузочные на k6 (этап 3). Остальное проверяется вручную по чек-листам, на автоматизацию уходит не больше четверти времени QA.
- NFR-7 (воспроизводимость): окружение разработки поднимается одной командой docker compose up. Версия Go одинакова в go.mod и CI.

## 6. Архитектура

### Компоненты

```
Браузер
   │  HTTPS / WSS
Nginx  (TLS, домен, раздача фронтенда, балансировка, limit_req)
   │
   ├── auth     (пользователи, токены, контакты)
   ├── chat     (WebSocket-хаб, доставка, presence)
   └── history  (чаты, участники, сообщения)

PostgreSQL  источник истины
Redis       pub/sub между инстансами chat, presence
```

### Ответственность сервисов

- auth: единственный владелец таблиц users, refresh\_tokens и contacts.
- history: единственный владелец таблиц chats, chat\_members и messages. Именно он назначает seq.
- chat: сам данные не хранит. Принимает сообщения по WebSocket, сохраняет их через history, затем рассылает получателям.
- Общий Go-пакет проверяет JWT (HS256), его подключают все сервисы. Отдельного gateway нет.

### Путь сообщения

1. Клиент A отправляет по WebSocket message.send с client\_msg\_id.
2. chat проверяет права и вызывает history: сохранить сообщение.
3. history в одной транзакции увеличивает last\_seq чата и вставляет сообщение. Уникальный ключ по client\_msg\_id защищает от дублей.
4. chat отправляет клиенту A message.ack (id, seq, время).
5. chat публикует событие в Redis, адресуя его всем участникам чата из chat\_members (в личном чате их двое). Инстанс, к которому подключён получатель B, доставляет ему message.new.
6. Если B офлайн, сообщение остаётся в истории и забирается при следующем входе.

### Переподключение

Клиент хранит последний полученный seq по каждому чату. После обрыва он переподключается и запрашивает у history сообщения с after\_seq. Отдельная очередь для офлайн-доставки не нужна.

### Масштабирование chat

Каждый инстанс держит собственный хаб соединений. Между инстансами события ходят через Redis pub/sub, по каналу на пользователя. Presence хранится в Redis с TTL и продлевается heartbeat-сообщениями. Балансировку между инстансами chat выполняет Nginx (ip\_hash или least\_conn).

### Протоколы

- Снаружи: REST/JSON и WebSocket с JSON-сообщениями вида { type, id, ts, payload }.
- Между сервисами: chat → history по gRPC, контракт лежит в /api/proto.
- Токены: access JWT с подписью HS256 и общим секретом из переменной окружения (не короче 32 байт). Проверку выполняет общий Go-пакет в каждом сервисе. Переход на RS256 затронет только этот пакет и конфигурацию.
- Контракты лежат в /api: OpenAPI для REST, описание событий для WebSocket и protobuf для gRPC.

## 7. Модель данных (черновик)

- users: id (uuid), username (unique), password\_hash, created\_at.
- refresh\_tokens: id, user\_id, token\_hash, expires\_at, revoked\_at.
- contacts: user\_id, contact\_id, created\_at.
- chats: id, type (personal или group), title, created\_at, last\_seq.
- chat\_members: chat\_id, user\_id, role (owner или member), joined\_at, last\_delivered\_seq, last\_read\_seq.
- messages: id, chat\_id, seq, sender\_id, client\_msg\_id, body, created\_at. Уникальны пары (chat\_id, seq) и (chat\_id, sender\_id, client\_msg\_id). Индекс под выборку истории: (chat\_id, seq desc).

Точная схема и миграции делаются в задачах этапа 0.

## 8. Контракты и правила их изменения

- REST: /api/openapi/auth.yaml и /api/openapi/history.yaml.
- WebSocket: /api/ws/events.md с примерами JSON для каждого события.
- Контракт меняется только через pull request в /api с approval фронтенда и владельца сервиса. Сначала меняем контракт, потом код.

## 9. Окружения, деплой, процесс

- local: docker compose (PostgreSQL, Redis, сервисы).
- staging: окружение для QA, деплой автоматически из main.
- production: публичный домен, тот же VPS (Selectel), что и staging, но отдельный compose-проект.
- Входная точка: Nginx (TLS, маршрутизация, апгрейд WebSocket с увеличенным proxy\_read\_timeout, балансировка chat, limit\_req). Собственного gateway нет.
- CI/CD: GitHub Actions: линтер, тесты, сборка образов, деплой, откат на предыдущую версию.
- Правила работы с кодом описаны в CONTRIBUTING: защищённая ветка main, pull request с минимум одним approval, squash merge, коммиты в стиле Conventional Commits.
- Definition of Done задачи: код смержен через PR, тесты написаны и проходят в CI, контракты и документация обновлены, критерии приёмки выполнены, QA проверил на staging, если задача меняет поведение.

## 10. Сроки и критерии выхода этапов

Сроки сокращены вдвое относительно первого плана, работаем плотно: всего около 6 недель. Размер задач: S до 2 часов, M до полдня, L до одного дня, всё крупнее дробим.

- Этап 0 (3-5 дней): в main лежат SPEC, контракты (OpenAPI, события WebSocket, protobuf), схема БД с миграциями, скелет сервиса, CI, wireframes и дизайн-система v1, тест-план.
- Этап 1 (около 1,5 недель): два пользователя регистрируются, входят и переписываются в реальном времени на staging, все экраны есть в мобильной, планшетной и десктопной раскладке. История сохраняется и подгружается, автодеплой работает.
- Этап 2 (около недели): статусы delivered и read в личных чатах, presence, индикатор набора. Основные сценарии покрыты 3-5 smoke-тестами e2e.
- Этап 3 (около недели): два и более инстанса chat работают вместе, переподключение не теряет сообщения. Опубликован нагрузочный отчёт с фактическими цифрами по NFR-1. Настроены метрики и дашборд, PWA и limit\_req на Nginx.
- Этап 4 (3-5 дней, по остаточному принципу): файлы, поиск по сообщениям, затем мобильное приложение, если всё остальное закрыто. Реализованное закрыто тестами и описано в README.
- Этап 5 (около 3 дней): README со схемой архитектуры, демо-видео, финальная регрессия. После него показ руководителю практики.
- Этап 6 (после показа): групповые чаты (FR-CHAT-8) и статусы в группах (FR-CHAT-11).

## 11. Ключевые решения

- ADR-1: монорепозиторий.
- ADR-2: PostgreSQL единственный источник истины, Redis только транспорт между инстансами и presence.
- ADR-3: порядок сообщений и идемпотентность через seq и client\_msg\_id на стороне history.
- ADR-4: Nginx на границе (TLS, маршрутизация, WebSocket, балансировка, limit\_req). Собственный Go-gateway не делаем.
- ADR-5: внешний API на REST и WebSocket с JSON.
- ADR-6: Docker Compose на VPS, без Kubernetes.
- ADR-7: JWT с подписью HS256 и общим секретом, проверка в общем Go-пакете.
- ADR-8: chat → history по gRPC (protobuf в /api/proto).
- ADR-9: интерфейс на Tailwind CSS и shadcn/ui. Дизайн-токены в Figma (цвета, радиусы, шрифты, отступы) совпадают с темой Tailwind, названия компонентов совпадают с названиями в shadcn/ui.

Каждое решение после обсуждения оформляем коротким файлом в /docs/adr.

## 12. Риски

- Бэкенд совмещает разработку и DevOps и становится узким местом. Мера: этап 4 вырезается первым, собственного gateway нет, группы отложены на этап 6.
- Фронтенд ждёт дизайнера. Мера: wireframes и дизайн-система готовы к концу этапа 0, макеты этапа 1 в первые дни этапа 1, до этого фронтенд работает на моках и базовых компонентах.
- Рассинхрон контрактов. Мера: правило из раздела 8 и моки на основе OpenAPI.
- Нагрузочные цифры окажутся ниже целевых. Мера: фиксируем фактические значения и объясняем узкие места, это тоже ценный результат.
- WebSocket через прокси ведёт себя неожиданно (таймауты). Мера: проверить в первые дни этапа 1.
- У QA нет стенда. Мера: staging к концу этапа 1.
- Сжатые сроки (вдвое меньше первого плана) оставляют мало запаса. Мера: этап 4 вырезается первым, группы и собственный gateway уже вне плана до показа.

## 13. Принятые решения

Решения приняты командой. Пересматриваем их только при новой информации.

- O-1: вход по username.
- O-2: chat → history по gRPC.
- O-3: подпись JWT HS256 с общим секретом из переменной окружения (не короче 32 байт). Переход на RS256 затронет только общий пакет проверки токенов и конфигурацию.
- O-4: фронтенд на React и TypeScript, стили на Tailwind CSS, компоненты на основе shadcn/ui (выбор дизайнера и фронтенда).
- O-5: staging и production на одном VPS (Selectel) в разных compose-проектах.
- O-6: язык интерфейса и документации: русский.
- O-7: собственный Go-gateway не делаем, вместо него Nginx.
- O-8: лицензия репозитория MIT.
- O-9 (открыт): дата показа руководителю практики. От неё зависит, сколько этапов войдёт в демо.
