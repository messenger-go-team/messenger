# Фикстуры для нагрузочных прогонов

Скрипт подготовки создаёт синтетические аккаунты и личные чаты через штатные Auth и History HTTP API. Подготовка выполняется отдельным процессом до запуска k6.

## Окружение

Используйте одноразовый локальный стенд с Auth и History либо отдельный тестовый стенд, согласованный с его владельцем. Перед запуском сверьте активную сборку, адрес API и назначение базы данных. Согласуйте объём, частоту запросов и уборку данных до подготовки. Продакшен и общий staging исключены из нагрузочных прогонов.

Скрипту требуется Node.js 24. Запускайте его из корня репозитория. Локальному HTTP разрешён только адрес `127.0.0.1`. Для согласованного изолированного HTTPS-стенда передайте точный origin в `--base-url` и `--allow-origin`. Используйте доверенный сертификат стенда и базовый адрес без пути, параметров и учётных данных. Редирект останавливает подготовку.

## Подготовка

```sh
node qa/k6/prepare-fixtures.cjs --base-url http://127.0.0.1:8085 --namespace t153_demo --pairs 2
```

Адрес в примере должен вести на реально запущенный локальный gateway. `--namespace` задаёт имя набора из 3–16 строчных латинских букв, цифр и подчёркиваний. Первый символ — буква или цифра. `--pairs` принимает от 1 до 1000. На каждую пару создаются два аккаунта вида `k6_<namespace>_<номер из четырёх цифр>_a` и `k6_<namespace>_<номер из четырёх цифр>_b` и один личный чат. Начните с небольшого набора, согласованного с владельцем стенда.

Регистрация, вход, сверка профилей и создание чатов выполняются последовательно. `--pace-ms` задаёт паузу между HTTP-запросами от 0 до 60 000 мс, по умолчанию 0. При `429` подготовка останавливается. Выдержите паузу по правилам стенда и повторите команду с тем же набором и допустимым темпом. Скрипт не повторяет запросы автоматически.

После частичного сбоя заново запустите подготовку с теми же адресом, namespace и числом пар. Случайные пароли остаются в локальном файле. На той же базе повторный запуск проверяет доступ к уже созданным аккаунтам и получает прежние ID аккаунтов и чатов. История чата сохраняется. Для замера с пустой историей используйте новый namespace или заново подготовленную изолированную базу.

Если подготовка была принудительно прервана и каталог `prepare.lock` остался, убедитесь, что процесс завершился. Удалите этот пустой каталог и оставшийся файл `run-*.tmp` в каталоге набора. Сохраните `credentials.json` для повтора.

## Передача в k6

Файлы набора находятся в игнорируемом каталоге `qa/k6/.local/k6_<namespace>/`.

- `credentials.json` хранит случайные пароли для повторной подготовки и обновления токенов.
- `run.json` хранит ID аккаунтов и чатов, исходный `lastSeq` каждого чата, access-токены и время их истечения. k6 читает файл на этапе инициализации. Пароли и refresh-cookie в него не записываются.

Укажите `K6_FIXTURE_FILE` как абсолютный путь к `run.json`, а `BASE_URL` как origin API, с которым подготовлен набор. Для сценария в `qa/k6` используйте импорт `import { fixturePairs } from './fixtures.js'`. Элемент массива содержит `chatId`, `lastSeq`, `a` и `b`. Поля аккаунта — `id`, `username`, `accessToken` и `expiresAt` в миллисекундах Unix. Подготовка и логины проходят до запуска k6, поэтому их задержки и запросы не входят в измерение переписки. [k6 SharedArray](https://grafana.com/docs/k6/latest/javascript-api/k6-data/sharedarray/)

Access-токен действует 900 секунд с момента выдачи. При планировании учитывайте самый ранний срок истечения в наборе. `K6_MIN_TOKEN_TTL_SECONDS` задаёт минимальный остаток срока на старте, по умолчанию 60 секунд. При истечении токена или слишком коротком остатке заново выполните подготовку перед замером. Для длительных прогонов и повторных подключений требования к сроку токенов уточняются в сценарии нагрузки. [T154](https://github.com/messenger-go-team/messenger/issues/154)

Файлы содержат секреты. На Unix применяются права `0600`. На Windows храните набор в каталоге приватного профиля с подходящим ACL. Не прикладывайте эти файлы к PR, CI-артефактам и отчётам. Для воспроизводимости сохраните в отчёте SHA стенда, namespace, число пар, темп подготовки и время начала замера.

## Очистка

1. Остановите k6 и закройте соединения тестовых аккаунтов.
2. Для одноразового Compose сверьте имя проекта и принадлежность томов. Выполните `docker compose -p <проект> -f <файл стенда> down --volumes` с теми же файлами Compose, что использовались при запуске. Удаление томов очищает всю базу этого проекта.
3. На согласованном стенде передайте оператору namespace и ID тестовых аккаунтов и чатов для уборки по правилам окружения. Публичные API удаления аккаунтов и личных чатов отсутствуют. Скрипт сброса набора T38 рассчитан на namespace `qa38_*`. [Сброс тестового чата T38](../staging.md#сброс-тестового-чата)
4. После уборки сервера удалите локальный каталог этого namespace, если набор больше не нужен.
