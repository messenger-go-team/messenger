## Когда и кто выполняет

QA или назначенный участник запускает этот список **после каждого деплоя приложения на staging**, после отката и повторной выкатки. Ответственный за выкат сначала подтверждает завершение миграций/деплоя и готовность сервисов, передаёт QA URL/версию веб-клиента с источником, URL REST/WSS и SHA backend-деплоя с источником, подтверждение их связки и перечень включённых функций. Проверяется внешний HTTPS/WSS через Nginx; локальные моки не заменяют этот прогон.

QA прикладывает результат с версиями frontend/backend к задаче/PR выката; первый прогон и подготовку стенда фиксирует в [#38](https://github.com/messenger-go-team/messenger/issues/38). Без отчёта выкат не считается проверенным QA. Это ручной шаг процесса: документ сам не запускает CI, smoke или rollback. На production использовать только заранее выделенные тестовые аккаунты/данные по принятому процессу, без staging reset.

## Предусловия и время

Подготовить **до старта таймера**:

- **Backend:** внешние HTTPS REST и WSS URL, ожидаемый и фактический SHA. Для выката через Actions источник — успешная запись GitHub Deployments/CD с URL, ID и SHA. Для ручного отката источник — запись оператора об откате с датой/временем и TZ, именем оператора, целевым SHA отката и фактическим SHA, подтверждённым на VPS, со ссылкой на доказательства сверки работающих образов Auth/Chat/History с активным снимком релиза/REVISION и маршрутизации Nginx. При откате ожидается целевой SHA отката; последняя запись GitHub Deployments может всё ещё относиться к более новому выкату Actions и не доказывает текущую версию. Если запись оператора или подтверждение фактического SHA недоступны, SMK-01 Blocked. Готовность сервисов подтверждена владельцем выката; порядок действий оператора — в [инструкции отката](../../deploy/staging-release.md#откат).
- **Веб-клиент:** отдельный HTTPS URL, ожидаемый и фактический frontend SHA/build ID, источник версии и способ связи с загруженными браузером файлами. Подходит manifest версии либо хеш загруженного bundle, сопоставленный с артефактом frontend-сборки и его SHA. Владелец frontend-выката передаёт QA ссылку на конкретный CI run и артефакт опубликованного dist, полный SHA сборки (включая merge SHA, если собирался merge ref), эталонный каталог SHA-256 файлов и подтверждение публикации именно этого dist. До таймера подготовить сверку по [процедуре версии веб-клиента](smoke-web-version.md); на старте и финише сравнить с файлами, реально загруженными A/B. Поле версии в UI не предполагается; SHA backend-деплоя и локальный git checkout не заменяют подтверждение веб-сборки. /app/version.json и /app/.vite/manifest.json, возвращающие HTML SPA, не являются источниками версии.
- **Связка:** ожидаемые REST/WSS адреса веб-сборки и подтверждённая маршрутизация на указанный backend-деплой (конфигурация/proxy и запись выката). Проверить фактические адреса в Network; WSS дополнительно сверить после входа в SMK-02. Для одного origin всё равно подтвердить backend за proxy. MSW/API/WS-моки отключены, ответы не подменяются локальной заглушкой. Нет доступного веб-клиента, источника его версии или подтверждения связки — SMK-01 Blocked.
- Согласованные браузер/ОС и scope сборки. Время развёртывания, создание пользователей, настройка доступа, проверка артефактов версии и seed — подготовка, не скрытые шаги smoke.
- Два тестовых аккаунта A/B с известными UUID/username, credentials из согласованного хранилища, две независимые браузерные сессии (отдельные профили). В начале обе сессии разлогинены; окна одного профиля с общей cookie не подходят.
- Заранее существующий личный чат AB с известным Chat.id и контрольным сообщением M0, сохранённым **до деплоя**, доступным в последней странице и прочитанным обоими. Все прежние сообщения AB уже прочитаны; никакие другие проверки/пользователи не пишут в этот чат во время smoke. Зафиксировать исходные ID/seq/текст M0 без секретов.
- Открытые инструменты Network/WS и способ быстро оборвать только соединение B: DevTools Offline, если он действительно разрывает сокет, либо подготовленный сетевой proxy/hook. Нужно подтвердить фактический разрыв WS, не только значок Offline; A остаётся online. В Network включить сохранение запросов и ответов; подготовить способ определить последний синхронизированный курсор AB в клиенте B (диагностика клиента либо завершённый history/recovery с сохранённым next_after_seq). Это не last_read_seq и не максимум seq из ack/new. Если разрыв или курсор нельзя подтвердить, SMK-07 — Blocked.

- Для SMK-10 основной путь — параллельное Network-наблюдение A/B; отдельная задача на debug-hook не требуется. Уже доступная read-only диагностика живого клиента остаётся альтернативой, но не условием начала прогона. Для Network определить максимальную задержку Dmax с jitter по исходникам/настройкам именно проверяемой веб-сборки. В [текущем backoff](../../web/src/ws/reconnect.ts) максимум базы 30 000 мс и jitter 20%: Dmax = 30 000 × 1,2 = 36 000 мс. Окно T = ceil(Dmax / 1000) + 2 секунды, то есть **38 секунд** при текущих настройках. Если настройки изменены, пересчитать T; не сокращать окно ради лимита smoke. Подготовить видимые, несвёрнутые окна A/B без заморозки вкладок и сохранение Network-log с временными отметками; сеть online, Offline/hooks из SMK-07 отключены. Если выполнение таймеров в окне наблюдения нельзя подтвердить (например, вкладка заморожена), использовать диагностику либо отметить Blocked.

**10 пунктов: план 9 минут 15 секунд + резерв 45 секунд = максимум 10 минут.** Это бюджет, а не измеренный результат. Границы замера:

1. До таймера заполнить постоянные поля полного отчёта: Run ID, исполнитель, браузер/ОС, URL, ожидаемые версии, ссылки на выкат/артефакт, аккаунты без credentials и M0. Подготовить эталонные хеши, средства сверки, Network и пустой короткий журнал из 10 строк. Проверку фактически загруженных файлов и активного backend для этого прогона заранее выполненной не считать.
2. Записать начало ISO 8601 с TZ и включить секундомер **перед открытием веб-клиента в SMK-01**. Внутри таймера выполнить все SMK-01…10: открытия страниц, вход, bootstrap/refresh, ожидание ответов, восстановление сети, догрузку, фиксацию S, наблюдение WS и параллельные не менее 38 секунд SMK-10, затем reload после logout. Никаких пауз секундомера при ожидании приложения. Во время каждого шага сразу отмечать ID, статус и краткий факт/ссылку на доказательство; обязательные ack/new, S/M3, L и окно t0/t1 фиксировать по месту, не восстанавливать из памяти.
3. После SMK-10, **не останавливая таймер**, повторно сверить обе активные версии и связку по свежим данным: файлы, загруженные браузерами A/B, с эталоном frontend, backend за REST/WSS proxy — с подтверждением оператора/активного релиза. В резерв 45 секунд входят эта подготовленная сверка и только короткое завершение журнала: проверить наличие 10 статусов, записать «версии/связка совпали» либо причину отказа, общий итог и причину Blocked/Not run, если есть. Сохранить время окончания и остановить секундомер после этой записи; вычислить длительность по началу/концу. Резерв нельзя продлевать за пределы 600 секунд.
4. **После остановки** развернуть короткий журнал в полный шаблон ниже, очистить доказательства от секретов, оформить баги и опубликовать отчёт. Подробное оформление в замер не входит; время этого оформления указать отдельно от начала/конца smoke. Оно не должно добавлять пропущенные проверки или менять Not run на Passed.

Если лимит исчерпан, прервать оставшиеся действия, отметить их Not run, итог не Passed; незавершённая финальная сверка также не допускает Passed. Уже найденный дефект сохраняет итог Failed. Полное окно наблюдения SMK-10 входит в его бюджет 75 секунд. На первом staging-прогоне записать фактическую длительность; план 555 + 45 секунд сам по себе критерий не подтверждает. Полная регрессия, нагрузка, намеренное ожидание истечения refresh-токена и подробный разбор багов выполняются отдельно. **Любой bootstrap/refresh, необходимый для шага smoke, целиком входит в таймер**, включая задержку T168.

Для полного MVP обязательны все 10 пунктов. Отсутствующая обязательная реализация/доступ/данные — Blocked, не Pass. N/A допустим только для заранее согласованной частичной сборки с основанием и владельцем; итог тогда «частичный smoke», а не полный Passed MVP. Вход, двусторонняя переписка и история обязательны всегда.

## Чек-лист

**Один прогон — одна неизменная пара версий frontend/backend.** От SMK-01 до остановки таймера отслеживать выкат/откат по заранее подготовленным источникам и наблюдать загруженную веб-сборку/связку. При обнаруженной смене любой версии немедленно прервать прогон: сохранить уже полученные результаты, время смены, прежнюю/новую версии и доказательства; оставшиеся пункты Not run, итог Blocked из-за смены сборки (если уже обнаружен дефект — Failed). Не объединять результаты до и после переключения, даже если затем вернули исходный SHA. После стабилизации стенда нужен новый полный smoke с новым Run ID. Перед Passed повторно подтвердить обе активные версии свежими данными тем же подготовленным способом: веб-сборку и её соответствие загруженным файлам A/B, фактический backend за REST/WSS proxy и их связку. Одной неизменной ссылки на старую запись Deployment недостаточно; при невозможности финальной сверки итог Blocked, не Passed.

Run ID: `smoke-<дата-время>-<короткий backend SHA>`. Метки новых сообщений: `M1=<run>-A`, `M2=<run>-B`, `M3=<run>-offline`. Каждый пункт выполнить один раз на этой сборке; результаты писать в отчёт, не проставлять галочки в исходном документе.

- [ ] **SMK-01 — Стенд и версии, 30 с.** Открыть подготовленный HTTPS URL веб-клиента; сверить ожидаемый и фактический frontend SHA/build ID с артефактом по [подготовленной процедуре](smoke-web-version.md), используя файлы, загруженные браузерами A/B именно сейчас. Отдельно сверить REST/WSS URL и backend SHA с подходящим источником: успешной записью Actions-деплоя либо записью оператора о ручном откате и подтверждением фактического SHA на VPS. После ручного отката сравнивать с целевым SHA отката, а не с последним Actions-деплоем. Подтвердить маршрутизацию этой веб-сборки на данный backend, сохранить выбранный источник и доказательства в отчёт. **Ожидается:** HTTPS без ошибки сертификата, приложение загрузилось без общего 5xx/белого экрана; подтверждены обе версии и их связка. Backend SHA сам по себе не доказывает frontend-версию. Недоступный веб-клиент или невозможность подтвердить любую версию/связку — Blocked.

- [ ] **SMK-02 — Вход двух пользователей, 60 с.** Войти A/B в отдельных контекстах; открыть профиль/GET /me каждого, проверить WS-соединения и фактические REST/WSS URL в Network относительно связки SMK-01. **Ожидается:** login 200, каждый видит свой username и список чатов; профиль 200 своего пользователя, refresh в cookie, WS подключён с выбранным messenger.v1. Credentials/полные токены в доказательства не копировать. Источник: AUTH-01, AUTH-06, AUTH-10, WS-01.

- [ ] **SMK-03 — Поиск и открытие AB, 45 с.** От A найти B по точному username и нажать «Написать» из поиска списка чатов; у B открыть AB. **Ожидается:** непустая выдача содержит именно B с исходным написанием/правильным ID; открыт прежний AB с тем же Chat.id, M0 доступно, второго чата нет. Если UI вызывает POST /chats/personal, для этой уже существующей пары ответ 200, не 201. Контакт добавлять не требуется. Источник: AUTH-11, CHAT-01, HIST-01.

- [ ] **SMK-04 — A → B, 60 с.** A впервые отправляет M1 с новым client_msg_id, коротким текстом и emoji; B действительно показывает его в активном чате. В WS Frames A/B найти события именно этой отправки. **Ожидается:** A обязательно получает серверный message.ack, сопоставленный с message.send по id/client_msg_id; B обязательно получает message.new. В обоих payload одинаковые message_id и seq, в message.new верные chat_id, автор и текст M1. Порядок ack/new свободный; у A sent, у B одна строка, без дублей. Sent по собственному message.new допустим для UI, но не заменяет обязательный ack этой штатной отправки: отсутствие ack при работающем наблюдении — Fail. Источник: FR-CHAT-3/4, CHAT-02, WS-06.

- [ ] **SMK-05 — B → A, 45 с.** B отвечает M2, A показывает ответ. **Ожидается:** отправка подтверждена у B, у A ответ один раз с правильным автором; seq M2 больше seq M1, строки не переставлены. delivered/read собеседнику не требуются в MVP. Источник: CHAT-02, MSG-04.

- [ ] **SMK-06 — История после перезагрузки, 60 с.** Перезагрузить страницу A и снова открыть AB; сверить REST-историю и UI. **Ожидается:** M0 пережило деплой, M1/M2 сохранились с прежними ID/seq/текстом и видны по одному, Chat.id прежний. Сам GET истории не отмечает прочтение; отдельный POST /read после реального показа допустим. Источник: HIST-01, HIST-02.

- [ ] **SMK-07 — Разрыв и автоматическая догрузка, 60 с.** У B уйти из AB в список чатов, через GET /chats проверить unread_count AB=0. До обрыва в Preserve log B найти последнюю полностью успешную автоматическую догрузку: GET /chats и цепочки GET /chats/{id}/messages?after_seq=… по всем чатам из ответа. Для AB взять S из next_after_seq последней страницы; при next_after_seq=null сохранить after_seq запроса этой страницы (для начальной пустой истории это 0). Дождаться окончания всей догрузки без ошибки, потому что клиент фиксирует курсоры после всего цикла, а не после одной страницы AB. Записать S, время, URL и ответ; обычный GET истории открытого чата, last_read_seq и max(seq) из WS не заменяют этот источник. Если последнего завершённого цикла не видно, дождаться очередного автоматического обновления при видимой вкладке B; это ожидание входит в SMK-07 и общий таймер. При отсутствии наблюдаемого завершения — Blocked, а не выдуманный S. Между фиксацией S и разрывом не должно завершиться другой догрузки; если завершилась, обновить S по ней. Оборвать WS B и подтвердить разрыв; A отправляет M3 и получает ack, B не получает live-событие M3. Восстановить сеть B, оставив его в списке: не открывать AB, не обновлять страницу и не запускать историю вручную. **Ожидается:** после reconnect B сам получает список чатов и отправляет GET /chats/{AB}/messages?after_seq=S&limit=100. В Network сравнить after_seq первого автоматического запроса AB после reconnect с записанным S (не с курсором прочтения); зафиксировать время reconnect, URL/инициатор запроса, 200 и ответ, содержащий M3 с прежними серверными ID/seq. Если страниц несколько, клиент использует next_after_seq до has_more_after=false; M3 входит в полученную историю ровно один раз. Всё это подтверждается до SMK-08 и до открытия AB: одно наличие M3 на сервере или его получение лишь при открытии чата не подтверждает recovery и означает Fail при доступном наблюдении. M0/M1/M2 и AB не потеряны. Если технически нельзя определить S или наблюдать Network/WS и разрыв — Blocked. При работающем наблюдении отсутствие автоматического запроса, неуспешный ответ или отсутствие M3 в завершённой догрузке — Fail; значок Offline не доказывает разрыв. Из offline B ничего не отправлять: terminal failed не проверяется. Источник: WS §8, REC-01, REC-04.

- [ ] **SMK-08 — Непрочитанное и показ, 45 с.** Пока B вне AB, получить unread_count; после зафиксированной автоматической догрузки SMK-07 открыть AB и действительно показать M3, проверить POST /chats/{chat_id}/read и новый GET /chats. **Ожидается:** M3 показано в UI ровно один раз с теми же ID/seq; загрузка при открытии AB не заменяет доказательство recovery в SMK-07. До показа unread_count ровно 1 (в SMK-07 было 0, после этого отправлено только M3); собственное M2 не увеличивает счётчик. Отметка последнего показанного seq даёт пустой 204, после показа всех чужих сообщений счётчик 0. Приватная отметка MVP не публикует message.read. Не объяснять неверное число неподготовленным старым счётчиком. Источник: HIST-03, FR-HIST-5.

- [ ] **SMK-09 — Личная запись Later, 75 с.** До действий A начать наблюдение за сырыми WS-сообщениями B и получить его личный GET /later. A сохраняет свежее M2 через «Просто сохранить»; зафиксировать ID L из ответа POST /later → 201. **Сразу после 201, пока L активна и до Done, выполнить GET /later в сессии B:** ожидать 200 и отсутствие именно записи с ID L; список B не обязан быть пустым. Только после этой проверки A открывает «Требует внимания», переходит из записи к M2 и нажимает «Готово». Наблюдение за WS B вести непрерывно от начала действий A до успешного Done включительно; после Done снова сверить GET /later B. **Ожидается:** новая пара (A,M2) создана с due_at=null/status=unscheduled, у A одна активная запись L. Запись L отсутствует у B и во время её активности, и после завершения; запросы только до Save и после Done не заменяют проверку активной записи. UI открывает правильную M2; свой размер context-окна не навязывается, допустим отсутствующий limit/default 50. Done → пустой 204, после обновления запись исчезла у A. B не получает запись/WS-события личных действий A ни на одном шаге. Ошибка записи, в том числе 503, не выдаётся за успех. Сроки и сам показ напоминаний — подробные кейсы T48 FR-LATER-1..5, здесь короткий путь без ожидания срока.

- [ ] **SMK-10 — Выход и отмена reconnect, 75 с.** Выйти из A/B. **В каждой сессии после ответа logout и до любой перезагрузки, закрытия вкладки или перехода, уничтожающего страницу,** проверить закрытие текущего WS и отмену автоматических переподключений. По умолчанию использовать описанный ниже Network-путь без отдельного debug-hook; готовая диагностика — допустимая альтернатива:
  - **Диагностика:** после logout в обоих живых клиентах зафиксировать остановленную сессию (`stopped=true` либо эквивалентный признак) и отсутствие активного/запланированного reconnect-таймера (`reconnectTimer=null` либо эквивалент). Сохранить время и доказательства. Ссылка на исходный `clearTimeout` или один факт закрытого WS не заменяют диагностику состояния работающей сборки; отдельное ожидание T не требуется только при подтверждённой отмене таймера и остановке сессии.
  - **Network:** наблюдать каждый профиль непрерывно с его logout. После того как оба logout вернули 204 и оба текущих WS закрылись, зафиксировать общий t0 и наблюдать оба профиля **не меньше T = 38 секунд** при текущем Dmax = 36 секунд, включая запас 2 секунды. Окна A/B остаются видимыми, страницы не перезагружать и не закрывать, сеть online; в Network не должно появиться ни одной новой попытки WS после соответствующего logout. Два окна наблюдаются параллельно, а не по 38 секунд последовательно. При иных настройках использовать T из предусловий. Сохранить t0, t1, фактическую длительность и Network-log обоих профилей. Новая попытка после logout, даже без успешного handshake, означает Fail. Если полный интервал не выдержан или наблюдение ненадёжно, Pass не ставить: Blocked при отсутствии наблюдаемости, Not run при исчерпании общего лимита.

  Затем отдельно обновить защищённые страницы и проверить требование входа. **Ожидается:** logout с действующей refresh cookie → пустой 204, cookie удалена, локальная сессия очищена; оба WS закрылись именно при logout, таймер reconnect отменён либо весь применимый интервал прошёл без попыток. После обновления UI предлагает вход и не показывает прежнюю переписку другой сессии. Перезагрузка не служит доказательством отмены reconnect. Подготовленное наблюдение, его полный интервал, обновление страниц и запись результата входят в общий замер smoke; превышение 10 минут не допускает Passed. Немедленный серверный отзыв уже выданного access не требуется в MVP. Источник: AUTH-09, REC-04, [backoff](../../web/src/ws/reconnect.ts), [отмена таймера](../../web/src/ws/client.ts).

## Итог, дефекты и повтор

- **Passed:** все 10 пунктов пройдены на одной неизменной паре версий frontend/backend за время не больше 10 минут; перед итогом обе активные версии и их связка повторно подтверждены свежими данными, совпадают с SMK-01 и загруженной веб-сборкой A/B; смены версий во время прогона не было. Нет Blocked/Not run/N/A. Финальная сверка включена в длительность.
- **Failed:** есть несовпадение с ожидаемым, даже если остальные пункты зелёные.
- **Blocked:** нет необходимых условий/реализации, нельзя подтвердить frontend/backend или их связку на старте/финише либо во время прогона сменилась любая версия; это не успешный smoke.
- **Not run:** пункт не выполнен. При превышении лимита и отсутствии уже обнаруженного дефекта итог «Not run — не завершён за лимит», не Passed. Для согласованного неполного scope — «частичный smoke» с причинами N/A, без заявления готовности MVP.

При ошибке записать ID, действие, фактический ответ/код и версии frontend/backend; сохранить доказательства без credentials, оформить дефект по [шаблону](../../.github/ISSUE_TEMPLATE/bug.yml) с bug и подходящей [severity](../../.github/severity-labels.json). Потеря подтверждённых сообщений/чужие данные — Critical; недоступность основного пути, дубли сохранения и существенное нарушение порядка — High. Действует [релизный критерий тест-плана](test-plan.md): QA даёт рекомендацию, владелец выката принимает и фиксирует решение; обходной путь не превращает Failed в Passed.

При невозможности входа/обмена или проблеме с данными остановить зависимые действия, отметить их Not run с причиной. Не тратить лимит на полный разбор бага. После исправления/отката — ретест дефекта и **новый полный smoke** с новым run ID с подтверждёнными версиями frontend/backend, сохранив старый неуспешный отчёт. Сбросом данных не маскировать потерю/дубли.
