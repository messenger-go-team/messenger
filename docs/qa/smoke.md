# T51: smoke после каждого деплоя

Задача: [#51](https://github.com/messenger-go-team/messenger/issues/51). Зависимость: [T48](https://github.com/messenger-go-team/messenger/issues/48), [PR #108](https://github.com/messenger-go-team/messenger/pull/108). Источники: [тест-план](test-plan.md), [SPEC](../SPEC.md), [базовые кейсы](test-cases/proposed-tests.md), [auth](../../api/openapi/auth.yaml), [history](../../api/openapi/history.yaml), [WS](../../api/ws/events.md).

Обновлено 18 ноября 2026 по main `a5099fb`. **Статус: Not run — подготовлен документ; реальный smoke и замер времени на staging не выполнены.** T48 ещё проходит ревью: перед приёмкой T51 перенести относящиеся к smoke замечания принятого набора. Ссылки на новые, ещё не смерженные файлы T48 не используются.

## Когда и кто выполняет

QA или назначенный участник запускает этот список **после каждого деплоя приложения на staging**, после отката и повторной выкатки. Ответственный за выкат сначала подтверждает завершение миграций/деплоя и готовность сервисов, передаёт QA URL, SHA и перечень включённых функций. Проверяется внешний HTTPS/WSS через Nginx; локальные моки не заменяют этот прогон.

QA прикладывает результат с SHA к задаче/PR выката; первый прогон и подготовку стенда фиксирует в [#38](https://github.com/messenger-go-team/messenger/issues/38). Без отчёта выкат не считается проверенным QA. Это ручной шаг процесса: документ сам не запускает CI, smoke или rollback. На production использовать только заранее выделенные тестовые аккаунты/данные по принятому процессу, без staging reset.

## Предусловия и время

Подготовить **до старта таймера**:

- HTTPS URL и ожидаемый SHA из результата деплоя, рабочий стенд auth/history/chat и веб-клиент; согласованные браузер/ОС и scope сборки. Время развёртывания, создание пользователей, настройка доступа и seed — подготовка, не скрытые шаги smoke.
- Два тестовых аккаунта A/B с известными UUID/username, credentials из согласованного хранилища, две независимые браузерные сессии (отдельные профили). В начале обе сессии разлогинены; окна одного профиля с общей cookie не подходят.
- Заранее существующий личный чат AB с известным Chat.id и контрольным сообщением M0, сохранённым **до деплоя**, доступным в последней странице и прочитанным обоими. Все прежние сообщения AB уже прочитаны; никакие другие проверки/пользователи не пишут в этот чат во время smoke. Зафиксировать исходные ID/seq/текст M0 без секретов.
- Открытые инструменты Network/WS и способ быстро оборвать только соединение B: DevTools Offline, если он действительно разрывает сокет, либо подготовленный сетевой proxy/hook. Нужно подтвердить фактический разрыв WS, не только значок Offline; A остаётся online. Если разрыв нельзя организовать/наблюдать, SMK-07 — Blocked.

**10 пунктов: план 8 минут 30 секунд + резерв 1 минута 30 секунд = максимум 10 минут.** Засечь время от открытия стенда SMK-01 до краткого отчёта после SMK-10. Это плановый бюджет, не измеренная длительность: на первом staging-прогоне записать фактическое время. Если лимит превышен, оставшиеся пункты Not run, итог не Passed; пересмотреть объём до следующего выката. Полная регрессия, нагрузка, длительное ожидание refresh и разбор багов за пределами smoke.

Для полного MVP обязательны все 10 пунктов. Отсутствующая обязательная реализация/доступ/данные — Blocked, не Pass. N/A допустим только для заранее согласованной частичной сборки с основанием и владельцем; итог тогда «частичный smoke», а не полный Passed MVP. Вход, двусторонняя переписка и история обязательны всегда.

## Чек-лист

Run ID: `smoke-<дата-время>-<короткий SHA>`. Метки новых сообщений: `M1=<run>-A`, `M2=<run>-B`, `M3=<run>-offline`. Каждый пункт выполнить один раз на этой сборке; результаты писать в отчёт, не проставлять галочки в исходном документе.

- [ ] **SMK-01 — Стенд и версия, 30 с.** Открыть URL, сверить домен и ожидаемый SHA с результатом деплоя (наличие версии в UI не предполагается). **Ожидается:** HTTPS без ошибки сертификата, приложение загрузилось без общего 5xx/белого экрана, проверяется нужная сборка. Нельзя подтвердить URL/SHA — Blocked, не проверка ожидаемого выката.

- [ ] **SMK-02 — Вход двух пользователей, 60 с.** Войти A/B в отдельных контекстах; открыть профиль/GET /me каждого, проверить WS-соединения. **Ожидается:** login 200, каждый видит свой username и список чатов; профиль 200 своего пользователя, refresh в cookie, WS подключён с выбранным messenger.v1. Credentials/полные токены в доказательства не копировать. Источник: AUTH-01, AUTH-06, AUTH-10, WS-01.

- [ ] **SMK-03 — Поиск и открытие AB, 45 с.** От A найти B по точному username и нажать «Написать» из поиска списка чатов; у B открыть AB. **Ожидается:** непустая выдача содержит именно B с исходным написанием/правильным ID; открыт прежний AB с тем же Chat.id, M0 доступно, второго чата нет. Если UI вызывает POST /chats/personal, для этой уже существующей пары ответ 200, не 201. Контакт добавлять не требуется. Источник: AUTH-11, CHAT-01, HIST-01.

- [ ] **SMK-04 — A → B, 60 с.** A отправляет M1 с коротким текстом и emoji; B действительно показывает его в активном чате. **Ожидается:** у A sent по ack или соответствующему собственному new; B получает одну строку с правильными автором/текстом. В штатном потоке ack отправителю и new участникам относятся к тем же message_id/seq; относительный порядок ack/new не фиксируется, получение обоих не создаёт дубля. Источник: CHAT-02, WS-06.

- [ ] **SMK-05 — B → A, 45 с.** B отвечает M2, A показывает ответ. **Ожидается:** отправка подтверждена у B, у A ответ один раз с правильным автором; seq M2 больше seq M1, строки не переставлены. delivered/read собеседнику не требуются в MVP. Источник: CHAT-02, MSG-04.

- [ ] **SMK-06 — История после перезагрузки, 60 с.** Перезагрузить страницу A и снова открыть AB; сверить REST-историю и UI. **Ожидается:** M0 пережило деплой, M1/M2 сохранились с прежними ID/seq/текстом и видны по одному, Chat.id прежний. Сам GET истории не отмечает прочтение; отдельный POST /read после реального показа допустим. Источник: HIST-01, HIST-02.

- [ ] **SMK-07 — Разрыв и догрузка, 60 с.** У B после показа M1 уйти из AB в список чатов, через GET /chats проверить unread_count AB=0. Оборвать WS B и подтвердить разрыв; A отправляет M3 и получает подтверждение, пока B не получает live-событие. Восстановить сеть B, оставив его в списке, дождаться reconnect/синхронизации. **Ожидается:** состояние подключения понятно, M3 догружено после восстановления и присутствует в REST-истории ровно один раз; M0/M1/M2 и AB не потеряны. Наблюдение только значка Offline без разрыва не подтверждает recovery. Из offline B ничего не отправлять: terminal failed не проверяется. Источник: REC-01, REC-04.

- [ ] **SMK-08 — Непрочитанное и показ, 45 с.** Пока B вне AB, получить unread_count; затем открыть AB и действительно показать M3, проверить POST /chats/{chat_id}/read и новый GET /chats. **Ожидается:** до показа ровно 1 (в SMK-07 было 0, после этого отправлено только M3); собственное M2 не увеличивает счётчик. Отметка последнего показанного seq даёт пустой 204, после показа всех чужих сообщений счётчик 0. Приватная отметка MVP не публикует message.read. Не объяснять неверное число неподготовленным старым счётчиком. Источник: HIST-03, FR-HIST-5.

- [ ] **SMK-09 — Личная запись Later, 75 с.** До действий A наблюдать сырые WS-сообщения B и его личный GET /later. A сохраняет свежее M2 через «Просто сохранить», открывает «Требует внимания», переходит из записи к M2, нажимает «Готово». **Ожидается:** POST /later для новой пары (A,M2) → 201 с due_at=null/status=unscheduled, у A одна активная запись. UI открывает правильную M2; свой размер context-окна не навязывается, допустим отсутствующий limit/default 50. Done → пустой 204, после обновления запись исчезла. B не получает запись/WS-события личных действий A. Ошибка записи, в том числе 503, не выдаётся за успех. Сроки и сам показ напоминаний — подробные кейсы T48 FR-LATER-1..5, здесь короткий путь без ожидания срока.

- [ ] **SMK-10 — Выход, 30 с.** Выйти из A/B, обновить защищённую страницу. **Ожидается:** logout с действующей refresh cookie → пустой 204, cookie удалена; локальная сессия очищена, WS закрыты и reconnect остановлен. UI предлагает вход, не показывает прежнюю переписку другой сессии. Немедленный серверный отзыв уже выданного access не требуется в MVP. Источник: AUTH-09, REC-04.

## Итог, дефекты и повтор

- **Passed:** все 10 пунктов пройдены на указанном SHA за время не больше 10 минут; нет Blocked/Not run/N/A.
- **Failed:** есть несовпадение с ожидаемым, даже если остальные пункты зелёные.
- **Blocked:** нет необходимых условий/реализации или нельзя подтвердить сборку; это не успешный smoke.
- **Not run:** пункт не выполнен. При превышении лимита и отсутствии уже обнаруженного дефекта итог «Not run — не завершён за лимит», не Passed. Для согласованного неполного scope — «частичный smoke» с причинами N/A, без заявления готовности MVP.

При ошибке записать ID, действие, фактический ответ/код и SHA; сохранить доказательства без credentials, оформить дефект по [шаблону](../../.github/ISSUE_TEMPLATE/bug.yml) с bug и подходящей [severity](../../.github/severity-labels.json). Потеря подтверждённых сообщений/чужие данные — Critical; недоступность основного пути, дубли сохранения и существенное нарушение порядка — High. Действует [релизный критерий тест-плана](test-plan.md): QA даёт рекомендацию, владелец выката принимает и фиксирует решение; обходной путь не превращает Failed в Passed.

При невозможности входа/обмена или проблеме с данными остановить зависимые действия, отметить их Not run с причиной. Не тратить лимит на полный разбор бага. После исправления/отката — ретест дефекта и **новый полный smoke** с новым run ID на фактическом SHA, сохранив старый неуспешный отчёт. Сбросом данных не маскировать потерю/дубли.

Краткий отчёт прикладывать после каждого выката, включая неуспешный. Время — с часовым поясом; Not run заменить только после выполнения:

```text
Начало/конец: <ISO 8601 с TZ>; длительность: <мин:сек>
SMK-01: Not run
SMK-02: Not run
SMK-03: Not run
SMK-04: Not run
SMK-05: Not run
SMK-06: Not run
SMK-07: Not run

SMK-09: Not run
SMK-10: Not run
Итог: <Passed/Failed/Blocked/Not run/частичный smoke>

```

После прогона выключить Offline/hooks и закрыть дополнительные контексты. Тестовые сообщения сохранить до окончания разбора, личные smoke-записи завершить; не сбрасывать общий стенд или production. Регистрация, границы/негативные запросы, полная пагинация, refresh-гонки, пресеты/напоминания Later и три раскладки остаются в T48. С этапа 2 ручной прогон дополняется 3–5 Playwright smoke-сценариями по тест-плану; их реализация не входит в T51.
