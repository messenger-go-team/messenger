# T49: API-тесты Auth и History

Коллекция Bruno проверяет действующие [Auth OpenAPI](../../../api/openapi/auth.yaml) и [History OpenAPI](../../../api/openapi/history.yaml) на настоящих сервисах из текущего checkout. Задача: [#49](https://github.com/messenger-go-team/messenger/issues/49). Стратегия: [тест-план](../test-plan.md).

## Запуск

Нужны Docker с Linux containers и Compose v2, Node.js 24.16.0, npm 11.13.0. Выполнять из корня репозитория:

```sh
npm --prefix docs/qa/api-tests ci --ignore-scripts
npm --prefix docs/qa/api-tests audit --audit-level=moderate
npm --prefix docs/qa/api-tests run check
npm --prefix docs/qa/api-tests run compose
npm --prefix docs/qa/api-tests run check:reports
```

На Windows сначала запустить Docker Desktop. Go устанавливать на хост для этих команд не требуется: мигратор и fixture собираются внутри Docker. Первый запуск скачивает образы и Go/npm-зависимости. Повторные запуски используют build cache.

`compose` создаёт проект с уникальным именем, собирает Auth, History и тестовый образ, создаёт две пустые БД, применяет миграции, назначает runtime-права, запускает HTTPS gateway и ждёт readiness. Затем выполняет два независимых прогона с пересозданием данных: позитивный и контроль схемы. В `finally` удаляет только контейнеры, сеть и том сертификатов собственного проекта. БД находится в tmpfs. Не запускать два прогона одновременно в одном checkout: каталог отчётов общий. При принудительном завершении процесса проверить оставшиеся проекты `docker compose ls`; удалять только относящийся к этому запуску проект `qa49-…`.

Стенд не публикует порты на хост. Произвольный `BASE_URL`, staging и production не поддерживаются. URL заданы внутри стенда и проверяются pre-request helper. Внешние proxy-переменные для Bruno сбрасываются. Docker и npm обращаются к реестрам для установки зависимостей.

## Что проверяется

В коллекции 205 упорядоченных запроса, каждый содержит три проверки: HTTP status, JSON-схема ответа по OpenAPI и дополнительные инварианты сценария. `check` автоматически сверяет наличие успешного запроса для каждой операции и каждого объявленного статуса ответа обоих контрактов. Покрытие операций не означает процент покрытия кода или всех комбинаций ошибок.

- Auth: регистрация и валидация полей, дубликат имени без учёта регистра, вход, одинаковые публичные `code`/`message` для неверного пароля и отсутствующего аккаунта, `/me`, отсутствующий/невалидный/просроченный JWT.
- Refresh и logout: настоящий cookie jar на HTTPS, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/auth`, ротация, отказ для прежнего refresh, успешное использование нового, удаление cookie и отказ после logout. Access JWT передаётся между запросами; refresh не ожидается в JSON. Ротация проверяется по refresh-cookie и отказу для прежнего refresh: access JWT, выданные в одну секунду, могут совпадать и не обязаны различаться.
- Контакты: пустой и собственный список, отсутствие обратного добавления, сортировка, PUT/DELETE с пустым 204 и повторами, 401/404/422, self PUT 422 и self DELETE 204. Последующие history-запросы подтверждают сохранение переписки после удаления контакта.
- Поиск: `ALICE`/`alice` находят `Alice_1` с исходным написанием и исключают `Malice_1`; одна и 32 буквы, 21 подходящий пользователь для проверки лимита 20, отсутствие результата, некорректный prefix и 401.
- Внутреннее получение пользователя: service token, минимальный ответ, ошибки, недоступность internal-маршрута через внешний gateway. Для последнего проверяется транспортный 404; HTML-ответ gateway не выдаётся за JSON по OpenAPI Auth.
- Личные чаты: создание 201, повтор в обратном направлении 200 с тем же ID, ошибки и изоляция списков.
- История: 205 сохранённых сообщений, последние 50, `after_seq=0` и три страницы с передачей `next_after_seq` в следующий запрос до `has_more_after=false`, `before_seq`, пустая страница, порядок `seq`, ошибки курсоров и доступа.
- Непрочитанные: собственное сообщение исключается, обычный GET истории счётчик не меняет; POST/read возвращает пустой 204; seq=0, частичная и полная отметка, повтор и старый курсор, неверный/слишком большой seq, 401/403/404/422, изоляция участников и чатов.
- «Вернуться позже»: все четыре операции, unscheduled/scheduled/due, повторное сохранение без дубля, перенос, Done и повтор, повторное создание, приватность владельца, ошибки query/времени/доступа. Неизвестные и некорректно закодированные query проверяются на всех четырёх операциях. Потеря доступа, удаление сообщения/чата исключают запись из списка и дают 404 при обращении.
- Контекст: старая цель вне последней страницы, limit=1/3/100 через API, границы истории, курсоры и присутствие цели, несоответствие пары chat/message, ошибки и недоступная цель.
- Сбой хранилища: контролируемый 503 для списка Later, трёх операций записи и основных history-запросов; после восстановления проверяется, что неуспешные операции Later не подтвердили и не изменили запись.

UI, WebSocket, гонки вкладок и нагрузка проверяются отдельно по T48/T51 и плану этапов. API-контекст не фиксирует размер окна, который должен выбирать UI.

## Схемы, порядок и отчёты

`collection/plan.cjs` задаёт порядок, маршрут OpenAPI, ожидаемый статус и проверки сценариев. `generate.cjs` создаёт `.bru`; после правок плана выполнить `npm --prefix docs/qa/api-tests run generate`. `check` отклоняет устаревшие сгенерированные файлы, повторные ID и непокрытые операции.

`collection/schema.cjs` читает YAML непосредственно из `api/openapi`, использует Ajv 2020 и ajv-formats, разрешает локальные `$ref`, проверяет required/additionalProperties, форматы UUID/date-time и безопасные целые int64. Для JSON проверяется Content-Type; для 204 — полностью пустое тело. Примеры OpenAPI не копируются в отдельные схемы. Контрольные валидный/невалидные ответы проверяются ещё до старта сервисов.

Второй прогон меняет только копию успешного ответа AUTH-LOGIN в проверке схемы: `expires_in` становится строкой. Серверный ответ и остальные проверки остаются исходными. Ожидается exit code 1, **ровно одна** ошибка `AUTH-LOGIN OpenAPI` с указанием `expires_in`, 614 остальных проверок успешны. Отсутствующий отчёт, ошибка запроса/загрузки, неверный статус, пропуск проверки или любое другое падение не принимаются как ожидаемое. Успех `compose` означает, что оба отчёта прошли эту проверку. `check:reports` дополнительно повреждает копии настоящих отчётов и проверяет их отклонение.

Результаты сохраняются в игнорируемом `reports/public/`: `positive` и `negative`, JSON, JUnit XML, log и summary. Публикуются только они. Тела и заголовки исключены из отчётов Bruno, JWT/refresh/известные тестовые secrets дополнительно редактируются. Временные raw-отчёты и fixture с токенами удаляются в `finally`. При сбое setup отчёта успешного прогона не будет.

## Тестовые данные и границы доступа

`fixture/main.go` — утилита стенда, не публичный endpoint. Она создаёт пользователей/чаты через реальные REST API, а сообщения — через настоящий History gRPC SaveMessage; сохранение не подменено SQL-вставкой. Отдельные фиксированные SQL-команды сбрасывают только тестовые БД, моделируют утрату доступа/удаление и временно переименовывают таблицы для проверки 503. Утилита отклоняет DSN с hostname или именем БД вне `postgres/api_auth` и `postgres/api_history`.

Auth и History работают под отдельными runtime-ролями без superuser и владения таблицами. Административные credentials получает только init/fixture. Все пароли и JWT/internal secrets в compose — заведомо тестовые, предназначены исключительно для заново созданных БД; настоящие credentials не требуются. Auth и History не получают общую административную строку подключения.

Gateway использует свежий локальный CA и сертификат с SAN `gateway`; Go и Node/Bruno проверяют цепочку сертификатов. Отключение TLS-проверки не используется. Корневой init нужен для прав тома, каталога reports/public и закрытого ключа; каталог отчётов доступен UID тестов и при исходных правах 0755 на Linux. Тесты работают под UID 65532. Developer sandbox Bruno нужен для локальных helper-модулей; он исполняет доверенный код репозитория и не является изоляцией от вредоносного PR. Workflow не использует secrets и `pull_request_target`.

## CI и зависимости

Workflow [api-contract-tests.yml](../../../.github/workflows/api-contract-tests.yml) запускает audit, сверку схем/коллекции, проверки совместимости, оба Compose-прогона и контроль валидатора отчётов на pull_request/main и push/main. Артефакты — только `reports/public/`, срок хранения 7 дней. Результат GitHub Actions подтверждается после push; локальная проверка не означает, что удалённый CI уже прошёл.

Bruno CLI 4.3.0 используется в отдельном npm-профиле с lock-файлом и проверенными для этой HTTP-коллекции overrides. Подробности и ограничения — [dependency-review.md](dependency-review.md). Исторический профиль `qa/tool-trials` из T24 этим изменением не обновляется и не получает разрешения работать с внешними credentials.
