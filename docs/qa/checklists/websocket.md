# WebSocket v1: контрактный чек-лист

Основание: [events.md](../../../api/ws/events.md) §2–13, [history.yaml](../../../api/openapi/history.yaml), SPEC FR-CHAT-2..7, FR-WEB-3..5. [Правила, окружения и данные](README.md). Проверки до реализации можно выполнять на моках, но commit, права и дедупликацию БД ими не подтверждаем.

## Подключение и авторизация — MVP

- [ ] WS-CL-001 [P0] Разрешённый Origin, messenger.v1 и ровно один bearer.<access JWT> → HTTP 101, выбран только messenger.v1; socket.protocol=messenger.v1, JWT в ответе отсутствует.
- [ ] WS-CL-002 [P0] Отсутствующий/невалидный/истёкший JWT, подмена подписи, неверный алгоритм, отсутствующие или некорректные sub/iat/exp, несколько bearer → HTTP 401 до Upgrade; от chat — JSON code=unauthorized и WWW-Authenticate: Bearer.
- [ ] WS-CL-003 [P1] Нет messenger.v1/некорректный Upgrade → 400 invalid_handshake; неизвестный, отсутствующий или null Origin → 403 origin_not_allowed. Коды смотреть протокольным клиентом; браузер не читает тело неуспешного handshake.
- [ ] WS-CL-004 [P1] Сервис не готов/останавливается → 503; при включённом ограничении подключений → 429. Не требовать тело chat от отказа, сформированного Nginx.
- [ ] WS-CL-005 [P0] Истечение exp открытого соединения → close 4401; новые команды не принимаются. Начатый commit может завершиться: отсутствие ack не доказывает отсутствие записи.
- [ ] WS-CL-006 [P1] После истечения клиент делает REST refresh и новый handshake; не обновляет JWT внутри WS, не передаёт refresh в событиях/URL. Вкладки координируют refresh, нет бесконечного refresh-loop.
- [ ] WS-CL-007 [P0] JWT/credential-заголовки не попадают в URL, логи, трассировки, Close reason и отчёты. После logout клиент закрывает сокеты и не переподключается.

## Конверт и ограничения — MVP

- [ ] WS-CL-008 [P1] Один text message содержит один JSON-объект с обязательными type/id/ts/payload; UUID и RFC3339 UTC корректны. Отсутствующие/неверные поля и неизвестные C→S поля → invalid_payload, retryable=false.
- [ ] WS-CL-009 [P1] Невалидный JSON, массив и несколько JSON подряд → invalid_json; request_type/client_msg_id=null. Невалидный/отсутствующий id → новый серверный error.id; при валидном id разобранной команды error копирует его.
- [ ] WS-CL-010 [P1] Неизвестный C→S тип, неверное направление (клиент посылает ack/new) и команды этапа 2 в MVP → unsupported_type, retryable=false. Следующая валидная команда всё ещё работает.
- [ ] WS-CL-011 [P1] Дополнительные поля/неизвестные типы S→C клиент игнорирует без разрыва. Клиентский ts не влияет на права, порядок, TTL или серверное created_at.
- [ ] WS-CL-012 [P1] body длиной 1/4096 Unicode code points принимается, 0/4097 и только Unicode White_Space → invalid_payload; emoji/комбинируемые символы считаются code points, не байтами/UTF-16 units. Проверять также общий лимит message.
- [ ] WS-CL-013 [P0] Декодированный U+0000 в body → invalid_payload, retryable=false до History: нет записи, ack/new и изменения last_seq; следующая валидная команда работает. Буквальная последовательность `\u0000` сохраняется без преобразования в нулевой символ.
- [ ] WS-CL-014 [P1] Пробелы вокруг текста, переносы строк, исходная Unicode-последовательность сохраняются без trim/нормализации. HTML/скрипт показываются как plain text, не выполняются.
- [ ] WS-CL-015 [P1] JSON-message ровно 65536 байт допустим при валидном payload; 65537 → close 1009 без автоповтора. Размер измеряется в UTF-8 после сборки frames, с конвертом и escaping; проверить фрагментированные text frames. Для границы размера дополнять валидный JSON разрешёнными JSON-пробелами вне body, не нарушая отдельный предел 4096 code points.
- [ ] WS-CL-016 [P1] Binary → close 1003, невалидный UTF-8 → 1007; compression не согласуется в v1. Для превышения размера/UTF-8 не требовать error перед Close.

## Отправка, ack/new и идемпотентность — MVP

- [ ] WS-CL-017 [P0] Валидный send от A в AB → ack только отправившему соединению после commit в PostgreSQL через History; ack.id равен id попытки, payload содержит chat_id/client_msg_id/message_id/seq/created_at, состояние sent, не delivered/read.
- [ ] WS-CL-018 [P0] Все активные соединения A и B получают new, включая вкладку отправителя; C не получает событие. message_id/seq/created_at совпадают с ack, sender_id взят из JWT, body совпадает с сохранённым.
- [ ] WS-CL-019 [P0] Варианты ack→new и new→ack, повторная рассылка new и повтор ack → в UI одно сообщение; собственный pending сопоставляется по (chat_id,sender_id,client_msg_id), сохранённое — по message_id или (chat_id,seq).
- [ ] WS-CL-020 [P0] Чат C/несуществующий чат при валидном UUID → forbidden, retryable=false без раскрытия существования; повтор тоже проверяет участие. Подмена sender_id/seq/message_id/created_at в C→S payload → invalid_payload, автор не меняется.
- [ ] WS-CL-021 [P0] Повторные/конкурентные send с одним (chat_id,sender_id,client_msg_id) и тем же body → одна запись, один seq и исходные пять полей ack; id/ts ack относятся к текущей попытке. Повтор после нового сокета не обходит дедупликацию.
- [ ] WS-CL-022 [P0] Тот же ключ с другим body → idempotency_conflict, retryable=false; исходная запись неизменна. Изменение текста пользователем создаёт новый client_msg_id.
- [ ] WS-CL-023 [P1] Один client_msg_id у другого отправителя или в другом доступном чате не объединяет независимые записи: ключ включает chat_id и sender_id. Не требовать повторного new при идемпотентном повторе.
- [ ] WS-CL-024 [P0] Seq — безопасное целое в 1..9007199254740991, монотонно внутри чата; не сравнивается между чатами. Перестановка событий/разные ts не нарушают сортировку по seq, числовая непрерывность не обязательна.

## Ошибки, потеря подтверждений и повтор — MVP

- [ ] WS-CL-025 [P0] Подавить для отправителя **и ack, и соответствующий собственный new**, до контрольной точки исключить подтверждение через history. После начального таймаута ack 10 с клиент повторяет с backoff, прежними chat_id/client_msg_id/body и новым id попытки, без параллельных повторов одного сообщения. Таймаут сам по себе не означает failed.
- [ ] WS-CL-026 [P0] Потерян ack, но получен собственный new → pending сопоставлен с сохранённым сообщением, дубля и ложного failed нет; подтверждённое сообщение не остаётся в очереди повторов.
- [ ] WS-CL-027 [P0] Разрыв после commit до ack/new → запись остаётся в БД; после reconnect REST может уже вернуть её без client_msg_id. Повтор с исходным ключом даёт ack с исходным message_id: pending объединяется с REST-записью по ack.message_id=REST.id, в UI одна строка.
- [ ] WS-CL-028 [P1] temporarily_unavailable/internal_error и rate_limited при включённом лимите → retryable=true, повтор с backoff и исходным ключом; неизвестный исход сохранения не приводит к созданию нового логического сообщения.
- [ ] WS-CL-029 [P1] invalid_json/invalid_payload/unsupported_type/forbidden/idempotency_conflict → retryable=false, без автоматического повтора до исправления причины; error содержит code/message/retryable/request_type/client_msg_id по §9, без SQL, stack trace или чужих данных.
- [ ] WS-CL-030 [P1; Blocked до согласования] Terminal failed и ручной повтор проверять только после фиксации лимита попыток или общего времени, поведения офлайн и позднего ack/new. После согласования ручной повтор сохраняет client_msg_id; сам failed не доказывает отсутствие записи. Не придумывать лимит по таймауту ack.

## Переподключение и синхронизация history — MVP

- [ ] WS-CL-031 [P1] При потере сети/1001/1011/1013 reconnect: 1,2,4,8,16, затем максимум 30 с с jitter ±20%; после 30 с стабильной работы задержка сбрасывается. После собственного logout reconnect выключен.
- [ ] WS-CL-032 [P0] После открытия сокета клиент буферизует new и запрашивает свежий список чатов, включая новый чат во время разрыва. Для нового чата after_seq=0, для известного — последний синхронизированный курсор.
- [ ] WS-CL-033 [P0] История догружается несколькими страницами limit=100: ближайшие seq>after_seq по возрастанию, следующий after_seq=next_after_seq; завершение при has_more_after=false. Буфер WS и REST объединяются без дублей.
- [ ] WS-CL-034 [P0] При пришедшем new seq=44 до загрузки seq=43 курсор не перескакивает на max увиденного ack/new. Недоступность history не продвигает курсор; числовые пропуски не заставляют ждать несуществующий seq бесконечно.
- [ ] WS-CL-035 [P1] После возврата вкладки на передний план и периодически (начально 30 с для активной вкладки) выполняется синхронизация: потерянный pub/sub при живом сокете восстанавливается из history. WS не является постоянной офлайн-очередью.

## Heartbeat и транспорт — MVP

- [ ] WS-CL-036 [P1] Сервер шлёт control Ping каждые 25 с, ждёт соответствующий Pong не больше 10 с; браузер отвечает протоколом, JSON pong не нужен. При потере Pong транспорт освобождается, Close может не дойти.
- [ ] WS-CL-037 [P1] Начальный write timeout 10 с; медленный клиент с переполнением ограниченной очереди закрывается 1013 и восстанавливает данные через history. Через Nginx соединение держится дольше минуты; начальный proxy_read_timeout 75 с.
- [ ] WS-CL-038 [P1] Нормальное закрытие 1000, shutdown 1001, ошибка протокола 1002 обрабатываются по §13; наблюдаемый 1006 при обрыве никогда не отправляется как Close frame. Graceful shutdown не отменяет сохранённые сообщения.

## Только этап 2 — не критерии MVP

- [ ] WS-CL-039 [P1] delivered/read принимают только chat_id и seq 0..last_seq; участник берётся из JWT. Чужой чат → forbidden, seq вне диапазона → invalid_seq, retryable=false; user_id от клиента запрещён.
- [ ] WS-CL-040 [P0] Курсоры участника общие для устройств, обновляются через max; read продвигает delivered. Повтор/запоздалое значение не уменьшает курсор; нет отдельного ack, актуальные статусы рассылаются участникам после сохранения.
- [ ] WS-CL-041 [P1] Read отправляется после показа в активном окне, не от факта new; собственные сообщения не дают статус от собеседника. После reconnect курсоры восстанавливаются из расширенного history-контракта; приватный REST read MVP не публикует message.read.
- [ ] WS-CL-042 [P1] Presence: online при хотя бы одном авторизованном живом сокете, offline после последнего; закрытие одной вкладки не сбрасывает online. Снимок и обновления доступны только собеседникам общих чатов; неизвестное состояние — unknown.
- [ ] WS-CL-043 [P1] Typing true не чаще раза в 2 с, TTL 5 с; false по остановке/отправке/уходу. Пользователь из JWT, проверяется участие; потерянный false устраняется TTL. Старый сигнал по ts не возвращает индикатор.
- [ ] WS-CL-044 [P1] Typing объединяется по вкладкам: false/закрытие одной не убирает другой живой сигнал; общий expires_at максимален. Typing не хранится в history, не повторяется после reconnect, не имеет ack.
