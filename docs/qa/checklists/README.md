- [WebSocket](websocket.md): handshake, send/ack/new, дедупликация, seq, сбои и восстановление; отдельно этап 2.
- [Контакты и поиск](contacts.md): REST, приватность списка и экран по решениям #68.

Все пункты **подготовлены, не выполнены**. Галочка означает успешную проверку конкретной сборки, а не наличие реализации. Оставляйте исходные списки неизменными: результат прогона фиксируйте в задаче/копии списка по ID как Pass, Fail, Blocked или N/A с причиной. Для результата указывайте SHA, окружение, дату, исполнителя, тестовые данные без секретов, фактический ответ и ссылку на дефект. Негативные наборы выполняйте для каждого значения отдельно.

P0 — сохранение/изоляция данных и основной путь; P1 — ошибки, границы и восстановление; P2 — дополнительные проверки. Приоритет указан у каждого пункта. Это списки проверок; подробные пошаговые сценарии развиваются в [T48](https://github.com/messenger-go-team/messenger/issues/48) и [существующих кейсах](../test-cases/proposed-tests.md).

## Общие предусловия

- Для API: отдельное тестовое окружение auth/history/chat, известные REST/WS адреса, разрешённый Origin, доступ к ответам/заголовкам. HTTPS нужен для проверки Secure cookie; локальный HTTP не подтверждает её поведение.
- Данные: A и B — участники личного чата AB, C — посторонний; второй чат AC; отдельный свободный username и отсутствующий UUID пользователя. Списки контактов независимы. Для границ и гонок — новые данные или сброс между наборами.
- Для UI: два изолированных браузерных контекста A/B, при необходимости две вкладки A; ширины по текущим макетам. Refresh хранится в cookie; настоящие токены, пароли и полные credential-заголовки не прикладывать к отчётам.
- Для сбоев: управляемое подавление отдельных WS-событий, отключение сети/history и контроль commit на тестовом стенде. Недоступность такого инструмента означает Blocked, а не Pass.
- Для handshake-кодов, binary, UTF-8 и Ping/Pong нужен протокольный клиент: браузер не раскрывает HTTP-ответ неуспешного WS-handshake. Моки подтверждают поведение клиента, интеграционные гарантии сохранения проверяются на сервисах/БД.
- Пункты этапа 2 не входят в приёмку MVP. Приватный REST read в MVP не равен WS message.read для собеседника.

## Вопросы до выполнения отдельных пунктов

1. В WS §7 не определены лимит попыток/общее время автоповторов, поведение офлайн и позднего подтверждения. Уточнить у владельцев клиента/chat перед проверкой terminal failed и ручного повтора; WS-CL-030 помечен как Blocked до решения. Остальные повторы проверяются по контракту.
2. Для malformed HTTP JSON, неверного Content-Type и методов вне OpenAPI не назначаем произвольные коды: зафиксировать фактический результат и согласовать ожидания отдельно от описанных 401/409/422. Верхний предел пароля также не вводим самостоятельно.
3. Файл WS в main сохраняет заголовок «проект T09», хотя #9 закрыт. Основа этих пунктов — версия файла в main; актуальность заголовка и факт согласования уточнить на ревью, не считать чек-лист новым согласованием контракта.
