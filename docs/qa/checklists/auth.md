# Auth: контрактный чек-лист MVP

Основание: [auth.yaml](../../../api/openapi/auth.yaml), SPEC FR-AUTH-1..5. [Правила прогона и данные](README.md). Ожидаемые тела — по схемам User, AccessTokenResponse, ApiError текущего OpenAPI; code/message примера не считаются единственным допустимым текстом ошибки.

## Регистрация — POST /auth/register

- [ ] AUTH-CL-001 [P0] Свободный username и пароль от 8 символов → 201, User с UUID id, исходным username и date-time created_at; password/hash отсутствуют.
- [ ] AUTH-CL-002 [P0] Регистрация не создаёт сессию: refresh/access не выдаются; для входа требуется отдельный login.
- [ ] AUTH-CL-003 [P1] Username длиной 3 и 32 с латиницей обоих регистров, цифрами и `_` → 201; длиной 0, 1, 2, 33 → 422, пользователь не создаётся.
- [ ] AUTH-CL-004 [P1] Кириллица, emoji, дефис, пробелы в username (включая вокруг валидного значения) → 422; не допускается неоговорённый trim/подмена имени.
- [ ] AUTH-CL-005 [P1] Пароль длиной 7/8 → соответственно 422/201 при остальных валидных полях; пароль не возвращается в ответе. Верхнюю границу не задаём сверх контракта.
- [ ] AUTH-CL-006 [P1] Поочерёдно отсутствующее обязательное поле, null, число/массив/объект вместо строки, лишнее свойство → 422; ответ ApiError, нет пользователя или сессии.
- [ ] AUTH-CL-007 [P0] Повтор username с тем же и другим регистром → 409; исходная запись не меняется.
- [ ] AUTH-CL-008 [P0] Два одновременных register одного свободного username, в том числе разного регистра → ровно один 201 и один 409, в БД один пользователь.

## Вход — POST /auth/login

- [ ] AUTH-CL-009 [P0] Правильные credentials → 200: token_type=Bearer, непустой access_token, expires_in=900; refresh отсутствует в JSON.
- [ ] AUTH-CL-010 [P1] Разный регистр username существующего пользователя с правильным паролем → успешный вход в тот же аккаунт.
- [ ] AUTH-CL-011 [P0] Неверный пароль и несуществующий, но синтаксически валидный username → 401 ApiError; успешная сессия не выдаётся. Не фиксировать точный текст message из примера как контракт.
- [ ] AUTH-CL-012 [P1] Пустые/отсутствующие username/password, границы username 2/33, пароль короче 8, неверные типы, null, лишнее свойство → 422 по LoginRequest; проверить отсутствие токенов при отказе.
- [ ] AUTH-CL-013 [P0] На HTTPS refresh приходит только через Set-Cookie: HttpOnly, Secure, SameSite=Lax, Path=/auth, Max-Age около 2592000 с; JS браузера не читает HttpOnly cookie, cookie не уходит на /me или посторонний путь.
- [ ] AUTH-CL-014 [P0] Проверить access JWT общим валидатором/тестовым сервисом: HS256, корректная подпись, sub UUID своего пользователя, iat/exp и срок около 15 минут. Декодирование без проверки подписи недостаточно.

## Профиль — GET /me

- [ ] AUTH-CL-015 [P0] Bearer A → 200 User A; Bearer B → профиль B, без чужих или секретных полей.
- [ ] AUTH-CL-016 [P0] Нет Authorization, пустой/испорченный/истёкший токен, подмена подписи или неподдерживаемый алгоритм → 401 ApiError, профиль не раскрывается.
- [ ] AUTH-CL-017 [P1] Валидировать тело User по схеме, включая обязательные поля, UUID/date-time и additionalProperties=false. Refresh cookie без access JWT не даёт доступа к /me.

## Обновление — POST /auth/refresh

- [ ] AUTH-CL-018 [P0] Cookie из login автоматически отправляется на /auth/refresh → 200 AccessTokenResponse и новый refresh в Set-Cookie с атрибутами исходной cookie.
- [ ] AUTH-CL-019 [P0] Новый access авторизует /me того же пользователя; новая refresh cookie позволяет следующее обновление.
- [ ] AUTH-CL-020 [P0] Повтор старого refresh после успешной ротации → 401, старый токен не создаёт ещё одну успешную ротацию. Не предполагать отзыв всей семьи токенов: политика сверх этого не описана.
- [ ] AUTH-CL-021 [P0] Отсутствующая, пустая, случайная, истёкшая или отозванная refresh cookie → 401; access в заголовке/JSON не заменяет refresh cookie.
- [ ] AUTH-CL-022 [P0] Два контролируемых одновременных запроса с одним refresh → только один успешно потребляет токен, второй 401; новая выданная cookie пригодна для следующей ротации. Изолировать cookie jars, чтобы проверить именно повтор старого значения.
- [ ] AUTH-CL-023 [P1] В нескольких вкладках клиент координирует refresh: нет конкурентного расходования одной cookie и бесконечного refresh-loop при ошибке. Неудачный запрос не маскируется как успешный вход.
- [ ] AUTH-CL-024 [P1] Ошибка сети в момент refresh не считается подтверждением ротации; клиент показывает согласованное состояние повторной авторизации, не раскрывает токены. Автоматическое восстановление при неизвестном исходе уточняется в клиентской политике, не гарантируется контрактом API.

## Выход — POST /auth/logout

- [ ] AUTH-CL-025 [P0] Действующая refresh cookie → пустой 204, refresh отозван; Set-Cookie удаляет cookie (Max-Age=0, Path=/auth и защитные атрибуты).
- [ ] AUTH-CL-026 [P0] После logout сохранённое старое значение refresh не обновляет сессию (401); браузер больше не отправляет удалённую cookie.
- [ ] AUTH-CL-027 [P1] Logout без cookie, с невалидным/отозванным refresh, в том числе повтор logout после удаления cookie → 401; идемпотентный 204 здесь не обещан.
- [ ] AUTH-CL-028 [P0] Клиент закрывает свои WS и отключает reconnect после logout. Немедленный серверный отзыв уже выданного access JWT не требуется в MVP: истечение access и отзыв refresh проверяются отдельно.

## Общие проверки и внутренний API

- [ ] AUTH-CL-029 [P1] 401/409/422 имеют JSON по ApiError; обязательны code/message, details при наличии соответствуют схеме; секреты/stack trace/SQL в ответах и отчётах отсутствуют.
- [ ] AUTH-CL-030 [P1] Пустой 204 logout не разбирается клиентом как JSON; ошибка сети/401 не оставляет интерфейс в состоянии бесконечной загрузки.
- [ ] AUTH-CL-031 [P0] Служебный GET /internal/users/{user_id} недоступен через внешний Nginx; пользовательский JWT/cookie не заменяет AUTH_INTERNAL_TOKEN. На внутреннем адресе отсутствующий/неверный служебный bearer → 401 до lookup.
- [ ] AUTH-CL-032 [P1] На внутреннем адресе с правильным служебным bearer существующий UUID → 200 UserSummary; отсутствующий/некорректный UUID → 404, без password/hash и refresh. Применять только на согласованном внутреннем стенде.
