# Приёмка веб-клиента Messenger на staging

Задача [#46](https://github.com/messenger-go-team/messenger/issues/46) проверяет веб-клиент с реальными Auth, History и Chat. Базовый стенд отвечает по [HTTPS](https://staging.tidingm.ru/app/). Экран «Важно» открывается по `/app/later`, а запросы списка и изменений идут в History по `/later`.

## Исходный прогон

На staging работали бэкенд `4a7b2b6` и веб-артефакт `f57bdc5` из #165. Восемь веб-файлов совпали по SHA-256 с артефактом из `main` на `4a7b2b6`. Для прогона использованы отдельные аккаунты и чаты. Учётные данные и содержимое токенов в отчёт не входят.

| Сценарий | Результат исходного прогона |
| --- | --- |
| Контакты | Поиск обращается к `/users/search`, добавление и удаление возвращают `204`. Запрос списка без JWT возвращает `401`, повтор с JWT восстанавливает список. Повторное открытие чата после удаления контакта возвращает тот же ID и показывает историю. |
| Непрочитанные | Входящее увеличивает `unread_count`. После чтения `POST /chats/{id}/read` возвращает `204`, REST-счётчик обнуляется. Повтор проверен после одного запроса, остановленного в браузере. |
| Восстановление списка | После разрыва WebSocket History сохраняет пропущенное сообщение. До исправления список чатов мог показывать старый текст и старый счётчик после повторного подключения. |
| «Вернуться позже» | Сохранение после WSS ACK, повтор без дубля, перезагрузка списка, перенос и `Готово` прошли с реальным History. Переход за пределы первых 50 сообщений использовал `/context`, выделил цель и позволил листать дальше. Напоминание появилось при наступлении срока и после повторного открытия. У второго аккаунта запись и событие отсутствовали, его счётчик не изменился. |

## Две вкладки и истечение токенов

В Edge у двух вкладок одного аккаунта открылись сокеты с одним сроком access-токена. Для одновременного старта первый bootstrap-запрос задержали в браузере на 900 мс и пропустили в реальный Auth. После загрузки вкладок задержку убрали. Срок действия токенов истёк на сервере при активных сокетах.

В `14:33:54.689` мск обе вкладки получили Close `4401`. Через 2 мс браузер отправил один `POST /auth/refresh` с ответом `200`. Сокеты восстановились через 966 и 1106 мс, обе вкладки остались в приложении. Запрос планового refresh примерно за минуту до закрытия сокетов относится к обычному продлению сессии. В окне обработки `4401` прошёл ровно один POST. Этот прогон начался на веб-артефакте `f57bdc5`, бэкенд `4a7b2b6`. Исправление в PR касается списка чатов, Auth и обработчик переподключения сохранили ту же реализацию.

## Повторный прогон на сборке PR #167

На VPS опубликован `dist` из `b5334d6`, бэкенд `4a7b2b6`. Контрольная сумма архива совпала на машине сборки и на VPS. После переключения проверены корневой редирект, прямые маршруты, MIME-типы JS/CSS и ответы API на корне. Предыдущая версия сохранена в каталоге релизов.

| Сценарий | Результат |
| --- | --- |
| Контакты и вход | Два аккаунта вошли через реальный Auth. В браузере подтверждены поиск, `401` без JWT и успешный повтор, `PUT`/`DELETE` с `204`, `POST /chats/personal` с `201` при создании и `200` при повторе. ID и сообщения сохранились после удаления контакта. |
| Непрочитанные и reconnect | При входящем сообщении счётчик стал `1`. После остановленного браузером запроса `/read` повтор вернул `204`, счётчик стал `0`. При обрыве WebSocket второе сообщение сохранилось в History и после reconnect появилось в списке без перезагрузки. |
| Скрытая вкладка и поздний `/read` | Видимость в headless-браузере задавалась тестовым `visibilitychange`. Пока вкладка была скрыта, `unread_count` оставался `1`. Поздний `POST /read` с меньшим `seq` от соседней вкладки вернул `204` и сохранил счётчик. При возврате фокуса новый курсор обнулил счётчик. |
| «Вернуться позже» | Повторно проверены публичные маршруты, сохранение после ACK, повтор без дубля, перенос с изменением порядка, переход через `/context` к сообщению за пределами первых 50 и загрузка более новых сообщений. Срок проверен при открытом приложении и после повторного открытия. `Готово` вернул `204`, закрыл напоминание и убрал запись. У второго аккаунта не появилось Later-событий или записей, счётчик остался прежним. |
| Раскладки Later | Проверены ширины 390, 820 и 1440 px. На мобильной и планшетной ширинах меню открывалось касанием. Встроенные поля даты и времени доступны с клавиатуры. Фокус возвращался на ту же кнопку после `Escape` и сохранения. |
| Локальная разработка | Прогон 560 тестов прошёл. При `VITE_API_MOCK=true` локальный Vite отдаёт `/mockServiceWorker.js` как JavaScript на корневом маршруте. |

В проверенных сценариях расхождений со статусами и адресами контрактов не выявлено. Обновление списка после reconnect было дефектом клиента и покрыто регрессионным тестом. Ранее при быстром обновлении `/app/contacts` наблюдалась пауза около 16 секунд до восстановления сессии. В этом PR исправляется обновление списка, таймеры bootstrap refresh требуют отдельной диагностики.
