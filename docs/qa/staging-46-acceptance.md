# Приёмка веб-клиента Messenger на staging

Задача [#46](https://github.com/messenger-go-team/messenger/issues/46) проверяет веб-клиент с реальными Auth, History и Chat. Базовый стенд отвечает по [HTTPS](https://staging.tidingm.ru/app/). Экран «Важно» открывается по `/app/later`, а запросы списка и изменений идут в History по `/later`.

## Исходный прогон

На staging работали бэкенд `4a7b2b6` и веб-артефакт `f57bdc5` из #165. Восемь веб-файлов совпали по SHA-256 с артефактом из `main` на `4a7b2b6`. Для прогона использованы отдельные аккаунты и чаты. Учётные данные и содержимое токенов в отчёт не входят.

| Сценарий | Результат исходного прогона |
| --- | --- |
| Контакты | Поиск обращается к `/users/search`, добавление и удаление возвращают `204`. Запрос списка без JWT возвращает `401`, повтор с JWT восстанавливает список. Повторное открытие чата после удаления контакта возвращает тот же ID и показывает историю. |
| Непрочитанные | Входящее увеличивает `unread_count`. После чтения `POST /chats/{id}/read` возвращает `204`, REST-счётчик обнуляется. Повтор проверен после одного запроса, остановленного в браузере. |
| Восстановление списка | После разрыва WebSocket History сохраняет пропущенное сообщение. До исправления список чатов мог показывать старый текст и старый счётчик после повторного подключения. |
| «Вернуться позже» | Сохранение после WSS ACK, повтор без дубля, перезагрузка списка, перенос и `Готово` прошли с реальным History. Переход за пределы первых 50 сообщений использовал `/context`, выделил цель и позволил листать дальше. Напоминание появилось при наступлении срока и после повторного открытия. У второго аккаунта запись и событие отсутствовали, его счётчик не изменился. |

## Исходный прогон истечения токенов

В Edge у двух вкладок одного аккаунта открылись сокеты с одним сроком access-токена. Для одновременного старта первый bootstrap-запрос задержали в браузере на 900 мс и пропустили в реальный Auth. После загрузки вкладок задержку убрали. Срок действия токенов истёк на сервере при активных сокетах.

В `14:33:54.689` мск обе вкладки получили Close `4401`. Через 2 мс браузер отправил один `POST /auth/refresh` с ответом `200`. Сокеты восстановились через 966 и 1106 мс, обе вкладки остались в приложении. Запрос планового refresh примерно за минуту до закрытия сокетов относится к обычному продлению сессии. В окне обработки `4401` прошёл ровно один POST. Этот прогон начался на веб-артефакте `f57bdc5`, бэкенд `4a7b2b6`.

## Повторный прогон на первой версии PR #167

На VPS опубликован `dist` из `b5334d6`, бэкенд `4a7b2b6`. Контрольная сумма архива совпала на машине сборки и на VPS. После переключения проверены корневой редирект, прямые маршруты, MIME-типы JS/CSS и ответы API на корне. Предыдущая версия сохранена в каталоге релизов.

| Сценарий | Результат |
| --- | --- |
| Контакты и вход | Два аккаунта вошли через реальный Auth. В браузере подтверждены поиск, `401` без JWT и успешный повтор, `PUT`/`DELETE` с `204`, `POST /chats/personal` с `201` при создании и `200` при повторе. ID и сообщения сохранились после удаления контакта. |
| Непрочитанные и reconnect | При входящем сообщении счётчик стал `1`. После остановленного браузером запроса `/read` повтор вернул `204`, счётчик стал `0`. При обрыве WebSocket второе сообщение сохранилось в History и после reconnect появилось в списке без перезагрузки. |
| Скрытая вкладка и поздний `/read` | Видимость в headless-браузере задавалась тестовым `visibilitychange`. Пока вкладка была скрыта, `unread_count` оставался `1`. Поздний `POST /read` с меньшим `seq` от соседней вкладки вернул `204` и сохранил счётчик. При возврате фокуса новый курсор обнулил счётчик. |
| «Вернуться позже» | Повторно проверены публичные маршруты, сохранение после ACK, повтор без дубля, перенос с изменением порядка, переход через `/context` к сообщению за пределами первых 50 и загрузка более новых сообщений. Срок проверен при открытом приложении и после повторного открытия. `Готово` вернул `204`, закрыл напоминание и убрал запись. У второго аккаунта не появилось Later-событий или записей, счётчик остался прежним. |
| Раскладки Later | Проверены ширины 390, 820 и 1440 px. На мобильной и планшетной ширинах меню открывалось касанием. Встроенные поля даты и времени доступны с клавиатуры. Фокус возвращался на ту же кнопку после `Escape` и сохранения. |
| Локальная разработка | Прогон 560 тестов прошёл. При `VITE_API_MOCK=true` локальный Vite отдаёт `/mockServiceWorker.js` как JavaScript на корневом маршруте. |

## Что изменилось по итогам ревью

Живое `message.new` и успешная догрузка после reconnect теперь отдельно сигнализируют списку чатов. Даже пустая догрузка обновляет список данными из `GET /chats`, который WS-клиент уже отправил в History при синхронизации. Для одного авторизованного клиента экран и WS-синхронизация используют общий загрузчик списка. Пока ответ ожидается, входящие события запоминают один последующий запрос. Успешный ответ применяется сразу, если после его начала в этой вкладке не завершились `POST /read` или создание чата.

Детерминированные тесты проверяют курсоры `after_seq=0` и `after_seq=1` с пустой догрузкой, очередь при потоке входящих и гонку с отметкой о прочтении. Локально прошли 563 фронтенд-теста, TypeScript, ESLint, Prettier и staging-сборка.

## Сборка `d244c40` после первого ревью

Frontend CI для head `36c51b3` собрал тестовый merge SHA `d244c40`. На VPS опубликован архив [web-dist](https://github.com/messenger-go-team/messenger/actions/runs/45613343886). Его SHA-256 совпал с метаданными GitHub Actions, а все восемь статических файлов побайтово совпали с чистой сборкой head `36c51b3`. Бэкенд staging - `4a7b2b6`. Сборка `b5334d6` сохранена для отката. После переключения проверены `302` с корня, прямые маршруты `/app/`, `/app/contacts` и `/app/later`, MIME-типы JS/CSS и `401` от `/chats` без JWT.

### Пустая догрузка после reconnect

В Edge две вкладки одного тестового аккаунта открыли один профиль. Первая догрузила одно сообщение с `after_seq=0` и показала бейдж `1`. Остановили WSS только в первой вкладке, затем во второй открыли чат. Реальный `POST /chats/{id}/read` с `seq=1` вернул `204`. В первой вкладке до восстановления связи всё ещё был бейдж `1`. После reconnect запрос `GET /messages?after_seq=1` вернул пустой список, `GET /chats` вернул `unread_count=0`. Бейдж исчез, последний текст сохранился без перезагрузки страницы.

В этом прогоне выполнены два последовательных `GET /chats` с разными access-токенами. Запросы не пересеклись. Содержимое токенов не сохраняли.

### Две серии живых сообщений

В браузере задержали выдачу трёх реальных ответов `GET /chats` по очереди. Пока первый и второй ответы ожидали выдачи, получатель принял по три настоящих `message.new` по WSS. Интерфейс отрисовал все три ответа `200`: начальный список и два последующих обновления, по одному на серию. Одновременно ожидался максимум один запрос.

### Две вкладки и реальный Close `4401`

В двух вкладках Edge одного профиля использовали один тестовый аккаунт. Для синхронного bootstrap первый refresh задержали в браузере на 900 мс и отправили в реальный Auth. После старта задержку убрали. Сервер сам закрыл оба исходных сокета по истечении access-токенов.

Первый Close `4401` получен в `15:43:10.596` мск, второй через 2 мс. В окне восстановления был один `POST /auth/refresh`: через 2 мс после первого Close, ответ `200`. Сокеты снова стали открытыми через 936 и 1126 мс после первого Close. Обе вкладки остались в приложении. Плановый refresh примерно за минуту до Close учитывался отдельно.

## Приёмка артефакта `7d0f786` по последнему ревью

На staging опубликован [артефакт Frontend CI](https://github.com/messenger-go-team/messenger/actions/runs/45621070650) для head `86d1c1b` и тестового merge SHA `7d0f786`. Бэкенд - `4a7b2b6`. SHA-256 архива сверили при скачивании и на VPS. Все восемь файлов из архива совпали с активной сборкой. Предыдущий веб-релиз `d244c40` сохранён для отката. После публикации прошли проверка корневого редиректа, прямых маршрутов `/app/`, `/app/contacts`, `/app/later`, MIME-типов JS/CSS и ответа `401` для запроса `GET /chats` без JWT.

### Тот же токен, старый GET в работе и пустая догрузка

1. Первая вкладка догрузила единственное сообщение с `after_seq=0` и показала бейдж `1`. Другое живое сообщение запустило `GET /chats`. Браузер удержал выдачу реального ответа `200`, в котором для первого чата было `unread_count=1`.
2. Остановили WebSocket первой вкладки. Из второй вкладки того же профиля отправили реальный `POST /chats/{id}/read` с `seq=1`. History вернул `204`, серверный счётчик стал `0`.
3. Первый сокет восстановился с тем же access-токеном. Пока старый ответ удерживался, свежий запрос списка не начался. После выдачи старого ответа прошёл один свежий `GET /chats` с тем же токеном. Он вернул `200` и `unread_count=0`. Максимум один запрос списка ожидался одновременно.
4. Догрузка с `after_seq=1` вернула пустую страницу. Бейдж исчез, текст последнего сообщения сохранился без перезагрузки.

### Реальный Close `4401` в двух вкладках

Открыли две вкладки Edge одного профиля и одного аккаунта. Для синхронного старта первый bootstrap refresh задержали в браузере на 900 мс, затем отправили в реальный Auth. После старта задержку убрали и дождались установленного сервером истечения access-токенов.

Первый Close `4401` получен в `16:38:25.522` мск, второй через 2 мс. В окне восстановления прошёл один `POST /auth/refresh` с ответом `200`, через 2 мс после первого Close. Сокеты восстановились через 1001 и 1149 мс. Обе вкладки остались в приложении. Плановый refresh примерно за минуту до закрытия сокетов учитывался отдельно.

## Наблюдение о быстрой перезагрузке

В отдельных предыдущих прогонах быстрой перезагрузки `/app/contacts` восстановление сессии занимало около 16 секунд, после чего refresh и выдача контактов завершались успешно. Диагностика вынесена в [#168](https://github.com/messenger-go-team/messenger/issues/168).
