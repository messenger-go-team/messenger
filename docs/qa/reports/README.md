## Подготовка данных

До smoke подготовить независимые браузерные контексты A/B, постороннего C, одноразовые пары AD/AE без чата, чат AB с сохранённым до выката M0, тестовые имена и поисковый набор с положительным совпадением Alice_1 и исключением Malice_1, более 20 совпадений. Зафиксировать UUID и серверные ID без секретов. Seed каждого кейса имеет приоритет над общими данными; повторно использовать изменённый другим кейсом чат без восстановления нельзя.

Для unread нужны исходные last_read_seq, состав чужих/собственных сообщений и счётчики. Для LATER-13 нужна его принятая фикстура 401 сообщения, M.seq=201 и исходная страница 352–401; для LATER-15 M от A непрочитано B и наблюдение подтверждено до действий A. API-варианты не должны получать скрытые POST /read от параллельно открытого UI.

Подготовить управляемые часы приложения и server_time/БД отдельно: изменение времени устройства не переводит серверную запись в due. Три ширины 360/768/1440 CSS px, браузеры/ОС и утверждённые макеты зафиксировать в отчёте; требования к вариантам брать из кейса, не выбирать только удобный браузер или одну раскладку.

## Порядок первого прогона

1. Создать папку docs/qa/reports/<run-id>/; скопировать mvp-register.md и mvp-report-template.md с теми же именами, чтобы сохранить взаимные ссылки. Заполнить Run ID, владельца, scope, источники кейсов/контрактов, версии frontend/backend и фактические URL. Проверить веб-версию по manifest/артефакту и загруженным файлам, backend — по актуальному GitHub Deployment/CD либо записи оператора ручного отката с целевым и фактическим SHA, подтверждённым на VPS; Network и proxy должны подтверждать их связку. Один backend SHA не подтверждает версию веб-клиента.
2. До таймера подготовить данные/доступы/наблюдение. Выполнить первый browser smoke T51 и приложить его отдельный отчёт. T51 принята через [PR #111](https://github.com/messenger-go-team/messenger/pull/111): использовать актуальный [smoke-чек-лист](../smoke.md), выполняя новый прогон на проверяемом выкате. Подтвердить ack A/new B и автоматическую history-догрузку после reconnect до открытия чата; измерить весь smoke по правилам T51, целевой предел — 10 минут. Измеренный результат не заменять плановыми 9:15+0:45. Подробная регрессия T50 не ограничена десятью минутами.
3. Если smoke Failed/Blocked, сохранить его отчёт и определить доступные независимые проверки. Не выполнять зависимый критический путь как будто smoke прошёл; остальное Not run/Blocked с причиной. Текущий документ не разрешает автоматически откатывать выкат.
4. При готовом стенде пройти P0, затем P1/P2. Для каждого ID записывать все обязательные варианты, факт и свидетельства; получать исходы по настоящему API/WS/UI. Успех локальной коллекции T49 не переносить автоматически в staging-ведомость.
5. Для Later выполнить путь после повторного открытия: A отправляет просьбу; B сохраняет с будущим сроком, закрывает приложение, после срока открывает, видит напоминание, переходит к исходному сообщению и нажимает «Готово». Запись не возвращается после обновления/перезагрузки; у A нет доступа к личной записи B. Переход к цели за пределами загруженной страницы проверить по предусловиям соответствующего кейса T48; его можно выполнить отдельным прогоном. Для каждого сценария зафиксировать данные, LATER-ID, фактический результат и доказательства. Также отдельно показать напоминание при открытом приложении; одно сохранение без напоминания не заменяет эти проверки.
6. Оформить выявленные дефекты, затем на сборке с исправлением повторить исходный сценарий и связанную регрессию. Указать новый SHA/build ID и отдельную попытку/новый run; прежний Failed не стирать. После исправления/отката требуется новый полный smoke T51.
7. Пересчитать статусы ведомости, сверить с итоговым отчётом и приложить рекомендацию QA. Полная приёмка T50 требует всех обязательных MVP-прогонов; подготовка этих файлов не закрывает T50 и не даёт оснований писать Closes #50 в PR только с шаблонами.

## Статусы, счётчики и дефекты

Passed — выполнены все обязательные шаги/варианты данного ID и получены ожидаемые результаты. Failed — есть фактически наблюдаемое отклонение; приложить дефект/факт, даже если другие варианты прошли. Если Failed нет, но обязательный вариант недоступен из-за условия/решения, статус Blocked с владельцем и основанием. Если выполнение не начато или оставшаяся часть просто не выполнена — Not run. Положительный результат части кейса не заменяет статус целого.

Считать каждый ID один раз: Passed + Failed + Blocked + Not run = 91. Выполнено = Passed + Failed; доля выполненных = (Passed + Failed)/91. Pass rate среди выполненных = Passed/(Passed + Failed), при нулевом знаменателе «не вычисляется». Ни доля, ни pass rate не равны покрытию кода или требований. Blocked/Not run не включать в Passed и не исключать из знаменателя, чтобы улучшить процент.

Баги — по [форме T22](../../../.github/ISSUE_TEMPLATE/bug.yml): требование/ID, окружение, обе версии, предусловия, шаги, ожидаемый и фактический результат, воспроизводимость, request_id и доказательства без паролей/JWT/cookie. Проверить дубликаты; назначить bug и ровно одну severity:* по [описаниям](../../../.github/severity-labels.json), не путать severity с приоритетом P0/P1. Список issue — уникальный: один баг, найденный несколькими кейсами, не считать несколько раз. Блокировки среды/решений перечислять отдельно от продуктовых дефектов.

Critical/High разбирать сразу; ретест и решение команды фиксировать по тест-плану. Нет доказательств прогона — количество дефектов «не оценивалось», а не «0 дефектов». Для обычного релиза все применимые P0/P1 должны пройти, открытые Critical/High и непроверенные P0/P1 блокируют рекомендацию; риски Medium/Low и непроверенные P2 принимаются командой явно. Это решение о релизе, а не автоматическое изменение статуса теста. По окончании выключить Offline/hooks, завершить личные тестовые Later-записи и сохранить необходимые доказательства; production и общий стенд не сбрасывать.
