# Инструменты тестирования Messenger

Задача: [T24](https://github.com/messenger-go-team/messenger/issues/24).
Основание: [тест-план T21](test-plan.md), SPEC NFR-6.
Статус: локальная часть T24 выполнена: инструменты выбраны, пробные запуски всех трёх выполнены. Согласование с командой, ревью и merge PR ещё предстоят. Обновлено по ревью: 16 ноября 2026.

## Критерии выбора

Инструменты должны поддерживать запуск локально и в CI, версионирование тестов в Git, передачу параметров окружения, понятную диагностику и ненулевой код завершения при нарушении критериев. Для API важны последовательные сценарии с токенами и cookies, негативные проверки, проверка схем и отчёты JUnit/JSON. Набор должен укладываться в ограничение автоматизации — не более 25% времени QA.

## API: Bruno и Bruno CLI

### Сравнение с Postman

Оба инструмента поддерживают коллекции, скрипты проверок, окружения, последовательные запросы и запуск через CLI. Для типовых проверок статусов, полей ответа и токенов принципиального функционального разрыва не выявлено. Оба могут работать с коллекциями из Git.

**Bruno:** локальные текстовые коллекции используются приложением и CLI; CLI поддерживает тестовые данные CSV/JSON, отчёты JUnit/JSON/HTML и ненулевой exit code при ошибках. Зависимость @usebruno/cli можно закрепить в package.json и lock-файле; в CI установить через npm ci. Это соответствует процессу «коллекция в PR → запуск из коммита → машинный отчёт».

**Postman:** предоставляет скрипты и Collection Runner, импорт OpenAPI и запуск локальных коллекций через официальный Postman CLI. Нужно учитывать формат: по текущей документации CLI для HTTP-коллекций v3/YAML поддерживается только CLI-репорт; набор встроенных JSON/JUnit/HTML-репортов доступен для HTTP v2/JSON. Newman не запускает коллекции v3. Postman подходит, но для требуемой отчётности нужно отдельно выбирать и проверять совместимый формат и runner.

### Решение

Выбираем **Bruno + Bruno CLI**. Решающие факторы — файловая коллекция в репозитории, закрепление версии CLI через npm и документированный вывод машинных отчётов. Для проекта это более прямой путь к API-проверкам в CI с требуемыми артефактами. Это оценка соответствия рабочему процессу, а не результат замера скорости или надёжности инструментов.

Коллекции и шаблоны окружений без секретов храним в Git и изменяем через PR. Секретные значения передаём отдельно, токены/пароли исключаем из отчётов. По умолчанию используем Safe Mode Bruno; если валидатор требует внешнего npm-пакета, отдельно проверяем необходимость Developer Mode и фиксируем зависимость и режим запуска.

### Контрактные проверки

OpenAPI auth/history использует 3.1. Импорт OpenAPI помогает создать запросы, но не доказывает проверку ответов по контракту. В T49 нужны явные проверки кодов, заголовков, схем и ошибок. При выборе валидатора проверяем используемые конструкции JSON Schema, разрешение $ref, UUID/date-time и отрицательные примеры. Эти требования одинаковы для Bruno и Postman; сам выбор клиента не подтверждает совместимость валидатора с OpenAPI 3.1.

В T24 проверены статус/JSON, намеренная ошибка, передача bearer между запросами, автоматический cookie jar с ротацией и удалением, а также фрагменты схем текущего auth-контракта. Подробности PoC приведены ниже. Полная коллекция auth/history остаётся в T49.

Источники: [Bruno CLI](https://www.usebruno.com/product/cli), [отчёты и пример CI](https://github.com/usebruno/bruno-docs/blob/main/v3/bru-cli/quick-start.mdx), [режимы и запуск коллекций](https://github.com/usebruno/bruno-docs/blob/main/v3/bru-cli/runCollection.mdx), [Postman CLI и ограничения форматов](https://learning.postman.com/docs/postman-cli/postman-cli-collections), [репорты Postman CLI](https://learning.postman.com/docs/postman-cli/postman-cli-reporters/), [ограничения Newman](https://learning.postman.com/docs/reference/newman-cli/command-line-integration-with-newman).

## E2E: Playwright Test и TypeScript

Выбираем **Playwright Test**. Изолированные BrowserContext подходят для одновременной проверки двух пользователей мессенджера с независимыми cookies и хранилищами. TypeScript соответствует стеку клиента; поддерживаются запуск в CI и диагностика падений через trace.

С этапа 2 поддерживаем 3–5 smoke-сценариев по тест-плану. Пробный запуск T24: открыть локальную тестовую страницу в Chromium и проверить элемент/текст; сохранить команду и результат. Этот запуск подтверждает работу инструмента, а не готовность полного e2e-набора. Vitest остаётся для компонентов и вспомогательных функций.

Документация: [изоляция контекстов](https://playwright.dev/docs/browser-contexts), [написание тестов и trace](https://playwright.dev/docs/writing-tests), [CI](https://playwright.dev/docs/ci).

## Нагрузка: k6

Выбираем **k6**. Он поддерживает HTTP и WebSocket-сценарии, виртуальных пользователей, метрики и пороги thresholds. Для новых WS-сценариев используем k6/websockets. Порог позволяет завершить прогон с ошибкой при невыполнении критерия; одних checks для этого недостаточно.

В T24 выполняем короткий локальный HTTP-прогон с одним виртуальным пользователем, проверкой ответа и threshold. На этапе 3 готовим отдельный WS-профиль по NFR-1: минимум 2 000 соединений на один chat-инстанс, около 200 сообщений/с и p95 доставки онлайн-получателю до 300 мс. Замеряем доставку message.new получателю, а не только ack отправителю. Пробный HTTP-запуск этих показателей не подтверждает.

Документация: [установка k6](https://grafana.com/docs/k6/latest/set-up/install-k6/), [WebSocket](https://grafana.com/docs/k6/latest/using-k6/protocols/websockets/), [thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/).

## Окружение и воспроизведение

Повторно проверено 16 ноября 2026 на Windows: Node.js **24.16.0**, npm **11.13.0**, Bruno CLI **4.3.0**, Playwright **1.65.1** с Chromium **159.0.8154.6**, k6 **2.4.0** (Windows amd64). npm-зависимости закреплены в package.json/package-lock.json. Portable k6 устанавливается в локальную .tools; версия и SHA256 официального архива закреплены в setup-k6.cjs.

Исходники и полная [инструкция повторения](../../qa/tool-trials/README.md) лежат в qa/tool-trials. Из корня репозитория в Git Bash:

```bash
cd qa/tool-trials
npm ci
npx --no-install playwright install chromium
node setup-k6.cjs
npm run trial:verify
```

Runner требует свободный порт 3100, самостоятельно запускает заглушку, ждёт готовности и после прогонов останавливает свой процесс. trial:all выполняет семь запусков и проверяет не только коды, но и содержание свежих JSON/JUnit-отчётов: точные имена/количество проверок, конкретную намеренную ошибку и успех остальных проверок. Старые отчёты удаляются перед запуском. Ошибки загрузки/запроса, пропуски, посторонние падения или отсутствие отчёта дают общий код 1. trial:verify дополнительно запускает контрольный сервис с другим адресом, подставляет его в BASE_URL, проверяет ноль обращений к нему и выполняет семь регрессионных тестов валидаторов. Это проверка способности инструментов обнаруживать сбои, а не обычная регрессия с разрешёнными падениями.

Цель — локальная заглушка на http://127.0.0.1:3100: GET /health возвращает HTTP 200 и {"status":"ok"}; GET / открывает HTML-страницу с кнопкой, вызывающей API; отдельные auth-маршруты обслуживают PoC. Прогоны подтверждают работу инструментов, не проверяют бизнес-функции Messenger, полные контракты или нагрузочные NFR. CI/Linux отдельно не проверялись.

## Результаты пробных запусков

### Bruno CLI

- Успешный прогон: GET /health, ожидаются HTTP 200 и status=ok; 2/2 проверки, exit code **0**.
- Отрицательный контроль: окружение negative ожидает 201 при фактическом 200; 1/2 проверки успешна, ошибка expected 200 to equal 201, exit code **1**.
- Для обоих прогонов созданы JSON и JUnit: reports/bruno-pass.json/xml и bruno-negative.json/xml. Проверены выбор окружения и передача ошибки в отчёт.

#### Proof of concept для T49

Коллекция bruno-poc выполняет **7 запросов и 20 проверок**, exit code **0**: login → /me → намеренно невалидный /me → /contacts → refresh → logout → refresh после logout (401). Заглушка разрешает профиль/контакты только с bearer из login, refresh — только с выданным cookie, logout — с ротированным cookie. После logout cookie jar очищен. Исходящие credentials маскируются Bruno в отчётах; результат подтверждается проверками и ответами заглушки.

Схемы читаются прямо из [текущего auth.yaml](../../api/openapi/auth.yaml), копий схем нет. Закреплены Ajv **8.20.0** (Ajv2020), ajv-formats **3.0.1**, yaml **2.9.1**. Проверены корневой и вложенный $ref (User, AccessTokenResponse, contacts.items → UserSummary), разрешение response $ref для ApiError, uuid/date-time, required, type, additionalProperties и const. Валидные ответы проходят; полученный HTTP-ответ с нарушениями User отвергается. Дополнительно проверены неверные UUID и date-time. Аннотация OpenAPI example объявлена невалидирующей; весь диалект OpenAPI 3.1 этим PoC не сертифицирован.

Для чтения контракта и внешнего Ajv коллекция запускается с **--sandbox developer**. Это осознанное исключение для проверенных локальных файлов; Developer Mode не является защитной границей. Базовая health-коллекция остаётся в Safe Mode. Проверяется HTTP cookie jar; атрибут Secure в локальном HTTP fixture опущен. Используются фиктивные access-токены, не проверяется JWT-подпись. HTTPS/Secure, настоящая авторизация Messenger, внешние $ref и полный history остаются вне этой пробы.

Источники валидатора и scripting API: [Ajv и JSON Schema 2020-12](https://ajv.js.org/json-schema.html), [Bruno JavaScript API](https://docs.usebruno.com/testing/script/javascript-reference).

### Playwright

- Chromium открывает страницу, проверяет заголовок, нажимает Check API, получает HTTP 200 и видит текст ok.
- Второй тест создаёт два BrowserContext и проверяет, что localStorage одного пользователя не виден другому.
- Успешный запуск: **2/2 теста**, exit code **0**.
- Отрицательный контроль ожидает broken вместо ok: один тест падает, второй проходит, exit code **1**. Сохранены JUnit, описание ошибки и trace.zip.

Эти два примера проверяют инструмент и изоляцию браузера. Продуктовые 3–5 smoke-сценариев Messenger готовятся с этапа 2.

### k6

- Общий runner явно передаёт BASE_URL=http://127.0.0.1:3100. Обёртка также закрепляет этот URL, отключает proxy для пробы, проверяет k6 **2.4.0** перед нагрузкой на любой ОС. Сам сценарий отвергает иной URL и запрещает редиректы. Несовпадение версии из PATH/K6_BIN останавливает запуск.
- Локальный HTTP-прогон: **1 VU, 3 секунды**, пауза 0.1 с между итерациями; проверяются статус и JSON.
- Успешный запуск: все checks выполнены, HTTP-ошибок нет; thresholds checks rate==1 и http_req_failed rate==0 пройдены, exit code **0**.
- Отрицательный контроль ожидает HTTP 201 при фактическом 200: половина checks не проходит, threshold checks нарушен, exit code **99**. HTTP-ошибок при этом нет: ошибка находится в ожидании теста.
- Метрики и результаты thresholds сохранены в reports/k6-pass.json и k6-negative.json. Число запросов и HTTP p95 зависят от машины и не используются как критерии производительности Messenger.

### Артефакты и ограничения

В reports/trial-summary.json сохранены дата, версии, команды, рабочие каталоги, параметры сценариев и ожидаемые/фактические exit codes. Отдельно сохраняются логи семи запусков, JSON/JUnit Bruno (включая PoC), JSON/JUnit и trace Playwright, JSON k6; у k6 проверяются точные имена/результаты checks и target URL. Регрессионный контроль BASE_URL записан в reports/base-url-regression.json. Отчёты, браузерные артефакты, node_modules и portable k6 исключены из Git; в репозитории остаются исходники, lock-файл и этот итог.

npm audit сообщает **18 записей уязвимых пакетов: 8 high и 10 moderate**; они соответствуют **20 уникальным GHSA** с учётом наследуемого риска. В [разборе зависимостей](t24-dependency-review.md) указаны конкретные advisories, пути, условия применимости, исправленные версии и план. Уязвимости не исправлены; подключение внешних API/CI отложено до устранения high и командного решения по оставшимся moderate. Выбор инструмента и успешный локальный PoC не означают принятие этого риска.
