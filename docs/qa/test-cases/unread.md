# Непрочитанные — приватная отметка MVP

Источник: [T48](https://github.com/messenger-go-team/messenger/issues/48), [history OpenAPI](../../../api/openapi/history.yaml), SPEC FR-HIST-5. Общие окружение, данные, очистка и правила результата — в [README](README.md). Статус всех кейсов: **Not run**. Каждый параметр набора — отдельный прогон.

### UNREAD-01 — Рост счётчика и исключение собственных сообщений [P0; MVP; API/UI/manual]

**Предусловия:** В AB для A/B last_read_seq=0, список сообщений пуст; отправка через API/WS-клиенты, UI не отправляет автоматические read ни за A, ни за B. В AC состояние неизменно.

**Шаги:**

1. B отправляет в AB сообщения seq=1,2; A отправляет seq=3, не показывая чат в активном окне.
2. Выполнить GET /chats A и B.

**Ожидаемый результат:**

1. Все сообщения сохранены; own seq=3 не отмечает автоматически чужие как прочитанные.
2. У A unread_count AB=2, у B=1 (сообщение A); AC неизменен. Список каждого содержит только его чаты.

### UNREAD-02 — GET истории и предзагрузка не отмечают прочтение [P0; MVP; API/UI/manual]

**Предусловия:** У A в AB два непрочитанных сообщения B; чат не показан.

**Шаги:**

1. Сохранить GET /chats, вызвать обычный GET /chats/{id}/messages и предзагрузить историю из списка чатов.
2. Повторить GET /chats, проверить журнал POST /read.

**Ожидаемый результат:**

1. История возвращает сообщения, предзагрузка может их кешировать, но это не показ пользователю.
2. unread_count и last_read_seq не изменились, POST /read из-за предзагрузки не отправлен.

### UNREAD-03 — Отметка последнего показанного seq в активном чате [P0; MVP; API/UI/manual]

**Предусловия:** B сохранил seq=1,2,3,4; A last_read_seq=0, реально показаны только 1,2.

**Шаги:**

1. Показать первые два сообщения в активном окне A; проверить POST /chats/{id}/read {"seq":2}.
2. Прочитать GET /chats; затем показать 3,4 и проверить следующую отметку.

**Ожидаемый результат:**

1. Пустой 204; выбран последний показанный N=2, а не max полученного или предзагруженного seq.
2. После N=2 счётчик 2; после показа и успешной отметки N=4 — 0. Ответ 204 не разбирается как JSON.

### UNREAD-04 — Фоновая вкладка [P1; MVP; API/UI/manual]

**Предусловия:** A открыл AB, затем скрыл вкладку; B онлайн.

**Шаги:**

1. B отправляет два сообщения, дождаться new/предзагрузки в скрытой вкладке; проверить отсутствие POST /read.
2. Вернуть вкладку на передний план и действительно показать сообщения.

**Ожидаемый результат:**

1. Получение данных в фоне не меняет курсор: GET /chats показывает рост unread_count.
2. После показа выполняется отметка последнего показанного seq, 204; счётчик уменьшается. Сам foreground без показа скрытых сообщений не обнуляет их.

### UNREAD-05 — Повтор и запоздалая отметка другой вкладки [P0; MVP; API/UI/manual]

**Предусловия:** Две вкладки A, в AB сохранены seq=1..5 от B; курсор A продвинут до 5.

**Шаги:**

1. Повторить POST /read seq=5; из задержанной второй вкладки отправить seq=2, затем seq=0.
2. Сверить GET /chats и курсор тестовыми средствами.

**Ожидаемый результат:**

1. Каждый запрос → пустой 204, cursor=max(старый,новый).
2. last_read_seq остаётся 5, unread_count не растёт повторно, старые сообщения не становятся непрочитанными.

### UNREAD-06 — Новое входящее во время отметки [P0; MVP; API/UI/manual]

**Предусловия:** У A реально показаны seq=1,2 от B; есть барьер сохранения POST /read seq=2.

**Шаги:**

1. Задержать завершение отметки N=2; B сохраняет seq=3; завершить отметку. Повторить с обратным порядком commit.
2. Получить GET /chats без показа seq=3 в UI.

**Ожидаемый результат:**

1. Отметка 204, новое сообщение сохраняется независимо от порядка транзакций.
2. seq=3 остаётся непрочитанным, unread_count=1; отметка N не захватывает будущее входящее.

### UNREAD-07 — Ошибка отметки и неизвестный исход [P0; MVP; API/UI/manual]

**Предусловия:** У A два непрочитанных сообщения B; нужны управляемый отказ до commit и потеря ответа после commit.

**Шаги:**

1. По отдельности вернуть контрактный 503 ServiceUnavailable для POST /read seq=2 до commit и потерять только ответ после commit.
2. Восстановить сеть, запросить GET /chats, безопасно повторить ту же отметку.

**Ожидаемый результат:**

1. В первом варианте 503 ApiError не считается подтверждённым обнулением, серверный курсор прежний; это временная недоступность, не 401. Во втором варианте исход неизвестен клиенту и отметка могла сохраниться.
2. UI сходится с GET /chats; повтор безопасен и даёт 204 без уменьшения курсора. До успешного подтверждения/сверки нет ложного окончательного результата.

### UNREAD-08 — Недопустимые seq [P1; MVP; API/UI/manual]

**Предусловия:** AB last_seq=5; исходные курсоры известны.

**Шаги:**

1. По одному POST /read: -1,6,1.5,"2",null, без seq, лишнее поле, число >9007199254740991.
2. На чистом экземпляре проверить допустимые seq=0 и 5.

**Ожидаемый результат:**

1. Каждое нарушение → 422 ApiError; курсоры и счётчики неизменны.
2. Оба допустимых значения → пустой 204; 0 не понижает курсор, 5 отмечает допустимый диапазон.

### UNREAD-09 — Чужой чат, JWT и отсутствующий чат [P0; MVP; API/UI/manual]

**Предусловия:** C не участник AB; подготовлен отсутствующий валидный chat UUID.

**Шаги:**

1. POST /read AB от C; затем от A без/с испорченным/истёкшим JWT.
2. От A отправить валидный запрос в отсутствующий чат.

**Ожидаемый результат:**

1. C → 403, неверная авторизация → 401; нет изменения или раскрытия чужого состояния.
2. 404 по history OpenAPI; курсоры существующих чатов не меняются. Не переносить сюда 404-правило контекста из Later.

### UNREAD-10 — Изоляция участников и отсутствие message.read [P0; MVP; API/UI/manual]

**Предусловия:** У A и B есть собственные непрочитанные сообщения; активны сокеты A/B/C, у A также AC.

**Шаги:**

1. A отправляет валидный POST /read в AB без открытия чата B; наблюдать сообщения WS.
2. Сверить GET /chats A/B/C и исходные значения AC.

**Ожидаемый результат:**

1. 204 продвигает только курсор A в AB. Приватная отметка MVP не публикует message.read собеседнику.
2. Счётчик B и все остальные участники/чаты не изменены; delivered/read собеседнику остаются этапом 2.

### UNREAD-11 — Контекст сообщения не равен прочтению или синхронизации [P1; MVP; API/UI/manual]

**Предусловия:** Есть сохранённая Later-цель вне текущей страницы AB, у A ненулевой unread_count и безопасный курсор синхронизации.

**Шаги:**

1. На уровне API вызвать GET /chats/{chat_id}/messages/{message_id}/context без показа UI и проверить GET /chats.
2. Затем показать контекст в активном окне и отдельно проверить допустимый POST /read после показа.

**Ожидаемый результат:**

1. Сам GET context не меняет last_read_seq/unread_count и не продвигает курсор синхронизации до максимума окна.
2. Прочтение может измениться только через отдельную отметку действительно показанного seq; это обычное поведение чата, не побочный эффект сохранения Later.

### UNREAD-12 — Перезагрузка и несколько чатов [P1; MVP; API/UI/manual]

**Предусловия:** AB и AC имеют разные непрочитанные; A отметил часть AB.

**Шаги:**

1. Перезагрузить приложение, получить свежий GET /chats без показа чатов; затем переподключить WS.
2. Отметить сообщения AC, повторно получить список.

**Ожидаемый результат:**

1. Серверное состояние AB/AC восстановлено независимо, загрузка списка/reconnect сами по себе не обнуляют счётчики.
2. Меняется только AC; курсор AB сохраняется. UI не использует глобальный общий счётчик вместо состояния каждого чата.
