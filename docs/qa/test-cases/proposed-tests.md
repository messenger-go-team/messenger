# Предложенные тест-кейсы

Источник: [тест-план](../test-plan.md), [SPEC](../../SPEC.md), [auth OpenAPI](../../../api/openapi/auth.yaml), [проект WS v1](../../../api/ws/events.md), [Тест-кейсы на auth, личные чаты, контакты и поиск — #48](https://github.com/messenger-go-team/messenger/issues/48).

Статус всех кейсов: **предложены, не выполнены**. WS-ожидания условны до согласования проекта контракта. HTTP-коды auth ниже взяты из локального OpenAPI; пути и коды history, кроме требования 403 для неучастника, уточняются в T08. P0/P1/P2 определены в тест-плане. Параметризованные наборы выполнять для каждого значения, изолируя данные.

Общие предусловия MVP: реализованные auth/history/chat, известный SHA, чистые seed-данные A и B, посторонний C, разрешённый Origin и действующие access JWT. Для UI — два изолированных browser context A/B; refresh в cookie. Для integration — доступ к тестовой PostgreSQL и контролируемым точкам сбоя. Индивидуальные условия уточняются в кейсах.

## Auth, профиль, поиск, контакты — этап 1

### AUTH-01 — Регистрация и отдельный вход [P0; FR-AUTH-1..2; API/manual]
Предусловия: username `qa_new` свободен. Шаги: зарегистрировать его с паролем от 8 символов; затем выполнить login. Ожидается: register 201 с User без password/hash и без автоматической сессии; login 200 с access_token/token_type/expires_in и refresh только в HttpOnly cookie.

### AUTH-02 — Границы username [P1; FR-AUTH-1; API/unit]
Шаги: зарегистрировать отдельные username длиной 2, 3, 32, 33; проверить латиницу обоих регистров, цифры, `_`, кириллицу, пробел, дефис, emoji. Ожидается: допустимые длины 3/32 и алфавит принимаются (201), остальные 422; отклонённый запрос не создаёт пользователя.

### AUTH-03 — Пароль и структура запроса [P1; FR-AUTH-1; API/unit]
Шаги: отправить register с паролем длиной 7/8, без каждого обязательного поля, с null, числом вместо строки и лишним полем; валидные данные использовать отдельно. Ожидается: длина 8 принимается; прочие перечисленные нарушения — 422 по схеме; пароль/хеш не возвращаются. Верхний предел и Unicode-семантику длины пароля сначала согласовать.

### AUTH-04 — Уникальность и гонка регистрации [P0; FR-AUTH-1; DB integration]
Шаги: зарегистрировать `Qa_User`; повторить с тем же написанием и другим регистром; затем барьером запустить два register нового одинакового username. Ожидается: повтор 409; при гонке одна регистрация 201, другая 409; в БД одна запись. В ответах сохраняется исходное написание username.

### AUTH-05 — Вход и ошибки credentials [P0; FR-AUTH-2; API]
Шаги: войти с правильным паролем и разным регистром username; затем с неверным паролем и несуществующим, но валидным username. Ожидается: валидный вход 200; оба неверных варианта 401 с одинаковым общим сообщением без раскрытия существования аккаунта; cookie сессии не выдаётся при отказе.

### AUTH-06 — JWT и профиль [P0; FR-AUTH-5, NFR-4; API/unit]
Шаги: GET /me с токеном A; повторить без токена, с истёкшим, повреждённой подписью, иным alg, некорректными sub/exp/iat. Ожидается: 200 с профилем A только для валидного токена; остальные 401, без чужих данных. Время проверять управляемыми часами, включая границу exp.

### AUTH-07 — Ротация refresh [P0; FR-AUTH-3; API/DB integration]
Шаги: сохранить тестовую копию cookie R1; обновить токены; повторить refresh с R1; отдельно проверить новый R2. Ожидается: первый запрос 200, новая cookie и access; R1 больше не принимается (401); R2 позволяет обновление. Refresh не присутствует в JSON и логах.

### AUTH-08 — Истечение и конкуренция refresh [P1; FR-AUTH-3; DB integration]
Шаги: refresh без cookie, с случайным и истёкшим токеном; затем два запроса с одним действующим R1 через барьер. Ожидается: первые варианты 401; один R1 не создаёт две независимые успешные ротации. Конкретный отказ конкурирующему запросу и судьба R2 требуют решения команды. Использовать тестовые часы вместо ожидания 30 дней.

### AUTH-09 — Logout [P0; FR-AUTH-4; API/UI]
Шаги: выйти с действующим refresh; попробовать обновиться старым refresh; проверить cookie и UI. Ожидается: logout 204, удаление cookie с тем же Path=/auth, refresh 401; UI закрывает сокеты и прекращает reconnect. Уже выданный access может жить до exp: немедленную блокировку /me не требовать.

### AUTH-10 — Cookie в реальном браузере [P1; FR-AUTH-2..4, NFR-4; manual/API]
Шаги: войти через HTTPS; проверить Set-Cookie и доступ JS, refresh и logout. Ожидается: HttpOnly, Secure, SameSite=Lax, Path=/auth, срок около 30 дней согласно контракту; JS не читает refresh; logout удаляет cookie. Проверка только локального HTTP не подтверждает рабочую cookie-сессию на HTTPS staging.

### AUTH-11 — Поиск по префиксу [P1; FR-AUTH-6; API]
Предусловия: 25 пользователей с общим префиксом. Шаги: поиск разным регистром; префикс без совпадений; без prefix, пустой, длины 1/32/33, недопустимые символы; запрос без JWT. Ожидается: 200, только совпадения по началу username, максимум 20; пустая выдача допустима; невалидный prefix — 422, без авторизации — 401. Порядок выдачи контрактом не задан.

### AUTH-12 — Контакты и изоляция [P1; FR-AUTH-7; API]
Шаги: A дважды PUT /contacts/{B}; получить контакты A и C; A дважды DELETE того же контакта; GET списка. Ожидается: PUT/DELETE каждый раз 204; одна запись B после добавления, ни одной после удаления; контакты C не меняются. PUT неизвестного корректного UUID — 404; неверный UUID — 422; защищённые операции без JWT — 401. Self-contact пока требует уточнения.

### AUTH-13 — Внутренний маршрут и секреты [P0; NFR-4; integration/manual]
Шаги: обратиться к /internal/users/{id} через внешний Nginx; из внутренней сети — без, с неверным и верным service token; проверить данные БД и логи на тестовом потоке. Ожидается: снаружи маршрут не опубликован; внутри без верного service token — 401, успешный ответ содержит только UserSummary. В users пароль только bcrypt/argon2 hash, refresh_tokens содержит token_hash; логи не содержат пароли/JWT/refresh. Точную внутреннюю схему авторизации согласовать.

## Чат, WebSocket и история — этап 1

### CHAT-01 — Единственный личный чат [P0; FR-CHAT-1,12; API/DB integration]
Шаги: A создаёт чат с B; повторяет; одновременно A создаёт A–B и B создаёт B–A. Ожидается: один chat_id для пары, два участника chat_members, без дублирования чата и участников. Ответы REST уточнить по T08.

### CHAT-02 — Двусторонняя переписка [P0; FR-CHAT-2..4; WS/UI]
Шаги: A отправляет B текст, затем B отвечает A. Ожидается: каждый получает ack после сохранения; new содержит те же message_id/seq/created_at, текст и автора из JWT; в UI каждое сообщение одно; история содержит обе записи.

### CHAT-03 — Запрет постороннему [P0; FR-HIST-3, FR-CHAT-12; API/WS]
Шаги: C подставляет chat_id A–B в чтение истории и message.send, повторяет с чужим client_msg_id; слушает свои WS-события при переписке A/B. Ожидается: история 403, WS error forbidden/retryable=false; сохранения и рассылки C нет; чужие тексты/метаданные не раскрываются. Неизвестный chat_id в WS также forbidden.

### WS-01 — Авторизация handshake [P0; NFR-4; WS integration]
Шаги: открыть /ws с messenger.v1, одним bearer.JWT и разрешённым Origin; повторить без/с двумя credentials, с истёкшим JWT, без messenger.v1, с чужим/отсутствующим/null Origin. Ожидается: валидный handshake 101 выбирает только messenger.v1; невалидные JWT 401, отсутствие messenger.v1 400, Origin 403. Неверные параметры менять по одному; JWT не отражается в выбранном протоколе или логах.

### WS-02 — Границы текста [P1; FR-CHAT-2; WS/unit]
Шаги: отправить 1/4095/4096/4097 code points, кириллицу, emoji, комбинируемые символы, пустую и только Unicode White_Space строку. Ожидается: 1..4096 code points допустимы в пределах транспортного лимита; пустая/пробельная/4097 — invalid_payload; пробелы и переводы строк сохраняются без trim/нормализации. `e` + combining acute — два code points, emoji вне BMP — один.

### WS-03 — Безопасное отображение текста [P0; NFR-4; UI]
Шаги: отправить `<img src=x onerror=alert(1)>`, `<script>`, кавычки, HTML entities; открыть new и историю с другой учётной записью. Ожидается: буквальный текст, никакого выполнения HTML/JS и сохранённого XSS; исходный текст не повреждён.

### WS-04 — Payload и корреляция ошибок [P1; WS §§3,9; integration]
Шаги: невалидный JSON, массив, два объекта подряд; по одному удалить обязательное поле, испортить UUID/ts, добавить sender_id/seq/лишнее поле; отправить неизвестный тип и событие неверного направления; затем валидный send. Ожидается: invalid_json/invalid_payload/unsupported_type по причине, retryable=false; разобранный валидный id скопирован в error, иначе новый UUID; сокет остаётся пригоден для валидной команды. В MVP delivered/read/typing от клиента дают unsupported_type.

### WS-05 — Транспортный лимит [P1; NFR-4, WS §§3,13; integration]
Шаги: сформировать валидный JSON-message ровно 65536 байт и 65537 байт с учётом escaping; проверить в цельном и фрагментированном виде; отдельно binary и невалидный UTF-8. Ожидается: ровно 65536 не отклоняется по размеру, 65537 закрывается 1009 после учёта полного message; binary 1003, невалидный UTF-8 1007. Body отдельно должен удовлетворять лимиту code points; compression не согласуется в v1.

### WS-06 — Несколько вкладок, ack и new [P1; FR-CHAT-3..4; integration/UI]
Предусловия: по два сокета A/B. Шаги: send из A1; проверить A1/A2/B1/B2; воспроизвести new раньше ack и обратный порядок. Ожидается: ack только A1; new всем четырём с едиными доменными полями; pending A1 превращается в одну запись, остальные UI также не дублируют сообщение.

### MSG-01 — Потерянный ack и повтор [P0; FR-CHAT-4..5, NFR-2; integration]
Шаги: оборвать доставку ack после commit; повторить точные chat_id/client_msg_id/body с новым id конверта, в том числе после reconnect. Ожидается: одна запись в БД; payload ack совпадает с первым сохранением, id ответа коррелирует новой попытке; нет второго seq и дубля UI. Повторный new не обязателен, дубль new допустим и дедуплицируется клиентом.

### MSG-02 — Конкурентные повторы [P0; FR-CHAT-5; DB/WS integration]
Шаги: из двух соединений A через барьер послать один client_msg_id и body в один чат. Ожидается: одна запись, все успешные ack с одинаковыми message_id/seq/created_at, нет 500 из-за гонки уникального ключа. Повторить после перезапуска chat: дедупликация не зависит от памяти процесса.

### MSG-03 — Конфликт и область ключа [P0; FR-CHAT-5, SPEC §7; integration]
Шаги: после сохранения повторить тот же ключ с другим body; отдельно тот же client_msg_id использовать другим отправителем того же чата и тем же отправителем в другом его чате. Ожидается: конфликт body — idempotency_conflict, исходная запись неизменна; другие sender/chat создают самостоятельные сообщения при наличии прав.

### MSG-04 — Порядок при конкурентной отправке [P0; FR-CHAT-6; DB/WS integration]
Шаги: A и B одновременно отправляют серию уникальных сообщений; доставить new с перестановками/повторами и одинаковыми клиентскими ts. Ожидается: уникальные монотонно назначенные seq внутри чата, UI сортирует по seq; history совпадает с набором сохранённых сообщений. Не требовать порядка по клиентским часам или отсутствия числовых пропусков.

### MSG-05 — Ack зависит от commit [P0; FR-CHAT-4; fault integration]
Шаги: контролируемо задержать commit history; затем отдельно вызвать rollback/отказ PostgreSQL до commit. Ожидается: до commit успешного ack нет; rollback не создаёт сообщение; retryable error допускает безопасный повтор. При неопределённом исходе сохранения повтор с тем же ключом приводит к одной записи.

### HIST-01 — Офлайн и перезагрузка [P0; FR-CHAT-7, FR-HIST-1..2; API/UI]
Шаги: B офлайн; A отправляет сообщения; B входит и открывает чат, перезагружает страницу. Ожидается: все подтверждённые сообщения доступны, тексты/авторы/seq сохранены; список чатов содержит актуальные последнее сообщение и время. Формат/сортировку REST проверить по T08.

### HIST-02 — Пагинация и границы [P1; FR-HIST-2; API]
Предусловия: 250 сообщений с известными ID/seq. Шаги: выгрузить все страницы before_seq, отдельно after_seq с limit=100; проверить 0/1/100/101/250 записей, границы курсоров, limit 0/1/100/101, неверные типы, оба курсора сразу. Ожидается: при валидных запросах полное множество без дублей/потерь, лимит до 100. Исключительность курсора, порядок страниц, default limit и ошибки невалидных комбинаций сначала закрепить в T08; неподтверждённые ответы не считать багом.

### HIST-03 — Чаты и непрочитанные [P1; FR-HIST-1; API/UI]
Шаги: A пишет B в A–B, затем C пишет A в A–C; проверить списки всех пользователей; с этапа 2 открыть чат и обновить read. Ожидается: отображаются только свои чаты, верное последнее сообщение/время; непрочитанные не смешиваются между чатами. Правило счётчика в MVP до появления read требуется определить; с этапа 2 оно согласуется с курсором read.

## Переподключение и ошибки — минимальный вариант этап 1, расширенный этап 3

### REC-01 — Догрузка нескольких страниц и нового чата [P0; FR-WEB-3,5; WS/API/UI]
Шаги: отключить B после синхронизированного курсора; сохранить >200 сообщений и создать новый личный чат с B; переподключить B, параллельно продолжая отправку. Ожидается: обновлён список чатов; дочитаны все after_seq страницы, новый чат от курсора 0; буфер live и history объединён без потерь/дублей.

### REC-02 — Безопасный курсор [P0; FR-WEB-5, WS §8; integration/UI]
Шаги: при синхронизированном seq=42 доставить live seq=44 до получения history с seq=43; вызвать ошибку одной страницы, затем повтор. Ожидается: ack/new не перескакивают синхронизированный курсор; ошибка history не продвигает его; после восстановления seq=43 загружен, оба сообщения видны ровно один раз. Отдельно проверить корректность при допустимом числовом пропуске в истории.

### REC-03 — Pending, failed и кнопка повтора [P0; FR-WEB-4, FR-CHAT-5; UI/integration]

Предусловия: тестовый proxy или hook позволяет подавлять события для конкретного сообщения отправителю после commit, сохраняя соединение. Управляемые часы позволяют проверить таймаут и backoff.

Шаги и ожидаемые результаты:

1. Подавить для отправляющего клиента и `message.ack`, и соответствующий `message.new`, включая ответы на повторные попытки. До нужной точки проверки исключить подтверждение через history.
2. После таймаута ack — начально 10 секунд — проверить автоматический повтор с backoff: прежние `client_msg_id`, `chat_id`, `body`, новый `id` попытки; без параллельных повторов одного сообщения.
3. В отдельном прогоне проверить: если ack потерян, но соответствующий `message.new` получен, pending сопоставляется с сохранённым сообщением по `(chat_id, sender_id, client_msg_id)`, дубля и ложного `failed` нет.
4. Переход в `failed` и ручной повтор проверять после согласования условия прекращения автоповторов: лимита попыток или общего времени, поведения офлайн и обработки позднего подтверждения через ack/new/history. При ручном повторе сохраняются `client_msg_id`, `chat_id` и точный `body`, меняется `id` попытки; после подтверждения в UI и БД остаётся одно сообщение.

**Таймаут ack сам по себе не означает `failed`.** Метка failed не доказывает отсутствие сохранённого сообщения.

Условие прекращения автоповторов и перехода в failed согласуют фронтенд и владелец chat и фиксируют в контракте/требованиях. До согласования шаг 4 — Blocked; шаги 1–3 проверяются независимо.

### REC-04 — Backoff, JWT и logout [P1; FR-WEB-3, WS §§2,8; fake timers/WS/UI]
Шаги: имитировать неудачные подключения; стабильные 30 с; истечение JWT с 4401; logout. Ожидается: интервалы 1/2/4/8/16/30 с с jitter ±20%, cap 30 с, сброс после стабильной работы; на 4401 refresh через REST и новый сокет; без бесконечной refresh-петли; после logout reconnect выключен. Вкладки координируют refresh.

### REC-05 — Потеря рассылки при живом сокете [P0; NFR-3, WS §8; fault integration]
Шаги: сохранить сообщение, подавить публикацию/new, оставить сокет B открытым; вернуть вкладку на передний план и отдельно дождаться периодической сверки. Ожидается: история восстанавливает сообщение; активная вкладка синхронизируется с начальным интервалом 30 с; отсутствие reconnect не оставляет сообщение потерянным навсегда.

### REC-06 — Перезапуск после ack [P0; NFR-3; fault integration]
Шаги: собрать множество message_id с успешным ack; остановить chat, перезапустить; переподключить клиентов и сверить history. Ожидается: все подтверждённые сообщения сохранены, pending разрешаются без дублей; новые соединения восстанавливаются. На этапе 3 повторить при разных chat-инстансах A/B и сбоях Redis.

### REC-07 — Heartbeat, slow consumer и Nginx [P1; NFR-3, WS §13; integration]
Шаги: держать соединение через Nginx >75 с; отдельно перестать отвечать Pong; переполнить очередь медленного клиента; остановить сервер штатно. Ожидается: здоровый сокет живёт с Ping каждые 25 с; после отсутствия соответствующего Pong более 10 с освобождаются ресурсы; slow consumer закрывается 1013, shutdown — 1001 с восстановлением history. 1006 может наблюдаться локально, сервер не посылает его в Close.

## Веб-клиент — этап 1

### WEB-01 — Экраны и адаптивность [P1; FR-WEB-1..2; manual]
Шаги: пройти вход, регистрацию, список чатов, переписку и профиль на 360/768/1440 CSS px; менять ширину, вставлять длинный username/текст без пробелов, открыть экранную клавиатуру. Ожидается: элементы доступны, форма и отправка не перекрываются, нет горизонтального скролла страницы из-за контента, навигация и прокрутка истории работают. Уточнить макеты/браузерную матрицу.

### WEB-02 — Управление с клавиатуры и ошибки [P2; FR-WEB-1..4; manual]
Шаги: пройти формы и чат Tab/Shift+Tab/Enter, ввести неверные данные, отключить сеть, повторить успешное действие. Ожидается: видимый фокус, понятные подписи и ошибки на русском, ввод не теряется, кнопки не создают параллельных запросов, состояние соединения и результат повтора различимы. Поведение Enter/Shift+Enter согласовать с UX до фиксации ожидаемого.

## Статусы и временные события — этап 2

### ST-01 — Delivered/read и монотонность [P0; FR-CHAT-9, WS §10; integration/UI]
Шаги: B подтверждает delivered=5, read=7; затем отправляет повтор и меньший seq из второй вкладки, меняет порядок доставки событий A. Ожидается: read=7 и delivered≥7; курсоры никогда не уменьшаются; все вкладки участников получают актуальное состояние; после reconnect оно восстановлено из history. Запись сервером в сокет сама по себе не означает delivered.

### ST-02 — Защита статусных курсоров [P0; FR-HIST-3, WS §10; integration]
Шаги: C посылает read/delivered чужого чата; B посылает seq выше last_seq, отрицательный, дробный и нечисловой. Ожидается: чужой чат forbidden; выход за диапазон целого курсора — invalid_seq, ошибка типа — invalid_payload; курсоры/чужие данные не меняются. Read продвигает delivered и вызывает обе рассылки при необходимости.

### ST-03 — Presence нескольких вкладок [P1; FR-CHAT-10, WS §11; integration/UI]
Шаги: открыть B1/B2, закрыть B1, затем B2; проверить снимок при входе A и наблюдение C без общего чата; на этапе 3 оборвать сеть без Close. Ожидается: online, пока живо хотя бы одно соединение; offline после последнего с last_seen_at; unknown не показан как offline; C не получает presence B. На этапе 3 проверить TTL и агрегацию по инстансам.

### ST-04 — Typing, TTL и вкладки [P1; FR-CHAT-10, WS §12; fake timers/integration/UI]
Шаги: B1/B2 отправляют typing=true; B1 отправляет false; потерять false от B2; передать старое событие после нового, перевести часы клиента. Ожидается: true от клиента не чаще раза в 2 с; сигнал жив максимум 5 с после приёма; false одной вкладки не сбрасывает другую; старый ts игнорируется; индикатор исчезает по TTL даже при потере false и сдвиге часов. После reconnect typing не переигрывается, C не получает событие чужого чата.

## Дополнительные проверки этапа 3

### OPS-01 — Нагрузка [P1; NFR-1; k6]
Шаги: выполнить профиль из тест-плана с 2 000 соединений и около 200 сообщений/с на одном chat-инстансе. Ожидается: p95 доставки онлайн-получателю ≤300 мс; отчёт содержит ошибки/таймауты, фактические соединения/RPS и ресурсы; сверено сохранение/доставка. Нельзя подменять latency доставки временем ack.

### OPS-02 — Наблюдаемость и rate limit [P1; NFR-4..5; integration/manual]
Шаги: проверить health/ready, JSON-логи с request_id, метрики и Grafana; превысить настроенный Nginx limit_req; восстановить нормальную частоту. Ожидается: readiness отражает возможность обслуживать запросы по согласованной политике; метрики показывают соединения/сообщения/ошибки/latency; секреты не логируются; лимит применяется согласно конфигурации и не блокирует обычный поток после восстановления. Значения лимитов и HTTP-код отказа закрепить в конфигурации, не предполагать 429 автоматически.

### OPS-03 — PWA и изоляция сессий [P1; FR-WEB-6, NFR-4; browser/manual]
Шаги: проверить manifest/иконки/установку; загрузить приложение, перейти офлайн; выйти из A и войти B; обновить service worker. Ожидается: офлайн-оболочка открывается, состояние сети явно показано; приложение не выдаёт локальный ввод за доставленный; новый пользователь не видит кэшированные приватные данные A; обновление оболочки не создаёт ложных ack/дублей. Политику кэширования приватных данных согласовать отдельно.

### ENV-01 — Воспроизводимость и staging [P1; NFR-7, задача #38; manual/integration]
Шаги: в чистом тестовом окружении подготовить .env по README, поднять Compose, позднее — полный стек; создать сообщение, перезапустить контейнеры без удаления volume; выполнить staging reset и проверить изоляцию. Ожидается: документированные команды работают, сервисы становятся ready, данные PostgreSQL сохраняются; seed/reset воспроизводимы и не затрагивают production. Сейчас Compose проверяет только инфраструктуру; полный MVP этим не подтверждается.

## Что проверить сейчас в каркасе

Уже написанные Go-тесты покрывают конфигурацию, health/readiness, request_id/logging, panic recovery, поведение Flush/Hijack и shutdown. Их имеет смысл запустить существующей командой `make test` в подходящем Go/CGO-окружении, а не дублировать новым набором. Frontend: `npm test`, `npm run lint`, `npm run build` после установки зависимостей.

Предлагаемые дополнительные проверки по мере превращения шаблона в сервис: readiness при недоступной обязательной БД; отсутствие чувствительных данных в бизнес-логах; работа настоящего WS Upgrade и shutdown активных сокетов через middleware. Это поведение будущих сервисов, а не основание требовать зависимости от БД у текущего шаблона.
