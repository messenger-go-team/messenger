# «Вернуться позже» — кейсы MVP

Источник: [T48](https://github.com/messenger-go-team/messenger/issues/48), [#84](https://github.com/messenger-go-team/messenger/issues/84), [#85](https://github.com/messenger-go-team/messenger/issues/85), [history OpenAPI](../../../api/openapi/history.yaml), SPEC FR-LATER-1..5. [Общие правила](README.md). Все кейсы **Not run**; UI-ожидания по несогласованным макетам #85 требуют подтверждения.

### LATER-01 — Меню и «Просто сохранить» [P1; MVP; API/UI/manual]

**Предусловия:** A видит сохранённое сообщение B в AB, активной записи A для него нет.

**Шаги:**

1. Открыть меню «Вернуться позже» у сообщения. Выбрать «Просто сохранить».
2. Проверить POST /later {chat_id,message_id,due_at:null}, затем GET /later и перезагрузку.

**Ожидаемый результат:**

1. В меню четыре варианта: «Просто сохранить», «Через час», «Вечером», «Выбрать время». Pending без серверного message_id не подменяет сохранённую цель.
2. Первое сохранение → 201 LaterEntryResult; entry.status=unscheduled, due_at=null. В личном списке одна запись без срока, сохранённая после перезагрузки.

### LATER-02 — «Через час» и произвольное время [P1; MVP; API/UI/manual]

**Предусловия:** Управляемое время устройства T; известна TZ, две разные цели.

**Шаги:**

1. Для первой цели в момент T выбрать «Через час»; для второй — валидные будущие дату и время через «Выбрать время».
2. Проверить готовые due_at в POST /later, ответы и личный список.

**Ожидаемый результат:**

1. Клиент рассчитывает срок T+1 час и выбранное локальное время, отправляет абсолютную UTC-строку RFC3339 с Z, не название пресета/TZ.
2. При времени сервера до обоих сроков статус scheduled; значения соответствуют выбранным моментам, доступны перенос и переход к сообщению.

### LATER-03 — «Вечером»: границы 19:00 и календарный день [P1; MVP; API/UI/manual]

**Предусловия:** Устройство Europe/Moscow (UTC+03:00), управляемые локальные часы; новая цель на каждый параметр.

**Шаги:**

1. Для 16.11.2026 18:59, 19:00, 19:01 и 23:59 выбрать «Вечером», перехватить due_at.
2. Отдельно выбрать пресет 31.12.2026 в 19:00; повторить в TZ с переходом часов через границу календарного дня, если она входит в поддерживаемую матрицу.

**Ожидаемый результат:**

1. В 18:59 → 16.11 19:00 локально (2026-11-16T16:00:00Z); в 19:00,19:01,23:59 → 17.11 19:00 (2026-11-17T16:00:00Z). Ровно 19:00 уже относится к следующему дню.
2. 31.12 19:00 → 01.01.2027 19:00 локально (2027-01-01T16:00:00Z). Используется следующий календарный день в TZ устройства, а не безусловное прибавление 24 часов.

### LATER-04 — Смена TZ не переносит сохранённый срок [P1; MVP; API/UI/manual]

**Предусловия:** A сохранил запись с due_at=2026-11-17T16:00:00Z на устройстве UTC+03:00.

**Шаги:**

1. Сменить TZ устройства на UTC, перезагрузить приложение, запросить GET /later.
2. Открыть запись и сверить отображаемое локальное время и значение API.

**Ожидаемый результат:**

1. Абсолютный due_at остался прежним, новый пресет автоматически не рассчитывается.
2. Локальный показ соответствует 16:00 UTC; срок записи не смещён сервером или клиентом. Сравнение due/scheduled идёт относительно server_time, не случайного сдвига часов устройства.

### LATER-05 — Три группы, граница срока и порядок [P1; MVP; API/UI/manual]

**Предусловия:** Управляемое время БД S; есть записи с due_at<S, =S, >S, null, а также равные сроки/created_at и известные UUID.

**Шаги:**

1. GET /later при фиксированном S; сравнить server_time, status и порядок entries.
2. Перевести БД за срок будущей записи и обновить список; на отдельном пустом аккаунте GET /later.

**Ожидаемый результат:**

1. due включает равенство S, затем scheduled, затем unscheduled. В группах со сроком порядок due_at,created_at,id по возрастанию; без срока — created_at,id. Все статусы рассчитаны по одному server_time, список полный без пагинации.
2. Запись переходит из scheduled в due после свежего ответа. Пустой список → 200 с entries=[], не ошибка/204.

### LATER-06 — Повторное и конкурентное сохранение без дубля [P0; MVP; API/UI/manual]

**Предусловия:** Для A нет активной записи сообщения M; известны два срока T1/T2.

**Шаги:**

1. POST /later для M; повторить с другим сроком и с null.
2. На чистой цели одновременно отправить два сохранения; затем GET /later.

**Ожидаемый результат:**

1. Сначала 201, потом 200; активный entry.id и created_at сохранены, due_at обновлён, active-запись одна.
2. Максимум одна активная запись на (A,message_id): создание 201, повторное обновление 200. Итоговый срок соответствует последнему сериализованному изменению БД, не обязательно последнему пришедшему ответу.

### LATER-07 — Перенос срока и снятие срока [P1; MVP; API/UI/manual]

**Предусловия:** У A одна доступная активная запись due.

**Шаги:**

1. PATCH /later/{id} с будущим due_at; затем с null; затем с допустимым прошлым временем.
2. После каждого запроса GET /later.

**Ожидаемый результат:**

1. Каждый PATCH → 200 LaterEntryResult: тот же id/message/created_at, новый due_at и updated_at; прошлое время допустимо.
2. Запись последовательно scheduled, unscheduled, due относительно соответствующего server_time; нет дублей, порядок групп обновлён.

### LATER-08 — «Готово», повтор и новое сохранение [P0; MVP; API/UI/manual]

**Предусловия:** Активная доступная запись E1 для M принадлежит A.

**Шаги:**

1. POST /later/{E1}/done, повторить; обновить список и перезагрузить приложение.
2. Снова POST /later для M, получить E2; отправить запоздалый done по E1.

**Ожидаемый результат:**

1. Каждый done по доступной E1 → пустой 204; E1 отсутствует в активном списке и после перезагрузки.
2. Новая активная запись → 201 с новым id E2. Повтор done старой E1 не завершает E2; E2 остаётся активной. Пустой 204 не разбирается как JSON.

### LATER-09 — Напоминание при открытом приложении [P0; MVP; API/UI/manual]

**Предусловия:** A авторизован, вкладка активна; ближайший срок известен из успешного GET /later с server_time.

**Шаги:**

1. Дождаться срока при открытом приложении и проверить обновление списка перед напоминанием.
2. Одновременно активировать периодический таймер и таймер срока; после успеха сверить список.

**Ожидаемый результат:**

1. Клиент делает свежий GET /later; напоминание только по доступной due-записи свежего ответа, не по старому кешу. Не требуется системный push.
2. Не больше одного GET /later одновременно; триггеры объединены. Срок/таймер рассчитывается с учётом server_time, напоминание не меняет active/done само по себе.

### LATER-10 — Просроченное напоминание после повторного открытия [P0; MVP; API/UI/manual]

**Предусловия:** Есть scheduled-запись A, приложение закрыто до срока.

**Шаги:**

1. Перевести время БД за срок, открыть приложение и дождаться GET /later.
2. Открыть цель из напоминания, ответить B, нажать «Готово», перезагрузить приложение.

**Ожидаемый результат:**

1. После загрузки доступной активной due-записи показано внутреннее напоминание. Работа при закрытом приложении и фоновый push не требуются.
2. Загружена правильная цель, переписка работает; done → 204, запись исчезает и не возвращается после перезагрузки. B видит обычную переписку, не приватную отметку A.

### LATER-11 — Запись из другой вкладки и обязательное напоминание [P1; MVP; API/UI/manual]

**Предусловия:** Два независимых прогона: у активной видимой вкладки A1 список пуст либо содержит только unscheduled-записи; A2 — тот же аккаунт. Часы клиента/БД управляемы и согласованы, нет ошибок сети. Для новой цели M установлен будущий срок T с запасом больше периода polling (например, через 60 с); в A1 нет локальной копии этой записи или таймера T. Вкладка A1 остаётся открытой и активной до показа напоминания.

**Шаги:**

1. В A2 сохранить M со сроком T. Не переоткрывать экран/приложение A1 и не обновлять его вручную; дождаться периодического GET /later в A1.
2. После обнаружения scheduled-записи в A1 перевести часы к T; запрос ближайшего срока завершить успешным свежим ответом с той же доступной записью status=due.
3. Проверить видимое напоминание в A1 и дождаться следующего периодического GET /later после этого успешного ответа.
4. Отдельно скрыть A1, изменить/завершить другую запись через A2, вернуть A1 на передний план и дождаться свежего ответа.

**Ожидаемый результат:**

1. GET начинается не позднее 30 с после завершения предыдущего успешного запроса, в том числе при исходном пустом списке/только unscheduled. A1 обнаруживает M как scheduled и учитывает её срок без повторного открытия.
2. При T выполняется обновление списка с учётом server_time; свежий успешный ответ содержит M как due. Одно только обнаружение/перемещение строки в список не считается прохождением кейса.
3. **Напоминание по M обязательно показано внутри приложения** с правильной целью/ID. Отсутствие показа при доступной due-записи — Fail. После успеха polling продолжается: следующий GET начинается не позднее 30 с после завершения предыдущего успешного; не больше одного GET одновременно.
4. В фоне polling необязателен; возвращение запускает свежий GET. Изменённая запись соответствует серверу, завершённая не восстанавливается из кеша.

### LATER-12 — Напоминание после одного 503 и автоматического повтора [P0; MVP; API/UI/manual]

**Предусловия:** Видимая активная вкладка A, известная scheduled-запись M со сроком T в кеше. Часы/ответы управляемы; M остаётся доступной активной записью на сервере после T. Напоминание по M ещё не показывалось. Без ручного обновления страницы/списка.

**Шаги:**

1. При наступлении T на GET /later вернуть ровно один 503; зафиксировать время завершения отказа и состояние напоминаний.
2. Продвинуть тестовые часы на 5 с после отказа. На автоматический повтор вернуть 200 со свежим server_time >= T и доступной записью M со status=due.
3. Проверить показ напоминания и следующий периодический GET /later. Для проверки сброса backoff на новом запросе отдельно вызвать один временный отказ.
4. В независимых прогонах из исходного состояния вызвать несколько сетевых/5xx отказов, затем 200 с доступной due-записью; отдельно вернуть 401 вместо временного отказа.

**Ожидаемый результат:**

1. 503 не превращается в успешный пустой список. Новое напоминание не показывается по устаревшему кешу; автоматическое восстановление не требует действия пользователя.
2. Повтор начинается через 5 с, получает свежий успешный ответ с M. Запросы не выполняются параллельно.
3. **Напоминание по M обязательно показано после успешного автоматического повтора**; отсутствие показа — Fail. Следующий периодический GET начинается не позднее 30 с после завершения успешного. Backoff сброшен: новый одиночный временный отказ снова повторяется через 5 с.
4. Для сети/5xx интервалы 5,10,20,30 с и далее 30 с до успеха; после успешного свежего ответа с доступной due-записью напоминание обязательно появляется, polling продолжается. 401 обрабатывается через обычное восстановление auth, а не этот цикл 5xx. Отрицательный вариант успешного списка без M выполняется отдельно в LATER-23.

### LATER-13 — API-контекст и переход UI без фиксированного limit [P0; MVP; API/UI/manual]

**Предусловия:** M в середине истории AB за пределами загруженной UI страницы; известны ID/seq ближайших соседей, включая возможные числовые пропуски. A имеет доступ к цели; есть собственная Later-запись/напоминание для перехода. Доступны журнал запросов и доставка контролируемого WS-дубля M. Прямые API-запросы не вызывают UI-показ/POST /read.

**Шаги:**

1. Отдельным API-клиентом выполнить GET /chats/{chat_id}/messages/{message_id}/context?limit=1 и затем тот же запрос с limit=3, независимо от действий UI.
2. В UI открыть M из личного списка/напоминания, не подменяя выбранный клиентом limit. Проверить фактический context-запрос и переход к цели.
3. Продолжить в UI загрузку более старых/новых сообщений через обычную пагинацию с курсорами полученного окна; доставить WS-дубль M с тем же серверным ID и сверить результат.

**Ожидаемый результат:**

1. Оба ответа 200 содержат target_message_id=M и цель ровно один раз. При limit=1 возвращается только M; при limit=3 — M и ближайшие доступные старый/новый соседи, seq по возрастанию. Числовые пропуски seq не заменяют соседние сообщения несуществующими номерами.
2. UI загружает контекст и открывает правильную M, точный фокус — по #85. Клиент может опустить limit (default 50) или передать любое допустимое значение 1..100. Не требовать от UI limit=1 либо 3; корректный вариант без параметра не является Fail. Оценивается фактическое окно, не выдуманный обязательный размер UI.
3. next_before_seq/next_after_seq соответствуют первому/последнему seq фактического окна; дальнейшие запросы используют before_seq/after_seq, флаги описывают наличие соседей на момент ответа. REST и WS объединяются по серверному ID/(chat_id,seq), M видна ровно один раз. Навигационное окно не продвигает курсор синхронизации всей истории (подробный recovery — UNREAD-11).

### LATER-14 — Границы окна и ошибки context [P1; MVP; API/UI/manual]

**Предусловия:** M у первого/последнего края истории; A имеет доступ, C не имеет.

**Шаги:**

1. Запросить context limit=1,50 по умолчанию,100; у края проверить отсутствие переноса незанятых соседних мест на другую сторону.
2. Отдельно limit=0/101, before_seq/after_seq в context, некорректный UUID; без JWT и от C с корректными UUID.

**Ожидаемый результат:**

1. 200 включает цель; соседей floor((limit-1)/2) старше, остальных новее. У края ответ может быть короче limit; это не потеря сообщений.
2. Невалидные параметры → 422, нет/невалидный JWT → 401; недоступная C цель → 404 без данных. Обычное чтение истории чужого чата остаётся 403.

### LATER-15 — Успешные личные действия владельца не раскрываются собеседнику [P0; MVP; API/UI/manual]

**Предусловия:** A/B — участники AB, C не участник. M сохранено в переписке и доступно A/B, но активных Later-записей для M пока нет ни у A, ни у B. Подготовлен будущий срок для переноса. Есть доступ к сырым входящим WS-сообщениям B и чтению его last_read_seq тестовыми средствами; GET /chats подтверждает unread_count. B не открывает сообщения/не отправляет POST /read; другие действия, меняющие курсоры/WS, на время опыта исключены. При отсутствии наблюдения за WS/курсором интеграционный прогон Blocked.

**Шаги:**

1. До любых действий A подключить наблюдатель к сокету B; записать исходные last_read_seq B, unread_count AB и GET /later B. Наблюдение не прекращать до окончания save/PATCH/done владельца.
2. От A успешно POST /later для M; сохранить entry.id=E_A. Сразу проверить сокет, курсор и список B.
3. От A успешно PATCH /later/{E_A} с новым due_at. Снова проверить те же данные B.
4. Пока E_A ещё активна, от B выполнить PATCH и done по E_A; убедиться, что отказ не изменил запись A.
5. От A успешно POST /later/{E_A}/done, обновить списки и снова сверить сокет/last_read_seq/unread_count B с исходными значениями.
6. От B самостоятельно сохранить доступное ему M в E_B; сравнить личные списки. От C попытаться сохранить M и загрузить его context.

**Ожидаемый результат:**

1. Наблюдение начато до создания E_A, исходные значения записаны. Иначе отсутствие эффекта от уже выполненного действия не считается проверкой приватности.
2. Save A → 201, E_A видна только в списке A. Ни сырые WS-события, ни GET /later B не раскрывают запись/действие/срок A; last_read_seq и unread_count B прежние.
3. PATCH A → 200 с обновлённым сроком той же E_A; B не получает события личного переноса, курсор/счётчик и его список неизменны. Успешный перенос обязателен: один отказ B его не заменяет.
4. Оба чужих действия B → одинаковый безопасный 404 без данных записи/сообщения. Срок и активность E_A не меняются.
5. Done A → пустой 204; E_A отсутствует в активном списке A. B не получает WS-события личного завершения/прочтения, его last_read_seq, unread_count и список не меняются. Для каждого успешного действия владельца доказательства собраны отдельно, не только один итоговый снимок.
6. Собственное сохранение B → 201 и отдельная E_B, не раскрывающая E_A; каждый видит только свои записи. C получает безопасный 404 для save/context без данных цели. Ошибочные запросы C не подменяют проверку успешных операций A.

### LATER-16 — Удалённая цель и потеря доступа [P0; MVP; API/UI/manual]

**Предусловия:** A сохранил M; доступны тестовые hooks удаления сообщения/чата и изменения membership без продуктового API удаления.

**Шаги:**

1. В отдельных прогонах удалить M, удалить чат или отозвать доступ A; обновить GET /later, дождаться срока.
2. Проверить ответ и наличие напоминания, не используя сохранённый текст как доказательство доступности.

**Ожидаемый результат:**

1. Недоступная запись исключена до формирования ответа; исчезает из UI после обновления, без текста/срока недоступной цели.

### LATER-22 — Авторизация, query-валидация и временный отказ записи [P0; MVP; API/UI/manual]

**Предусловия:** A имеет доступ к AB/AC, M принадлежит AB. Есть отсутствующие валидные UUID, отдельная свежая цель без активной записи и активная доступная E_A с известными due_at/state/updated_at. Для POST проверять как создание, так и обновление активной записи; PATCH и done адресовать действующей E_A владельца. У каждого параметра независимые исходные данные, остальные параметры/body валидны. API-клиент сохраняет сырую query string, включая неверные escape-последовательности; если клиент нормализует её, взять протокольный клиент/HTTP-test hook и проверить фактически отправленную строку. Есть контролируемый отказ хранилища до commit; без него интеграционная часть 503 — Blocked.

**Шаги:**

1. Для save/list/PATCH/done/context отдельно убрать/испортить/просрочить JWT. Для четырёх маршрутов Later повторить с невалидной query, чтобы проверить приоритет auth.
2. С валидным JWT независимо передать неверный UUID; сохранить AC+M из AB; обратиться к отсутствующим later_id/message_id. В body save/PATCH добавить неизвестное поле.
3. С валидным JWT и корректным body поочерёдно запросить **POST /later**, **GET /later**, **PATCH /later/{later_id}**, **POST /later/{later_id}/done**. На каждом независимо проверить сырые suffix: ?unexpected=1, ?limit=1, ?due_at=%zz, ?%zz=1, ?%. Неверное кодирование не исправлять и не переносить только на GET.
4. До/после каждого варианта сравнить активные записи и due_at/state/updated_at, затем выполнить контрольный GET /later без query на доступном хранилище.
5. Без query и с валидными JWT/body в независимых прогонах вызвать контролируемый отказ хранилища **до commit** для POST /later (создание/обновление), PATCH /later/{later_id} и POST /later/{later_id}/done. Проверить HTTP-ответ и состояние клиента, затем убрать отказ.
6. Сверить серверное состояние после восстановления и повторить валидные операции без сбоя. Не трактовать общий 503 как доказательство гарантированного отсутствия commit при другом, неизвестном исходе: здесь неизменность проверяется только для специально вызванного отказа до commit.

**Ожидаемый результат:**

1. Каждая защищённая операция → 401 без данных, включая комбинацию с невалидной query. JWT проверяется раньше параметров и обращения к ресурсам.
2. Невалидные UUID/неизвестные поля → 422; корректные, но отсутствующие/недоступные/несовпадающие ресурсы → 404 без данных. Параметры контекста проверяются отдельно: его допустимый limit не переносится на маршруты Later.
3. Все пять query-вариантов на каждом из четырёх маршрутов → **422** ApiError. Непустая query string запрещена даже при неизвестном ключе, limit или неверном percent-encoding; 200/201/204 вместо отказа — Fail. Пустая query для этих проверок не используется.
4. Отклонённые записи не создаются/не обновляются/не завершаются, исходные значения прежние; контрольный GET без query показывает реальный список. 422 не скрывается побочным успешным изменением.
5. Каждая из трёх операций записи при временной недоступности → **503 с code=service_unavailable** по LaterWriteUnavailable, не 200/201/204; в ответе нет SQL, секретов или данных записи. UI не подтверждает save/перенос/done как успех. Ошибка не объявляется пустым успешным списком, новым входом или успешным завершением записи.
6. Для заданного отказа до commit состояние прежнее, завершение не подтверждено. После восстановления новый валидный запрос даёт контрактный успех: POST 201/200 согласно исходной активности, PATCH 200, done пустой 204; список соответствует серверному результату, без дублей. Пропуск любого из четырёх query-маршрутов либо любой из трёх write-операций 503 — неполный прогон, не Pass.

### LATER-23 — Свежий список без записи не создаёт напоминание [P0; MVP; API/UI/manual]

**Предусловия:** В кеше A есть scheduled-запись M, напоминание ещё не показано. До срока запись завершена из A2 либо цель стала недоступна через тестовый hook; текущий серверный список пуст. **Шаги:**

1. В момент срока на GET /later вернуть один 503. Через 5 с разрешить автоматический повтор с 200, свежим server_time после срока и entries=[].

**Ожидаемый результат:**
