# Контакты и поиск — подробные кейсы

Источник: [T48](https://github.com/messenger-go-team/messenger/issues/48), [#68](https://github.com/messenger-go-team/messenger/issues/68), [auth](../../../api/openapi/auth.yaml), [history](../../../api/openapi/history.yaml), SPEC FR-AUTH-6..7. Общие окружение, данные, очистка и правила результата — в [README](README.md). Статус всех кейсов: **Not run**. Каждый параметр набора — отдельный прогон.

### CONTACT-01 — Пустой список и состояния экрана [P1; MVP; API/UI/manual]

**Предусловия:** У A нет контактов, JWT действителен.

**Шаги:**

1. Открыть «Контакты», задержав GET /contacts; затем вернуть 200 {"contacts":[]}.
2. Отдельно вызвать сетевую ошибку при первой загрузке, затем нажать повтор и вернуть пустой список.

**Ожидаемый результат:**

1. Сначала видна загрузка, после ответа — состояние пустых контактов, доступен поиск; это не ошибка и не 204.
2. Показана ошибка с действием повтора, а после успеха — пустой список. Ошибка не подменяется успешным пустым результатом.

### CONTACT-02 — Добавление, удаление и идемпотентность [P0; MVP; API/UI/manual]

**Предусловия:** A и B не добавлены друг у друга; C имеет независимый список.

**Шаги:**

1. От A дважды PUT /contacts/{B}, затем GET /contacts; отдельно выполнить два конкурентных PUT на новой паре.
2. Получить списки B/C. Дважды DELETE /contacts/{B} от A и снова получить список A.

**Ожидаемый результат:**

1. Каждый PUT возвращает пустой 204; у A ровно одна запись B, включая конкурентную проверку.
2. Списки B/C не получают A. Оба DELETE — пустой 204, B исчезает у A; остальные контакты неизменны, JSON из 204 не читается.

### CONTACT-03 — Сортировка и принадлежность списка [P0; MVP; API/UI/manual]

**Предусловия:** У A контакты с именами Qa_Z, qa_a, Qa_M; у B другой набор.

**Шаги:**

1. Получить список A, затем B, затем переключить аккаунт в UI с A на B.
2. Добавить контакты A в другом порядке и повторить GET.

**Ожидаемый результат:**

1. Каждый ответ 200 содержит только собственный полный список без пагинации; UI B не показывает данные A.
2. Порядок по ASCII lower-case username: qa_a, Qa_M, Qa_Z; исходное написание сохранено. Контакт определяется по id, обязательного is_contact нет.

### CONTACT-04 — Ошибки контактов [P1; MVP; API/UI/manual]

**Предусловия:** Есть UUID A, отсутствующего пользователя U и существующий B.

**Шаги:**

1. PUT собственного A и несуществующего U; PUT/DELETE невалидного UUID.
2. DELETE собственного A и отсутствующего U; для GET/PUT/DELETE отдельно убрать JWT, испортить или просрочить его.

**Ожидаемый результат:**

1. PUT A → 422, PUT U → 404; неверный UUID → 422. Нет изменений списка.
2. DELETE A/U → пустой 204. Каждый защищённый метод с отсутствующим/невалидным/истёкшим JWT → 401 ApiError; данные не раскрываются.

### CONTACT-05 — Prefix-поиск: регистр, лимит и ошибки [P1; MVP; API/UI/manual]

**Предусловия:** Отдельный набор: Alice_1 и Malice_1, других совпадений ALICE нет; A — другой пользователь. Независимые наборы: 21+ совпадений общего prefix и валидные username для границ 1/32; известен prefix без совпадений.

**Шаги:**

1. Выполнить GET /users/search?prefix=ALICE, затем prefix=alice на отдельном наборе. Независимо проверить общий prefix с 21+ совпадением, границы 1/32 и prefix без совпадений.
2. Отдельно отправить без prefix, пустой, длиной 33, с кириллицей, @, пробелом, дефисом; повторить валидный без JWT.

**Ожидаемый результат:**

1. Для ALICE/alice ответ 200 обязательно содержит ID Alice_1 с username точно Alice_1 и не содержит ID Malice_1; пустой users здесь — Fail. Для массового набора выдача непустая, не больше 20, все username начинаются с prefix без учёта регистра. Границы 1/32 возвращают подготовленные совпадения; без совпадений users=[]. Порядок глобальной выдачи не задан.
2. Некорректный prefix → 422; нет/невалидный/истёкший JWT → 401. Тела соответствуют auth OpenAPI.

### CONTACT-06 — Локальная подстрока и отдельный глобальный prefix [P1; MVP; API/UI/manual]

**Предусловия:** Контакт A — AlphaBob; глобально есть Bob_new, отсутствующий в контактах.

**Шаги:**

1. Ввести bob в экране контактов; проверить локальный блок и GET /users/search?prefix=bob.
2. Изменить регистр ввода на BOB.

**Ожидаемый результат:**

1. AlphaBob остаётся в локальных контактах по вхождению подстроки; Bob_new находится глобально по началу username. Алгоритмы не подменяют друг друга.
2. Регистр не меняет результат ни локального фильтра, ни API-поиска; написание имён в строках исходное.

### CONTACT-07 — Пустой ввод и очистка запроса [P1; MVP; API/UI/manual]

**Предусловия:** У A несколько контактов; ответ глобального поиска можно задержать.

**Шаги:**

1. При пустом поле открыть экран и проверить сетевой журнал.
2. Ввести валидный prefix, задержать ответ, очистить поле и доставить старый ответ.

**Ожидаемый результат:**

1. Показаны все контакты; GET /users/search с пустым prefix не отправляется.
2. Восстановлен полный локальный список, глобальная выдача очищена; поздний ответ не восстанавливает старые строки.

### CONTACT-08 — Невалидный ввод глобального поиска [P1; MVP; API/UI/manual]

**Предусловия:** Загружены валидные контакты Alice_1 и Bob_1, длина username не больше 32; показана глобальная выдача предыдущего валидного prefix.

**Шаги:**

1. По отдельности ввести кириллицу, @ и строку из 33 символов; не создавать username, нарушающий auth-контракт. Проверить локальный блок и сетевой журнал.
2. Доставить задержанный ответ прошлого prefix, затем ввести Alice.

**Ожидаемый результат:**

1. Невалидный глобальный запрос не уходит; в «Найдено» подсказка о допустимом вводе, не пустая выдача/серверная ошибка. Локальная фильтрация применяется и даёт пустой результат на этих данных: валидный username не содержит кириллицу/@ и не может включать подстроку длиной 33. Прежние строки контактов не остаются видимыми, старая глобальная выдача скрыта.
2. Поздний ответ игнорируется; после ввода Alice локальный список снова содержит Alice_1, запускается актуальный глобальный поиск. Не требовать положительного локального совпадения для недопустимого username.

### CONTACT-09 — Быстрый ввод и устаревшие ответы [P1; MVP; API/UI/manual]

**Предусловия:** Есть разные результаты для a и al; доступен контроль времени/порядка ответов.

**Шаги:**

1. Быстро набрать a, al, ali; проверить debounce по настройке клиента без придуманного фиксированного интервала.
2. Для двух реально отправленных запросов доставить новый ответ раньше старого; отдельно ответ после ухода с экрана.

**Ожидаемый результат:**

1. Нет отдельного глобального запроса на каждую промежуточную клавишу; актуальное значение обработано после debounce.
2. Отмена либо игнорирование старого ответа сохраняет выдачу последнего ввода; ушедший экран не обновляется старой выдачей.

### CONTACT-10 — Исключение себя и повторных строк [P1; MVP; API/UI/manual]

**Предусловия:** A попадает в API-поиск; B — контакт A и совпадает с локальным и глобальным запросом.

**Шаги:**

1. Отобразить запрос с A/B в ответе API.
2. На согласованных данных вернуть B с одним и тем же ID в GET /contacts и глобальном prefix-поиске; проверить строку и действие «Удалить». Затем добавить найденного C и обновить список.

**Ожидаемый результат:**

1. В UI нет A; B показан один раз по id, исключение дублей применяется между показанными локальными строками и «Найдено». Исключение себя не требуется от самого API.
2. B остаётся одной строкой в локальных контактах; в «Найдено» второй строки этого ID нет, доступно «Удалить», не «Добавить». Принадлежность определяется по полному GET /contacts; после добавления C нет дубля между блоками. Недостижимый на согласованных данных вариант «контакт совпал с prefix, но не с локальной подстрокой» не используется.

### CONTACT-11 — Новый и существующий чат из двух источников [P0; MVP; API/UI/manual]

**Предусловия:** Две независимые пары без чата: A–D (D добавлен в контакты A) и A–E (E только в глобальном поиске, не контакт). Общий существующий AB не использовать для проверки 201; перед каждым прогоном подтвердить отсутствие AD/AE в тестовой БД.

**Шаги:**

1. Из контактов A нажать «Написать» для D и проверить POST /chats/personal {"user_id":"<UUID D>"}; независимо из глобального поиска A нажать «Написать» для E и проверить {"user_id":"<UUID E>"}. UUID B не подставлять: AB уже существует.
2. Вернуться к исходной строке и повторить «Написать»; повторить четыре комбинации: контакты/поиск × новый/существующий чат.

**Ожидаемый результат:**

1. Для каждой новой пары AD/AE 201 Chat; открывается чат с правильным собеседником. Из поиска контакт добавлять не обязательно, список контактов сам не меняется.
2. Повтор из контактов снова передаёт user_id=D и возвращает 200 с прежним Chat.id пары AD; повтор из поиска передаёт user_id=E и возвращает 200 с прежним Chat.id пары AE. Нет второго чата или дублей участников; перепутанный user_id — Fail, даже если сервер корректно отвечает для другой пары.

### CONTACT-12 — Удаление контакта сохраняет переписку [P0; MVP; API/UI/manual]

**Предусловия:** A добавил B; есть чат AB с сохранёнными сообщениями и известным id.

**Шаги:**

1. Удалить B и обновить GET /contacts; открыть AB через список чатов.
2. Обменяться новыми сообщениями A/B и открыть чат из поиска без повторного добавления.

**Ожидаемый результат:**

1. Пустой 204, B отсутствует только в контактах A; прежние chat_id, история и права доступны.
2. Новые сообщения доставляются и сохраняются; поиск открывает тот же чат, удаление контакта не блокирует переписку.

### CONTACT-13 — Сеть, 401 и повтор действия [P1; MVP; API/UI/manual]

**Предусловия:** Загружен корректный список; доступны управление ответами и тестовая авторизация.

**Шаги:**

1. При добавлении/удалении/создании чата задержать ответ и повторно нажать действие; отдельно вернуть ошибку сети или 401.
2. Для поиска вернуть ошибку; восстановить сеть/авторизацию и повторить действие.

**Ожидаемый результат:**

1. Нет параллельных запросов одной кнопки, видна занятость. Отказ не объявляется успехом; ошибочный create не открывает чужой/несуществующий диалог. 401 идёт через восстановление авторизации.
2. Последний корректный список контактов сохранён с текущим фильтром; ошибка глобального поиска относится к «Найдено». Повтор приводит к серверному состоянию без дублей и вечной загрузки.

### CONTACT-14 — Пустая выдача отличается от пустых контактов [P1; MVP; API/UI/manual]

**Предусловия:** У A есть контакты, не совпадающие с выбранным валидным prefix.

**Шаги:**

1. Ввести prefix без локальных/глобальных совпадений и вернуть API 200 users=[].
2. Очистить поле; затем очистить контакты тестовыми средствами и открыть экран снова.

**Ожидаемый результат:**

1. Пустой результат поиска не отображается как ошибка и не означает отсутствие всех контактов.
2. Сначала снова видны контакты, после очистки данных — отдельное состояние пустого списка с доступным поиском.

### CONTACT-15 — Три раскладки и клавиатура [P1; MVP; API/UI/manual]

**Предусловия:** Согласованный макет контактов, пустой/полный список и длинные username; браузерная матрица записана в прогоне.

**Шаги:**

1. На 360/768/1440 CSS px проверить пустой/заполненный экран, оба блока поиска, добавление, удаление и «Написать».
2. Пройти поле и действия Tab/Shift+Tab/Enter, проверить видимый фокус и открытие экранной клавиатуры.

**Ожидаемый результат:**

1. Действия доступны без обрезки и нежелательного горизонтального скролла; на узком экране работает возврат, общая навигация и поиск в списке чатов сохранены. Точные размеры сверяются с макетом.
2. Управление доступно с клавиатуры, фокус различим, после перехода в чат не теряется; точное поведение по макету. При отсутствии нужного макета соответствующий UI-прогон Blocked.
